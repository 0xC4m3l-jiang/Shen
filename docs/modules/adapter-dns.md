## 1. 职责

### 做什么

按**来源**决定域名解析到**引擎**还是**真实业务**（`INT-2`）：

- 可疑来源 → 解析到引擎 IP（由引擎接住并继续判定）；
- 其余来源 → 解析到真实业务 IP，**完全走原路径**。

**本模块不产生源码。** 交付物是给现成 DNS 服务（CoreDNS）的配置模板，
放入 [`../../edge/dns/config/`](../../edge/dns/)。
这是 `AR-3`（L0 接入层禁止自研、必须复用现成组件）在 DNS 形态上的体现。

### 明确不做什么

- **禁止**自研 DNS 服务（`AR-3`）；
- **禁止**在本层做判定 —— 只按**来源**分流，不评估行为（`AR-7`）；
- **禁止**维护会话状态（`AR-7` / `INT-20`）；
- **禁止**解析到引擎后由引擎**改写业务响应**（`INT-8`）；
- **禁止**影响未经接入的域名 —— 必须只对**指定域名**生效（见 §6「配错的影响面」）。

> 规则 `MD-1`：本模块**不得**跨层拆分。

## 2. 输入 / 输出契约

| 方向 | 契约 | 定义位置 |
| --- | --- | --- |
| 输入 | DNS 查询（域名 + 客户端 IP） | DNS 协议本身 |
| 输出 | 按客户端网段不同的 A / AAAA 记录 | [`../../edge/dns/config/`](../../edge/dns/) 的模板 |

**无代码级契约。** 本模块不与核心有 gRPC 往来 ——
它只决定「请求发给谁」，不会调 `api/judge/v1`。这是它与 ③④ 的本质区别。

## 3. 依赖

| 允许依赖 | 原因 |
| --- | --- |
| CoreDNS（Apache-2.0） | `AR-3` 复用现成组件；`view` 插件支持按 `expr` 匹配客户端 |
| 真实业务的 A / AAAA 记录 | 分流的另一半目标 |

| 禁止依赖 | 原因 |
| --- | --- |
| 自研 DNS 服务 | `AR-3` |
| 判定面 / 遥测面 | 本层不做判定，也不上报（`AR-7`） |
| 任何 GPL / AGPL 系 DNS 服务（dnsmasq / mosdns / AdGuard Home） | `TB-16` 许可审计 |

> 为什么选 CoreDNS：**`Apache-2.0`**（`TB-16` 通过），且 `view` 插件可**纯配置**实现按来源分流，
> 不需要编译自定义插件。被否决的候选见 §8。

## 4. 关键规则

| 规则 | 与本模块的关系 |
| --- | --- |
| `AR-3` | L0 禁止自研 —— 本模块**零源码**，只有配置模板 |
| `AR-4` | 每层只选一个组件 |
| `INT-2` | 本模块对应的接入形态 |
| `INT-5` | 四种形态各自独立工作 |
| `INT-19` | 会话身份三级优先级 —— 本模块**不参与**会话识别 |
| `INT-23` | DNS 分流不得导致业务侧丢失真实来源 IP |
| `INT-25` | 白名单（内部 IP / 探针）**必须**在分流前生效 |
| `NI-5` | 未识别状态回落真实业务 —— DNS 侧的等价行为是**解析到真实业务** |
| `TB-16` | 所选 DNS 服务必须是通过许可审计的 |
| `TB-25` | 一个进程只允许一种语言 —— 本模块不引入新进程类型 |

## 5. 状态与生命周期

| 状态 | 存在哪里 | 生命周期 | 多副本一致性 |
| --- | --- | --- | --- |
| 分流规则 | CoreDNS 配置文件 | 随配置 reload | 各副本同一份配置 |
| **会话身份** | ❌ **不持有** | —— | —— |
| 缓存（DNS TTL） | CoreDNS 与客户端各自缓存 | 由 TTL 决定 | 见 §6 的 TTL 陷阱 |

> ⚠️ **DNS 缓存会延迟规则生效，也会延迟回退。** 客户端与递归解析器都可能缓存旧记录，
> 因此「把某个来源改成解析到真实业务」这个动作**不是瞬时的** ——
> TTL 必须按这一点设定（`INT-24` 要求阈值集中定义）。

## 6. 失败模式与降级

| 失败情形 | 行为 | 是否满足 `NI-1` | 依据 |
| --- | --- | --- | --- |
| DNS 服务整体不可用 | 解析失败 → 客户端拿不到地址 → **业务不可达** | ❌ **本形态最危险的失败** | `NI-1` |
| 规则配错（把正常来源解析到引擎） | 流量进引擎；引擎必须能继续放行到业务 | ✅ **前提是引擎可用** | `NI-3` / `INT-8` |
| 引擎不可用而 DNS 仍指向引擎 | 业务不可达 | ❌ **必须避免** | `NI-1` |
| 内网域名被误纳管 | 内部解析被劫持 | ❌ **必须避免** | `INT-25` |

> ⚠️ **本形态的 `NI-1` 风险显著高于其他三种。**
> 镜像形态天然不碰业务路径；代理形态引擎挂了可放行；但 **DNS 形态一旦把关，
> 引擎就是业务可达性的前置条件** —— 解析到引擎而引擎不可用，等于业务中断。
>
> 因此本模块的配置模板**必须**包含：
>
> 1. **只对白名单外的指定域名生效**，默认不接管任何域名；
> 2. **引擎侧必须有可用的放行路径**（即形态 ③ 的 `adapter-proxy` 或真实业务本身）；
> 3. **可一键回退**：把引擎的 A 记录改回真实业务 IP，且 TTL 要短到能快速生效。
>
> 这三条是接入物料的一部分，写入 [`../../edge/dns/`](../../edge/dns/) 的模板注释与
> 接入指南。**不满足这三条时禁止启用本形态。**

**另一个必须说清的陷阱**：CoreDNS 的 `view` 块**必须写在兜底块之前**。
若兜底块在前，它会先匹配所有请求，带 `view` 的块永远不会被命中 ——
表现为「配置看起来生效了，但分流完全不发生」，且**没有报错**。

## 7. 测试

## 8. 未决项

| # | 未决 | 阻塞什么 | 去向 |
| --- | --- | --- | --- |
| 1 | **② 与 ③ 组合是否违反 `AR-4`** —— DNS 把关后引擎必须能接住，最自然的接法就是形态 ③ 的 `adapter-proxy`。但 `AR-4` 禁止多层代理叠加争抢流量控制 | 本形态的推荐部署拓扑 | 需评审，可能新增 ADR |
| 2 | **引擎侧在阶段 2a 用什么接住** —— 阶段 3 有蜜罐，2a 没有 | 本形态能否端到端可用 | 见第 1 条 |
| 3 | **白名单与域名清单的来源** —— 静态配置还是从核心下发 | 多租户与运维体验 | [`../design/integration.md`](../design/integration.md) 的接入物料 |
| 4 | **TTL 取值** —— 属实测问题：太短则解析压力大，太长则回退慢 | 回退时间 | [`../design/terminology.md`](../design/terminology.md) §4.2 |
