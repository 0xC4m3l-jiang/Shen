## E1 · 语言 spike：核心能否胜任 ext_proc

### 为什么要做

[ADR-0005](../decisions/0005-layered-languages.md) 把核心定为 **Go**，但**没有实验数据支撑** ——
它明确承认自己是「论证，不是数据」。风险点很具体：

> `ext_proc` 是 **gRPC bidi streaming**，每个 HTTP 请求一条流，按
> `request_headers → request_body → response_headers → response_body → trailers` 分阶段响应。
> **每流的状态机要我们自己写**，不是 Envoy 的。这正是 AI 生成代码最容易写错、也最难测的形状。

### 任务

各写一个**最小** `ext_proc` 服务（两个臂）：

```text
输入：Envoy 发来的 ext_proc 流
处理：解析 request headers → 按配置返回一个路由决策头
输出：返回 HeadersResponse + clear_route_cache = true
```

**不含**任何判定逻辑、不含会话状态 —— 只验证协议形态与迭代成本。

### 对照臂

| 臂 | 语言 | 为什么是它 |
| --- | --- | --- |
| **主臂** | **Go** | 现行基线（ADR-0005） |
| 对照臂 | **Rust**（`tonic`） | 它是 ADR-0001 原定的回退目标；若主臂不达标，这就是替代方案 |

### 度量指标（六项 + 三项新增）

| # | 指标 | 归类 |
| --- | --- | --- |
| ① | 零到跑通耗时 | 上手成本 |
| ② | LOC | 表达力 |
| ③ | 增量编译耗时 | **内循环成本（真成本）** |
| ④ | 写第 1 个单测耗时 | 测试能力 |
| ⑤ | 加 1 个 mock 耗时 | 接口替代能力 |
| ⑥ | 加「第 2 个判别器」要改几处 | 扩展能力 |
| ⑦ | **bidi streaming 阶段状态机的正确性**（分阶段响应是否按序、是否会死锁 / 泄漏流） | **新增 —— 这是 ADR-0005 的真实风险点** |
| ⑧ | 单请求额外开销（P50 / P99） | 新增 —— 对照 AR-29 的 5 ms 预算 |
| ⑨ | 每流内存占用（并发 1k 流时） | 新增 —— 对照 NI-7 的资源围栏 |

### 判定标准（必须事先固定，不得事后调整）

| 情形 | 结论 |
| --- | --- |
| 主臂 ⑦ 正确，且 ⑧ P99 在预算内 | ✅ 维持 ADR-0005（Go 核心） |
| 主臂 ⑦ **不正确**（阶段状态机写不对 / 流泄漏） | ❌ 触发 [ADR-0005](../decisions/0005-layered-languages.md) 失效条件第 1 条 → 重开 |
| 主臂 ③ 增量编译让内循环不可接受 | ⚠️ 记录数据；若同时对照臂显著更优 → 考虑核心换语言 |
| 主臂 ⑨ 超 NI-7 资源围栏 | ❌ 需重新评估核心的无状态多副本模型 |

### 结果 · 2026-09-17

> ⚠️ **只跑了主臂（Go）。Rust 对照臂未执行**（本机未安装 Rust 工具链）
> → **`E1` 仍属未完成**。但主臂的 ⑦⑧⑨ 是 ADR-0005 的真实风险点，已有数据。

**spike 位置**：`/tmp/spike-extproc`（抛弃式，不入库 —— 不污染 `core/` 的模块结构）

| 文件 | 行数 | 内容 |
| --- | --- | --- |
| `server.go` | 147（**112 行有效代码**） | 最小 ext_proc 服务：六阶段分支 + 失败关闭 |
| `spike_test.go` | 437 | 7 个测试：自建 gRPC 驱动（bufconn 内存 + 真 socket 两种） |

#### 九项指标实测

| # | 指标 | 结果 |
| --- | --- | --- |
| ① | 零到跑通耗时 | 一个会话内（含 **2 次编译错** + **3 次驱动 bug** 的修正） |
| ② | LOC | 服务端 **112 行有效代码**（147 含注释）；测试 437 行 |
| ③ | 编译耗时 | 全量 **0.08 s** · 增量 **0.08 s** · 全部单测 **1.64 s** |
| ④ | 写第 1 个单测耗时 | —— **未单独计时** |
| ⑤ | 加 1 个 mock 耗时 | —— **未单独计时**（Go 只需实现 1 个接口，无需 mock 框架） |
| ⑥ | 加第 2 个判别器要改几处 | 仓库 `judge` 模块实测：**新增 1 个实现 + 注册 1 行，现有代码 0 处改动** |
| ⑦ | **阶段状态机正确性** | ✅ **通过**（见下） |
| ⑧ | 单请求额外开销 | 真 socket：P50 **48.8 µs** · P90 76.5 µs · **P99 116 µs** · max 450 µs |
| ⑨ | 每流内存 | **15.4 KB/流**（500 条并发实测） |
| 附 | 单核吞吐 | **41,421 流/秒** · 248,525 阶段往返/秒（bufconn 内存传输） |
| 附 | 依赖规模 | 10 个直接依赖 · **325 个包**编译进二进制 |

**⑦ 的细节**（这是本实验的核心）

- 六阶段（`request_headers` → `request_body` → `response_headers` → `response_body` → `request_trailers` → `response_trailers`）**正序各回对应分支**，无错配
- 200 条流依次开合后 **goroutine 回落到基线**（无泄漏）
- 未识别阶段回 `ImmediateResponse`（**失败关闭**），不静默放过
- 500 条流并发时服务端**同时持有 500 条**，互不干扰

#### 判定

| 事先固定的标准 | 实测 | 结论 |
| --- | --- | --- |
| 主臂 ⑦ 正确 | 正确 | ✅ |
| 主臂 ⑧ P99 在预算内 | 116 µs vs `AR-29` 的 **5 ms** = 用掉 **2.3%** | ✅ |
| 主臂 ③ 内循环可接受 | 增量 0.08 s | ✅ |
| 主臂 ⑨ 超 `NI-7` 围栏 | **不适用** —— `NI-7` 只要求「施加 cgroup CPU/内存上限」，**未规定字节数** | —— |

> ✅ **ADR-0005 / ADR-0006 的失效条件均未触发。维持 Go 核心。**
>
> ⑨ 的 15.4 KB/流 不是达标判据，而是**给 `NI-7` 定 cgroup 上限的输入**：
> 1000 并发流 ≈ **15.4 MB 堆**。

#### 意外收获（两条都进了 [`../../kb/known-issues.md`](../../kb/known-issues.md)）

1. ext_proc 流**必须 drain 到 EOF 或取消 context** —— 只 `CloseSend()` 会泄漏客户端流（实测 200 条流泄漏 205 个 goroutine）
2. 未识别阶段**必须**回 `ImmediateResponse` 失败关闭

#### 仍未回答

- **对照臂（Rust）** —— 工具链未安装，③⑥ 无对照，因此「若 Rust 显著更优」这一条**无法评估**
- ①④⑤⑥ 的人工计时
- **真实载荷**：本 spike 的消息体是空 `HttpHeaders` + 1 字节 `HttpBody`。`AR-29` 那 3 ms 里「跨进程 gRPC」的真实占比需要带真实载荷的重量
- **跨节点**（非本机）延迟

### 成本与复用

成本**极低**；两个 spike 骨架都能被后续实现复用（`api/` 的 `.proto` 定义可直接沿用）。

## E2 · TLS 指纹一致性：我方栈与真实站是否可区分

### 为什么要做

威胁模型 **T5** 标为 🔴 高、且**无任何缓解**：

> 若真实站是 nginx + OpenSSL，而我方栈（envoy / rustls / OpenResty）的 **JA3 / JA4 握手特征**不同，
> 对手**抓一次握手就知道"这不是同一个服务"** —— 此时所有内容层的伪装全部白做。**这是架构级缺陷。**

这是一个**可以用一天验证**的假设，但至今未测。

### 任务

```text
对同一站点采集两组 TLS ClientHello / ServerHello 特征：
  A 组：真实站原始栈（如 nginx + OpenSSL）
  B 组：我方拟用栈（Envoy / OpenResty / rustls）
比对：JA3、JA4、扩展顺序、支持的曲线 / 密码套件集合、ALPN、TLS 版本协商结果
```

### 判定标准

| 结论 | 后续动作 |
| --- | --- |
| A / B **不可区分** | ✅ 风险 R-1 关闭；现有 TLS 方案可用 |
| 可区分，但**仅差少数可配置项** | ⚠️ 调整我方栈配置使其对齐；重新验证 |
| 可区分且**无法通过配置对齐** | ❌ 需要 BoringSSL 级控制（Rust 侧 `boring` / 或让 L0 用与真实站同款代理）；**威胁模型 R-1 必须重估整个欺骗命题** |

### 成本

低（半天到一天）。**但它的结论可能改变项目前提** —— 因此优先级高于任何实现工作。

## E3 · 换底座后的 `AR-29` 实测（内嵌 Caddy）

### 为什么要做

[`ADR-0017`](../decisions/0017-caddy-l1-base.md) 把 L1 的转发与 TLS 终结换成**内嵌 Caddy**。
`AR-29` 要求业务路径 P99 额外延迟 **≤ 5 ms**，而 L1 是它的主要贡献者之一。
换底座后**旧的下界不再直接适用**：`E1` 的 116 µs 是「核心侧 ext_proc 空载往返」，
既不是新底座，也不是真实载荷。

### 任务

在形态 ③④ 各跑一轮接入演练，测三档：

```text
A 空载：单客户端串行请求（取框架下界）
B 真实载荷：混合静态 / 动态 / 大响应 / 流式，含 shadow 与接管两种模式
C 故障路径：核心不可达 / 引流后端不可达（回落路径的延迟不得恶化）
```

### 判定标准（先固定，不得事后调）

| 结论 | 后续动作 |
| --- | --- |
| P99 额外延迟 **≤ 5 ms** | ✅ `AR-29` 达标，底座继续 |
| **> 5 ms** | ❌ 触发 ADR-0017 失效条件 1：按 `AR-29` 回退到旁路镜像接入，或重开底座选型 |

### 成本

中（需真实业务与压测环境）。**必须在形态 ③④ 上线前跑掉。**

---

### 结果 · 2026-09-19（**主臂初测**，非最终结论）

**工具**：[`scripts/fingerprint/`](../../../scripts/fingerprint/README.md)（`make fp-capture` / `make fp-diff`，只依赖 Go 标准库 + 自写握手解析）。
**原始数据**：[`../research/e2-tls-fingerprint/`](../research/e2-tls-fingerprint/)（两组采集 JSON，逐字段可比对）。

| 项 | A 组：真实站（`example.com:443`） | B 组：我方栈（内嵌 Caddy → Go `crypto/tls`） | 判定 |
| --- | --- | --- | --- |
| TLS 版本 / 套件 / ALPN / 会话恢复 | TLS 1.3 · `TLS_AES_128_GCM_SHA256` · 无 ALPN · 支持 | 完全相同 | ✅ 一致 |
| **ServerHello 扩展序列** | `51-43` | `43-51` | ❌ **本质差异** |
| JA3S 原文 | `772,4865,51-43` | `772,4865,43-51` | ❌ **不同 ⇒ 可区分** |
| OCSP 装订 | 支持 | 不支持 | ⚠️ 可配置项 |
| 证书链形状 | 公有链 · 链长 4 · ECDSA | 自签 · 链长 1 · RSA | 仅证书（部署时替换） |

**结论（主臂）**：**不可对齐** —— 服务端扩展序列由 TLS 实现决定，Go 的 `crypto/tls` 与 OpenSSL 系实现顺序不同，
且**不提供**调整该顺序的配置。按本实验的判定标准，`R-1`（不可区分性）**必须重估**。

**⚠️ 局限（不得当作最终结论）**：

- **单站、单次采样**：A 组只采了 `example.com`（OpenSSL 系）；
- **结论对「客户站与我方栈是否同款」高度敏感**：若客户站本身也用 Caddy（或同为 Go 系），两侧天然一致 —— 此时无需任何改动；
- 未做多次采样与稳定性检验（TLS 1.3 的 ServerHello 形状在不同客户端 offering 下可能不同）。

**建议的后续动作**（按代价从低到高）：

1. **对客户真实站重复**：≥3 次采样、错开时间，并把 A 组换成**客户实际前端栈**；
2. **把「TLS 终结交客户 L0」列为 [`ADR-0017`](../decisions/0017-caddy-l1-base.md) 的重估选项** —— 客户 L0 用的就是真实站同款栈 ⇒ **指纹天然一致**，
   同时仍满足 `INT-22`（我们收到的是明文，读得到请求体）；代价是形态 ③④ 不再是「单组件」（要重新对 `AR-4` 说清楚）；
3. 若仍坚持自终结：评估换用与真实站同款的 TLS 实现（如 BoringSSL 系）—— 成本最高，且与「复用现成组件」的取向冲突。
