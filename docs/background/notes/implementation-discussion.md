## 1. D0 · 架构律（⏳ **待拍板**）

> **路由决策必须「会话出生即终局」。**

### 为什么

```text
Agent 第 1 跳  GET /api/user/1  → 真实业务 → {balance: 1000}
Agent 第 2 跳  GET /api/user/1  → 蜜罐 → {balance: 42}
                                   ↑ 同会话、同资源、两个答案 = 立刻识破
```

Agent 必然重复请求同一资源（验证、重试、翻页）。所以**一旦会话拿到真实数据，该会话就再也不能被改道**。

### 三条推论

| # | 推论 | 对设计的约束 |
| --- | --- | --- |
| 1 | **误导决策只能落在会话第一跳** | 判定器必须在**无会话历史**下判准 → 输入限于 IP / TLS 指纹 / UA / 首跳路径 / 首跳行为 |
| 2 | **首跳决策 = 该会话终局**（幂等于会话） | 判错只能靠「加重处置」补救，**不能**改道 |
| 3 | **加重处置必然可见**（挑战页 / 维护页 / 403） | 「中途拦截」与「透明改道」是两套互斥机制，无法无缝衔接 |

> ⚠️ 推论 3 是**决策取值**的核心输入（[ADR-0002](../decisions/0002-decision-model.md) 已据此拍板「三值 + `severity`」）：
> 若承认「加重处置必然可见」，它就是**另一套机制**，不该塞进透明改道的决策枚举里。

### 三种可选世界观

| 模式 | 机制 | 代价 | 状态 |
| --- | --- | --- | --- |
| **A 早定粘性** | 首跳判定，之后永不改道 | 无法靠累积证据 | 🔵 建议 MVP |
| **B 可升级**（参考实现路线） | 中途可升级，但升级可见 | 暴露"有东西在拦我"，Agent 会绕 | ❌ 建议明确拒绝 |
| **C 混合** | 首跳高置信才改道；中途只做**不可见加重**（限速、加噪声） | 最复杂，理论最优 | 🔵 演进终点 |

### 与旧结论的冲突

早前写「判定必须会话级有状态」。**该结论对「加重处置」成立，对「路由」有害。**

正确表述：**判定可累积用于加重处置；路由必须会话粘性且首跳确定。**

## 2. 关键工程决定（🔵 提案）

### 2.1 模型走 sidecar，不嵌入

```text
热路径  (<1ms)   核心：规则 + 查表                    ← 不含任何模型
近线    (~秒级)  Python sidecar 异步打分 → 回填规则表
离线    (分钟级) Python：训练 / 生成 / 画像 / 评测
```

| # | 好处 |
| --- | --- |
| 1 | 热路径不需要跑模型（不用绑 ONNX Runtime，不用为推理引入 FFI） |
| 2 | AI 全部留在 Python 生态（PyTorch / transformers / numpy 随意用） |
| 3 | **sidecar 挂了只降级不阻塞** —— fail-open 回落到纯规则 |
| 4 | 热路径 P99 不被推理污染 |

接缝 **S3**（核心 ↔ L4 分析）**必须**是 gRPC + 带版本号，**异步非阻塞**。
**禁止** FFI / CGO / 共享内存 / 嵌入式 Python（见 [`design/language.md`](../../design/language.md) 的 TB-24）。

### 2.2 读 body 后换后端 —— 不需要写代码

```text
ext_proc 读完请求体 → 写一个内部头 → 返回 clear_route_cache
   → Envoy 重新选路由 → 命中不同 cluster
```

`HeadersResponse.clear_route_cache = true` 是这条路成立的关键开关。
**⚠️ Envoy 版本差异必须实测**；若版本不支持 `filter_state` 链路，退化为「注入内部头 → 出站剥离」。

### 2.3 负载均衡策略

LB 策略**必须**用一致性哈希（`RING_HASH` / `MAGLEV`），扩缩容时迁移最少。
**禁止** `ROUND_ROBIN` —— 会话粘性会碎。

### 2.4 AI 生成内容的工程约束（⭐ 与 D0 直接相关）

若 AI 参与生成蜜罐内容：**输出必须落库 + 按 (会话, 资源) 缓存，同一请求永远返回同一答案。**

否则 LLM 的随机性会造成「同资源两次不同」—— **这正是 §1 架构律要防的东西，
而 AI 是最容易破坏它的组件**。

## 3. AI 能力（⚪ 占位 —— 独立的大模块）

### 3.1 明确不做（❌）

| 不做 | 理由 |
| --- | --- |
| 热路径逐请求调 LLM 做判定 | 延迟爆炸；CheeseWAF 类工作已在专门解决这个被自己制造出来的问题 |
| **对抗性提示注入作为主要手段** | **已被实测证伪**：参考实现自测显式注入 **0/8 服从**。有效的是**功能性伪装** |

### 3.2 三层切分

```text
热路径   (<1ms)   规则 + 预计算特征 + 查表          ← 不放 AI
近线     (~秒级)  异步打分 → 结果回填规则表          ← 模型在这里
离线    (分钟级)  内容生成 / 画像 / 蜜饵再生 / 评测   ← AI 主力
```

### 3.3 候选用途（按 价值 / 成本 排序，待评估）

| # | 用途 | 位置 | 备注 |
| --- | --- | --- | --- |
| 1 | **蜜罐内容的真实感**（假用户 / 假订单 / 假日志） | 离线 + 近线 | 直接提升不可区分性 —— **命题核心** |
| 2 | 行为序列建模（节奏、探索顺序、翻源码模式） | 近线 | 规则做不到；人 / Agent 区分的最强信号 |
| 3 | 情报提取与画像（行为序列 → TTP） | 离线 | 零延迟约束，纯收益，也是论文卖点 |
| 4 | 蜜饵多态与再生成 | 离线 | 对应综述空白 F（被众包识破后重生成） |

## 4. 效果保障（🔵 提案）

> **效果的第一性保障不是算法，是不变量（invariants）。**

### 4.1 差异哨兵 —— 建议作为**第一个**实现的东西

比判定器更早做。它是唯一能客观回答"欺骗成不成立"的装置，同时兼任回归测试、验收标准、论文评测指标。

```text
定时对同一组 URL，在真实业务与蜜罐各打一次，逐字段 diff：
```

| # | 检查项 |
| --- | --- |
| 1 | 状态码 |
| 2 | 响应头集合与取值（除 `Date` 等必然项） |
| 3 | `Content-Type` / charset |
| 4 | body 结构（JSON 键集合 + 类型；值可不同） |
| 5 | 错误格式（404 / 500 的 body 形状） |
| 6 | 时序分布（P50 / P99 是否落在对方分布内） |
| 7 | **幂等性**（同资源第 2、3 次是否同答案）← 与 D0 / §2.4 直接对应 |
| 8 | 分块与压缩行为（`Transfer-Encoding`、`Content-Encoding`） |
| 9 | TLS 握手特征（JA3 / JA4） |
| 10 | HTTP 版本与 ALPN |
| 11 | Cookie 行为（**不得引入新 cookie**，见 `NI-9`） |
| 12 | 重定向行为 |

### 4.2 姊妹装置：可用性哨兵

`NI-12` 要求的 `V-1…V-5` 需要一个**常驻执行者**，而不是 CI 里的一次性用例。

## 5. 最小可信路径（🔵 提案）

```text
第 0 步  差异哨兵                    ← 先有度量"欺骗成不成立"的能力
第 1 步  旁路镜像接入一个真实站点，跑两周，只观测     ← INT-11：零风险取得观察价值
第 2 步  反向代理 / Sidecar 接管，粘性 + 首跳判定
第 3 步  打开"只对高置信 Agent 误导"，看误调度率与识破延迟
第 4 步  才轮到 AI 生成蜜罐内容
```

**每一环都能独立证伪。** 若第 0 步证明改道一眼被看穿，后面全不用做 —— 这正是应该最先知道的事。
