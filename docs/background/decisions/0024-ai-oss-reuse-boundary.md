## 背景

阶段 A 的 AI 能力层（`analysis/llm/` 9 个模块 + `analysis/aicap/` 9 个模块）已实现并过门禁，
除 `PyYAML` 外**零第三方依赖**。本轮要回答的是：**这些手写能力里，哪些本可以直接复用开源实现？**

不决定的代价（三件具体的坏事）：

1. **重复造轮子的成本会持续累积。** `llm/extract.py` 那 91 行要自己覆盖 markdown 围栏、前置叙述、
   截断、转义、多顶层元素 —— 这不是一次性成本，是每一次「模型输出又一种畸形」的维护成本。
   `aicap/tasks/content.py` 的假数据同理。
2. **ADR-0023 的未解决 1 / 2（模型后端与 PII 检测）卡在同一个前置条件上**：
   「先过许可证台账 `TB-16`」。而 `TB-16` 要求「依赖必须经许可与漏洞审计」——
   本轮查证发现 `make licensecheck` **只审 Go 模块**（`go list -deps` 反推，源码
   `scripts/licensecheck/main.go::buildModules`），`analysis/requirements.txt` 的运行期依赖
   **没有审计面**。也就是说：**在补上这一面之前，任何 Python 依赖都进不来** ——
   这不是流程洁癖，是因为引入 AGPL 类依赖的后果（通过 HTTP 提供服务即触发披露义务）不可逆。
3. **不把边界写下来，阶段 B 会各引各的。** 谁先动手谁定标准，
   最终「统一的护栏出口」（`AR-33`）会被一堆第三方框架的调用图切碎，
   而 `AR-33` 唯一的机器判据（门禁结构检查：除出口与接缝外禁止 import 模型客户端）会直接失效。

## 候选

| 候选 | 它擅长什么 | 它的代价 | 什么条件下它最优 |
| --- | --- | --- | --- |
| **A** | **引入完整框架接管护栏出口**（`guardrails-ai` / `NeMo Guardrails`）：① 现成的 validator 生态与 Hub；② 结构化输出（Pydantic 模型直通）；③ 有 `OnFailAction.EXCEPTION` 这类 fail-closed 档位；④ 社区大（7.4k★ / 7.2k★，均 Apache-2.0、均活跃） | 🔴 **形态不匹配**：框架自带 Hub、CLI、Flask 服务端与远程 validator 拉取，而本模块要的是「一个函数 + 启动期断言」；🔴 **`AR-15` 冲突**：`fix` / `reask` 动作就是「修复后放行」；🔴 **`AR-33` 判据失效**：出口变成框架的调用图，门禁结构检查无从判断「有没有绕过护栏」；🔴 **依赖面不可控**：Hub 侧已停止托管远程推理（2026-08 截止），validator 改为逐个 `pip` 装 | 若需求变成「需要几十个现成 validator，自研明显不及」，且愿意放弃 `AR-33` 的结构判据 |
| **B** | **零新增依赖，全部自研**：① 语义 100% 自控（fail-closed 语义可逐行保证）；② 无许可与供应链风险；③ 无版本升级负担 | 🔴 「不引依赖」被当成目标本身 —— 而 `AR-15`/`AR-21` 约束的是**默认行为**，不是**是否引入**；🔴 手写解析器的边界情况是无底洞（`json_repair` 5.1k★ 的覆盖度不是 91 行能追的）；🔴 假数据生成自研几乎必然产出「一眼假」的数据 | 若某能力**没有任何**默认行为同向的实现（见下方空白 C-2 / C-3） |
| **C** | **按能力分层复用**（只复用「默认行为与本项目规则同向」且**不接管处置语义**的库；本项目保留 fail-closed 外壳）：① 复用决定变成一条**可判的判据**（默认行为是否 fail-closed）；② `AR-33` 的结构判据完好（框架不进调用图）；③ 把「该不该引」从口味问题变成证据问题 | 🟡 需要逐项做行为对齐测试（不能只看文档就换）；🟡 依赖面开始增长，供应链与升级成本开始存在 | 在「有成熟实现且其默认行为可对齐」与「必须守住 fail-closed 与唯一出口」之间，这是唯一同时成立的解 |

## 决定

**采纳 C**，并定下两条配套纪律：

### 决定 1 · 复用判据：看默认行为，不看功能表

一项能力**可以**复用开源实现的**充要条件**（三条同时成立）：

1. 该实现存在一个**默认或可配置为 fail-closed 的模式**（出错即抛异常 / 拒绝，**不**补默认值、**不**修复后放行）
   —— 这是 `AR-15` / `AR-21` 的判据；
2. 它**不接管处置语义**（不知道 `Envelope`、不决定「入库与否」、不决定「下发与否」）——
   处置只在本项目的 `aicap/service.py` 里发生（`AR-33`）；
3. 它**不破坏确定性**：凡参与 `AR-30` 那条链路的（内容体、校验和、清单），
   要么本身确定性，要么有可固定的种子（如 `seed()`）。

**不满足第 1 条的，无论多流行都不引**——这是本条的实质：
`pydantic` 默认 lax 强制转换、`guardrails-ai` 默认 `fix`、`json_repair` 默认 repair，
**三者的默认行为都与 `AR-15` 相反**；`json_repair` 之所以入选，只因为它提供 `strict=True`。

### 决定 2 · 前置条件：先把 Python 依赖审计面补上（`TB-16` 的实现缺口）

- `scripts/licensecheck/` 扩到**两类依赖**：Go 模块（既有）+ **Python 运行期依赖**（`analysis/requirements.txt`）；
- Python 侧的**依赖集合**以锁文件为准、**许可声明**以已安装发行版的元数据为准（离线，不需网络）；
- **版本不一致即失败**（锁文件与环境不同步），错误信息指向 `make pyenv` ——
  宁可让门禁红，不可拿 A 版本的元数据审定 B 版本的许可；
- **认不出的许可一律「需人工判定」并让门禁失败**（沿用既有白名单式判定，不改成黑名单式）；
- 开发期依赖（`ruff` / `pytest` / `grpcio-tools`）**不进台账**：与 Go 侧「只审真正参与构建的模块」同口径 ——
  它们不进交付物。

### 决定 3 · 本轮落地范围：只判定，不改 AI 代码

`analysis/llm/` 与 `analysis/aicap/` 的代码**本轮不动**。理由：
`✅ 可复用` 的三项（`json_repair` / `Presidio` / `Faker`）里有两项属于阶段 B（模型后端与 PII 检测），
第三项（`json_repair`）需要先做行为对齐测试（见失效条件 1）。详见调研材料 §3 与 §5。

## 理由

**为什么是 C 而不是 A**：A 的最强优点是「现成的 validator 生态」——这条被正面回应，而不是被绕开：
本轮**不排除复用单个 validator 的实现**（如 Presidio 的识别器作为 `AR-22` 泄露类的识别器），
只排除让框架接管**出口与处置**。分界线是「谁决定内容入不入库」，不是「谁提供检测能力」。
另外 A 会让我们付出一个**不可逆**的代价：`AR-33` 的门禁结构检查是本项目把「无绕过路径」
变成机器判据的唯一手段；让框架进调用图，这个判据就没了，而它换不回来。

**为什么不是 B**：「不引入依赖」本身不是目标。B 的最强优点是「语义 100% 自控、零风险」——
这条同样被正面回应：所以决定 1 把复用的门槛定在**默认行为**上，而不是放宽到「有对应库就引」。
在被这条门槛挡住的地方（`AR-31` 的数据/指令分离、`AR-16` 信封、`AR-18` 长度纪律、`AR-32` 无执行面），
自研确实是唯一选项 —— 调研材料 §4 的空白矩阵记着这一点。

**为什么决定 2 必须和决定 1 捆在一起**：只写「允许引宽松许可的库」而不补审计面，
等于把 `TB-16` 变成一句口号。台账只覆盖一半语言时，「依赖都经过审计」这个说法是错的 ——
而这恰恰是 ADR-0023 未解决 1/2 无法推进的真实原因。

## 后果

**正面**：

- 「该不该复用」有了**可判的判据**（决定 1 三条），不再依赖个人偏好；
- `AR-33` 的机器判据完好：框架不进调用图，「唯一出口」仍可用门禁结构检查证；
- 台账覆盖两种语言 ⇒ `TB-16` 从「Go 侧成立」变成「两侧都成立」，ADR-0023 未解决 1/2 的前置条件解除；
- 三项落点已带许可证据（MIT / MIT / MIT），阶段 B 选型不必再从零查证。

**负面 / 代价**：

- **依赖面开始增长** ⇒ 供应链风险与升级成本从此存在（此前是零）；
- `json_repair` 是**单维护者项目**（bus factor 1）；`Presidio` 的 NER 需要下载模型文件（体积与离线物料成本）；
- Python 侧的许可审计**依赖本地 venv**（`make pyenv`）。这是刻意的取舍：离线、可直接核到元数据；
  代价是门禁多了一个环境前置条件，而它已经被 `pytest` / `pylint` 要求着（不新增）。

**引入的新风险**：

- **环境漂移会让门禁红**。本轮就撞到一次：锁文件 `protobuf==7.36.2` vs 环境 `7.35.1`。
  这是**特性**而非缺陷 —— 但需要在 runbook 里写清「改锁文件后必须重跑 `make pyenv`」。
- **「默认行为可对齐」是文档级判断**，不是实测。故决定 1 的第 1 条必须配行为对齐测试才能落地（失效条件 1）。

**被排除掉的可能性**：

- 让第三方框架接管护栏出口（候选 A）—— 除非失效条件 4 触发；
- 把 `AR-31` 换成「提示注入分类器」—— 分类器给的是概率，`AR-31` 要的是断言，两者不可互换（调研材料 §4 空白 C-2）。

## 失效条件

写成可观测的触发条件：

1. **`json_repair(strict=True)` 的行为对齐测试不通过**（旧提取器与新提取器在同一组样本上结果不一致，
   尤其 markdown 围栏与非 JSON 前置文本）⇒ 该条复用作废，保留自研提取器，本 ADR 的决定 1 需追加一条反例；
2. **任一已引入依赖出现维护停滞（12 个月无提交）或归档** ⇒ 立即重开评估。
   先例：`protectai/llm-guard`（已归档，最后推送 2026-07-08）与 `Azure/PyRIT`（已归档）——
   两者都是最常被二手文章推荐的选型，说明**按热度选型会踩中归档仓库**；
3. **Python 依赖审计面被证实在无 venv 的 CI 环境不可用** ⇒ 决定 2 的「以已安装元数据为准」需要改写
   （备选：在锁文件旁维护一份可核验的许可清单 + 漂移守卫）；
4. **出现必须由框架才能满足的需求**（例如需要几十个现成 validator 且自研明显不及）⇒ 候选 A 重新进入比较，
   此时必须同时给出「`AR-33` 的结构判据如何保住」的答案；
5. **阶段 B 实测发现 `Faker.seed()` 的跨版本稳定性不足**（同种子跨版本产出不同 ⇒ 破 `AR-30`）⇒
   假数据复用作废，改写为「生成一次、把结果当资源入库」。

**复查日期**：2026-12-20（或阶段 B 立项时，以先到者为准）。
