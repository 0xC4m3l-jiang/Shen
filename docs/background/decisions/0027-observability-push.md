# 0027. 观测面推送：核心事件流 + SSE（与策略面 Pull 的边界）

- 状态：✅ **已采纳**（2026-09-21，用户四问四答：Q1-A / Q2-A / Q3-A / Q4-A）
- 日期：2026-09-21
- 影响范围：`api/telemetry/v1`（新增 `WatchEvents` 流）· 核心 `telemetry` 模块（新增有界广播 `Hub`）·
  `control` 服务面（新增流式方法）· 控制台（新增 `GET /api/stream` + 页面改为**增量更新**）·
  契约 [`../spec/console-api.md`](../../spec/console-api.md) §3
- 决策者：用户
- 依据：用户「报告不是轮询刷新，而是监控到了就要通知/主动更新到管控平台」·
  [ADR-0018](0018-policy-plane-pull-model.md)（策略面的 Pull 决策 —— 本文说明**为什么观测面不适用**）·
  `AR-6`（异步上报）· `AR-10`（控制面不参与判定）· `NI-1`（不影响原始业务）· `MD-10`（缓存必须有上限与失效规则）

## 背景

控制台的时效性下限就是它的轮询间隔：页面每 5 秒整块重取一次（**还要有人盯着**）。
而告警的价值随时间衰减 —— 「5 秒后才亮，而且没人看就不会亮」对一个观测面是不够的。

用户的原话是：「**不是轮询刷新，而是监控到了、并且记录了，就要通知或者主动更新到管控平台**」。
即：**事件落库的那一刻**就应当到管控平台，而不是等下一次拉。

### 与前一个决策的关系（必须说清，否则看起来自相矛盾）

[ADR-0018](0018-policy-plane-pull-model.md) 明确**不做** `Watch`，理由写得很清楚：

> `Watch` 的收益是**延迟**，成本是**状态**：长连接、重连、心跳、半开检测、代理/网关对流的支持。
> 而当前策略的变更方式是「改配置文件 + 重启核心」，一个轮询间隔（默认 60s）完全够用。

那说的是**策略面**：策略**变更稀疏**（改配置 + 重启），慢一分钟没有代价。
本文说的是**观测面**：事件**持续**产生、时效**就是**它的价值。**前提完全不同**，因此：

- **策略面仍然 `Pull`**（`policy.Watch` 保持 `Unimplemented`，一字不改）；
- 本文只给**读侧的观测流**加推送。

## 候选

| 候选 | 内容 | 真实优势 | 代价 |
| --- | --- | --- | --- |
| **A** | **核心 gRPC 服务端流 + 控制台 SSE**（采纳） | ① 真推送（记录即到）；② **零新依赖**（gRPC 流已在用的库；SSE 只要标准库 `http.Flusher`）；③ 浏览器原生 `EventSource` 自带重连 | 核心多一类**长连接状态**（订阅者表 + 缓冲）；控制台与页面要改成增量更新 |
| **B** | **高频短轮询**（如 1 秒，带 `since` 游标） | 改动最小（不动 proto、不动核心） | ❌ 本质仍是**拉**（用户已明确否掉）；时效下限 = 间隔；空闲时白跑查询 |
| **C** | WebSocket | 双向 | 🔴 Go 侧要引库（`TB-16` 许可台账要走一遍），而我们只需要**单向推**；握手/心跳/分帧都要自己管 |
| **D** | 核心主动 webhook 控制台 | 直连 | 🔴 **反向依赖**（核心变成要认识控制台）+ 控制台成为核心的失败点；与 `MD-4` 的依赖方向相悖 |

## 决定

**采纳 A**，并定下四条配套纪律。

### 决定 1 · 两段管道，各用各的现成机制

```text
核心 ──gRPC 服务端流 WatchEvents──▶ 控制台 ──SSE GET /api/stream──▶ 浏览器（EventSource）
```

- **核心 → 控制台**：`api/telemetry/v1` 新增 `rpc WatchEvents(WatchEventsRequest) returns (stream WatchEvent)`；
- **控制台 → 浏览器**：`GET /api/stream`（`text/event-stream`），帧形状见契约 §3；
- 控制台**不缓存**、**不改写**：它只把核心的事件（已由 `viewOf` 解成页面视图形状）转成 SSE 帧转发。

### 决定 2 · 三条不可破的纪律

| # | 纪律 | 为什么 | 落地 |
| --- | --- | --- | --- |
| ① | **旁路**：推送在**落库之后**进行，投递失败**不得**影响任何写入路径 | 上报路径是业务链路（`AR-6` / `NI-1`）——「有人在看」不该改变它的成败 | `Collector.ReportBatch` 里 `pub.Publish(written)`，**只推真正写入的**；`Hub.Publish` 不返回错误 |
| ② | **无背压 + 丢包可见**：订阅者跟不上就**丢最旧**并**计数**，丢了多少**随流告知** | 长连接最危险的是「慢消费者拖死核心」；而**不可见**的丢包会让页面把「漏了」误读成「没发生」 | 每订阅者有界 channel（默认 256，上限 4096）；`WatchStatus{dropped, buffer_size, capacity}` 只在**有变化时**发 |
| ③ | **可补漏**：`since` 非空时先补一段历史（有上限）再转流 | 断线期间的事件不能**静默**消失 | `WatchEventsRequest.since` + `catch_up_limit`（默认 500，上限 5000）；**先订阅再补漏**（反了会丢补漏期间的新事件），重叠用 event_id 去重 |

### 决定 3 · 页面：增量更新 + 30 秒对账（**删掉 5 秒整块轮询**）

- **及时性**由事件流负责：新事件立即插入表格、告警立即计数并亮；
- **正确性**由 30 秒整块刷新负责：纠偏本地计数（本地累加久了会漂）；
- 因此原来的「每 5 秒自动刷新」开关与 `setInterval(load, 5000)` **删除** —— 它已被更快的机制取代，
  留着只会让人以为时效还是 5 秒。

### 决定 4 · 不新增依赖、不新增模块

- gRPC 流用已有依赖；SSE 用标准库（`http.Flusher`），页面用原生 `EventSource`；
- 广播逻辑落在**已有的** `telemetry` 模块（它拥有事件管道）与控制台，**不新增模块**（`MD-18` 不触发）。

## 理由

**为什么是 A 而不是 B**：B 的最强优点是「改动最小」——用**决定 3 的删除**回应：
本轮确实改了契约与核心，但换来的是**时效下限从「轮询间隔」变成「无」**（实测 3ms，见下），
并且顺手删掉了页面里那套 5 秒轮询（净代码量没有暴增）。

**为什么是 A 而不是 C/D**：C 要引依赖且我们只需单向；D 会让核心反向依赖控制台。
A 两个方向都用**已有**机制（gRPC 流 / SSE），零新依赖 —— 这是能用现成的就不自造。

**为什么纪律②要「丢包可见」**：无背压是**必然要丢**的，丢包本身可接受；
**不可见**才不可接受 —— 页面上的「事件少了」与「真的没发生事」长得一模一样。

## 后果

**正面**：

- **时效从「≤5 秒 + 人工点击」变成「记录即到」**：实测端到端延迟 **3 ms**（回环，含 gRPC 一次往返）；
- 断线可补漏（实测：带 `since` 连上后补到 3 条历史），不静默丢数据；
- 零新依赖、零新模块；策略面的 `Pull` 决策**不受影响**；
- 顺手删掉页面的 5 秒轮询与开关（见决定 3）。

**负面 / 代价**：

- **核心多了一类进程内状态**：订阅者表 + 每订阅者缓冲。它与 `AR-9`（核心无状态多副本）的关系要写清：
  订阅是**进程内、非请求状态**，副本重启即断，客户端自动重连并补漏 —— **不影响判定与路由**；
- 控制台从「整块重画」改成「增量 + 对账」，页面逻辑变复杂（列定义必须共用一份，否则两条路径会漂 —— 已在代码里用 `eventCells`/`flowCells`/`alertCells` 强制）。
- **慢消费者仍然会丢事件**（这是设计，不是缺陷）—— 代价是页面上要显示「累计丢弃 N 条」。

**引入的新风险**：

- **长连接是新的失败面**：半开连接、网络抖动、反代缓冲。缓解：`since` 补漏 + 状态帧 + 页面显示「已断开（重连中）」；
  SSE 头带 `X-Accel-Buffering: no`（前置反代不得缓冲，否则「实时」会变成批量）。
- **多副本下视图不完整**（见「未解决」1）—— 这是**既有**边界（`ListEvents` 同样如此），本轮把它显式写下来。

**被排除掉的可能性**：把策略面也改成流式（`policy.Watch` 保持未实现）；用 WebSocket；核心 webhook 控制台。

## 失效条件

1. **订阅者数变多（如每个副本一个订阅 + 多个运维页）** ⇒ 核心的 fan-out 成本需要重新评估
   （当前是 `O(订阅者)` 的非阻塞投递；订阅者很多时应改成发布订阅或事件总线）；
2. **需要「事件不丢」**（审计级要求，而不是观测级）⇒ 无背压的设计**不适用**，
   必须改成有持久化与确认语义的消费（那是 `store` 与真实存储的活，见 `NI-13`）；
3. **控制台需要写能力**（确认告警 / 静默 / 改配置）⇒ SSE 是**单向**的，那时要重新比较 B/C
   （并且要先重开 [ADR-0020](0020-console-minimal-static-ui.md)）；
4. **`severity` 档位定下来、告警要做分档推送** ⇒ 需要扩展 `WatchEventsRequest` 的过滤
   （按严重度订阅），本轮只有「按事件类型」过滤。
