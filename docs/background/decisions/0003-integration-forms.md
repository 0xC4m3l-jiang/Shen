# 0003. 接入形态：①③ vs 增加旁路镜像 / Sidecar

- 状态：✅ **已采纳**（2026-09-17）
- 日期：2026-09-17
- 影响范围：`docs/design/integration.md`、接入方指南（`docs/integrate/`，**尚未创建**）、配置生成器（INT-16）、`shen doctor`（INT-17）、`docs/design/constraints.md` 的 NI-3 适用范围
- 决策者：用户

## 背景

`INT-1` / `INT-2`（**旧编号**，映射见 [`../../design/README.md`](../../design/README.md) §4.1.1）已批准两种形态：

```text
① Envoy ext_proc 过滤器   客户已有 Envoy，挂 ext_proc 指向本引擎（旁挂，不碰流量）
③ 反向代理前置            业务 upstream 指向本引擎（流量全过我们）
```

`INT-4`（**旧编号**）明确**未批准**② nginx `auth_request`/`mirror`、④ DNS/CNAME 托管、**⑤ 应用内 middleware/SDK**。

`docs/research/deception-engine-design.md` §3.1 提案五种方式，其中两种是新的：

```text
方式 1  旁路镜像（iptables TEE / eBPF / LB 镜像）   ★ 只观察不响应，"零风险起步"
方式 4  Sidecar / Service Mesh（Istio EnvoyFilter / Linkerd / Cilium）
```

**为什么必须重开**：**旁路镜像不是第三种接入形态，而是影子模式（`NI-6`）的一种实现手段。**

它只观察、不处置，所以它**天然满足** `NI-6` 的「首上必须是影子模式」——
而 `INT-1` / `INT-2`（**旧编号**）形态下，影子模式要在引擎内部实现（决策照算、结果不回写）。
这是一个**实现路径的选择**，不是信任模型的增加。把它当成「第四种形态」会让
`INT-3`（**旧编号**，现为 `INT-5`）（两种形态必须各自独立通过 V-1…V-5）的判据失焦。

**不决定的代价**：接入方指南的选择树（尚未创建）无法确定分支；
配置生成器（`INT-8`）的输出去向无法确定。

## 候选

| 候选 | 它擅长什么 | 它的代价 | 什么条件下它最优 |
| --- | --- | --- | --- |
| **A. 维持 ①③ 两种形态，旁路镜像归为影子模式的实现手段** | 信任模型只有两种，判据清晰；`INT-5` 不变；镜像只用于影子阶段，不引入长期维护面 | 需在 `integration.md` 增加一条「影子模式的许可实现方式」，明确镜像 ≠ 第三种形态 | 采纳路径确实是「先给价值（只观测），再要权限（接触流量）」时 |
| **B. 明确增加旁路镜像为独立形态（与 ①③ 并列）** | 表达直白；`NI-6` 与形态直接对应 | `INT-5` 变成「三种形态各自独立通过 V-1…V-5」——而镜像形态下引擎**不在请求路径上**，V-1/V-2/V-3（杀死、注入延迟、malformed）**无意义**，判据不成立 | 需要把「镜像」作为可长期保留的部署形态（例如客户始终不给流量）时 |
| **C. 增加 Sidecar 为独立形态** | 云原生客户的天然形态（随 Pod 生命周期、K8s 原生高可用） | 本质是 `ext_proc` 的另一种挂载方式（Istio 的 EnvoyFilter 就是 Envoy）——**不是新信任模型**；但会带来第二套配置生成与自检物料 | 主要客户群是 K8s 微服务时 |
| **D. 批准 ⑤ 应用内 SDK** | 能干代理看不懂的业务语义级欺骗 | **直接违反 `INT-7`（禁止要求客户改业务代码）与 `INT-9`（必须是独立服务），并与 `NI-7`（必须独立进程）冲突**。审计偏差 B3 指出「侵入业务」正是本项目要避免的失败模式 | **不适用**（需要先推翻 `INT-7` / `INT-9` / `NI-7`） |

## 决定

**批准四种接入形态，⑤ SDK 不批准。** 详见 [`../../design/integration.md`](../../design/integration.md) §1：

```text
① 旁路镜像（iptables TEE / eBPF / LB 镜像）   ← 在请求路径外，只观察
② DNS / 智能解析引流                          ← 在请求路径上
③ 反向代理前置                                ← 在请求路径上
④ Sidecar / Service Mesh                      ← 在请求路径上
⑤ 应用内 SDK / middleware                     ❌ 不批准
```

**与候选倾向的差异（如实记录）**：本记录的倾向是候选 A（镜像降为影子模式的实现手段，不作为独立形态）。
**用户选择了 B（镜像作为独立形态）**。两者均优于候选 D（SDK）。

**该差异带来的后果已被新规则吸收**：镜像形态下引擎**不在请求路径上**，因此
依赖「在路径上」的 `NI-3`（失败放行）/ `NI-4`（硬超时）/ `NI-10`（熔断）与 `V-1…V-4` **不适用** ——
已升格为 [`../../design/integration.md`](../../design/integration.md) 的 `INT-6`（镜像形态不适用「引擎在请求路径上」的规则） 与 [`../../design/constraints.md`](../../design/constraints.md) 的适用形态列。

## 理由

**对候选 A 最强优点的回应**（信任模型只有两种、判据清晰）：
用户选择独立形态是为了**表达直白**与「与 `NI-6` 影子模式一一对应」。这个收益真实，
而其代价（原 `INT-3` 式「各形态独立通过 V-1…V-5」判据失效）已用 `INT-6` 的适用性标注取代旧判据 —— 代价被消除。

**对候选 C 最强优点的回应**（云原生客户的天然形态）：
Sidecar 已作为**独立形态④**被采纳，形式留待实现期定（Wasm 插件 vs `ext_authz` 旁路服务）。

**对候选 D（SDK）的处理**：
它违反 `INT-7`（须改业务代码）与 `INT-9`（须独立进程）。这是**其他能力做不到时的最后手段**，
但采纳它就要推翻本项目「不影响原始业务」的第一性约束。因此**不批准**。

## 后果

- **正面**：四种形态覆盖传统虚机与云原生两类环境；镜像形态提供「零风险起步」入口（`INT-11` 指出它天然满足影子模式）；SDK 被明确排除，不再反复讨论。
- **负面**：需维护四套配置生成与自检物料（`INT-16` / `INT-17`），接入侧工作量翻倍；镜像形态需要单独标注适用性，文档复杂度上升。
- **引入的新风险**：镜像形态下引擎不在路径上，**既不能处置也不能被故障注入验证**（`V-1…V-4` 无对象）—— 仅靠 `V-5` 与出站审计保障。
- **被排除掉的可能性**：业务语义级欺骗（无需业务内埋点的代理方案看不到业务语义）。该缺口**登记为已知能力边界**，不作为新形态。

## 失效条件

- 当**任一形态无法独立通过 INT-5（各形态独立工作）**时 → 重开。
- 当**镜像形态被证实无法满足任何实质观测需求**（只能看不能算）时 → 重开并考虑降为手段（回到候选 A）。
- 当**客户环境出现四者都覆盖不了的接入口**时 → 评估新增形态或重新考虑 SDK（需先推翻 INT-7 / INT-9）。
