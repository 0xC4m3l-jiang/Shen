# 0009. 策略版本的来源：配置文件显式声明（否决内容推导与启动自增）

- 状态：✅ **已采纳**
- 日期：2026-09-18
- 影响范围：`docs/spec/config.md` §2.7 的 `policy.version`；
  `core/internal/policy/`（`Loader` 与 `Publish`）；
  [`../plans/2026-09-18-policy-2a.md`](../plans/2026-09-18-policy-2a.md)（本轮访谈第 ⑥ 项）
- 决策者：用户
- 依据：`AR-13`（策略下发**必须**版本化、可灰度、可回滚、各层**必须**回执以便版本对账）·
  `ST-8`（策略面**必须**携带版本号与校验和，并支持回滚）

---

## 背景

`policy` 模块要把一份配置文档变成可下发、可回滚、可对账的**版本化**策略。
其中 `version` 这个字段的取值方式有三种可行做法，必须选一个 ——
它决定了「回滚」和「对账」两个动作在运维上长什么样。

约束来自两条已确认规则：

1. `AR-13` 要求**可回滚**且**可对账** —— 版本号必须能表达「谁比谁新」；
2. `store.PolicyStore` 的既有语义（`core/internal/store/memory.go` 注释与实现）已经写死：
   **版本只增**，低于等于当前版本的发布被拒绝；**回滚不是回退版本号，而是发布一个内容为旧版的新版本**。

## 候选

| 候选 | 内容 | 真实优势 |
| --- | --- | --- |
| **A** | **配置文件显式声明** `version: 5`；装载时校验「严格大于台账当前版本」 | 版本是**运维语义**：可编排、可对账、可解释「这一版是谁、什么时候、为什么发的」 |
| **B** | 由**内容推导**（校验和 / 哈希即版本） | 同内容天然同版本，幂等；无需人工维护 |
| **C** | 启动时读台账 `Current()` 然后 **+1** | 无需人工维护；单调性天然满足 |

## 决定

采用 **候选 A**：

1. `version` **必须**由配置文件显式声明，整数且 `≥1`；
2. 装载后写入台账时**必须**严格大于当前版本，否则**必须**启动失败（由 `store.PolicyStore` 侧强制）；
3. **回滚 = 高版本 + 旧内容**，而不是回退版本号。

## 理由

### 1. 候选 B 与「回滚」直接冲突

内容哈希做版本号时，回滚会**撞上旧版本号** —— 而版本次序恰好是对账（`AR-13`）的唯一依据：
分不清「这是第 3 次发布」还是「第 5 次发布回滚到第 3 次的内容」，回执对账就退化成内容比对。
`store` 侧「版本单调递增」的现成语义也会把这次回滚判为非法。

### 2. 候选 C 把版本号与「谁发布了什么」脱钩

启动自增的版本号只反映**进程重启次数**，不反映**策略内容的演进**：
同一份内容重启三次会产生三个版本，台账里出现三条无法解释的记录；
而真正的内容变更（改配置 + 重启）与无变更的重启**无法区分**。
`AR-13` 要求的对账在这种台账上做不出结论。

### 3. 候选 A 让版本号成为可编排的运维对象

灰度放开（`INT-12` 的「逐级推进」）与自动回退（`INT-13`）都需要一个**可被人工写下来、
写进发布记录、在回执里被引用**的标识。显式声明的整数是唯一满足这三点的形态；
校验和（`ST-8` 的另一半）随后跟上，负责「内容是否与声明一致」。

### 4. 代价可控

代价是「人工维护一个递增整数」。它被两条既有事实抵消：

- **本期变更靠「改文件 + 重启核心」生效**（无下发面），一次变更本来就要人写文件；
- 遗忘递增会被**启动失败**挡住（`store` 拒绝非递增版本），不会静默产生歧义版本。

## 后果

| 类型 | 内容 |
| --- | --- |
| ✅ 正面 | 版本号可编排、可对账；回滚语义与 `store` 既有实现一致；遗忘递增被启动失败挡住 |
| ⚠️ 负面 | 人工必须维护递增整数；同一份内容重复发布会产生不同版本（可接受：发布动作本身要留痕） |
| 🔧 需同步 | `docs/spec/config.md` §2.7 · `docs/modules/policy.md` §1 / §6 · [`../plans/2026-09-18-policy-2a.md`](../plans/2026-09-18-policy-2a.md) §3 |

## 失效条件

出现下列任一情形时**必须**重开本记录：

- **策略来源变为控制面（`console`）或 L4 自动写入**：版本号应由写入方分配（数据库序列 / 控制面事务），
  「人工在文件里写」变成瓶颈或冲突源 —— 此时改用「控制面分配 + 文件仅作开发期来源」；
- **配置文件在生产形态下不再是权威来源**（改为 PostgreSQL 台账为源、文件仅供本地开发）：
  候选 A 仍可成立，但「显式声明」的落点要改到台账写入路径，需重开确认；
- **出现多站点共用一份策略、需要版本号按站点分区**：单一递增整数不再够用，需重新设计标识。
