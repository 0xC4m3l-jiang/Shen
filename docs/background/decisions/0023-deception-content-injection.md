# 0023. 欺骗内容注入：离线生成 + 确定性命中 + 强制护栏

- 状态：✅ **已采纳**
- 日期：2026-09-20
- 影响范围：新增 L4 模块 `ai-capability`（第 25 行）；`architecture.md` 新增 `AR-33`；`policy` 的边缘投影（`inject_enabled` / `content_manifest`）；`adapter-proxy` 的改道侧注入；`edge-injection` 的调用方式（不变）；`docs/spec/ai-contract.md`（新）
- 决策者：用户
- 依据：用户「AI 能力服务 + 欺骗内容注入」的需求与 `grill_deck` 访谈结论（2026-09-20，六问全部给出取值）+ `AR-15` / `AR-22` / `AR-30` / `AR-31` / `AR-32` / `INT-8` / `NI-1`

---

## 背景

`docs/modules/README.md` §0.4 与 `docs/kb/capabilities.md` 记着同一处缺口：**「处置内容的边缘通路未接通」**——
`decoy` / `responder` 在核心内已实现，改道后端表与**静态**注入规则（`injects` → `inject_rules`）也已能经策略面下发，
但**「改道侧的响应正文由谁产出」**一直没有定义（`architecture.md` §10.2 缺口 13 的「仍未定」部分）。

同时，`responder` 的 `ContentStore`（键 = 一致性键）已经存在，注释写着「内容由 L4 离线预生成落库，热路径只读」——
即设计早已假定「生成在离线侧、消费在热路径」，缺的只是**生成侧的服务形态**与其**下发通路**。

本轮要回答的是三件事：

1. **生成放在哪** —— 每个消费方各自调模型，还是收敛到一个可开关的出口？
2. **生成的内容怎么到边缘** —— 走策略面（版本 + 校验和）还是各自配置？
3. **怎么保证生成的内容不出事** —— 生成内容会出现在对手的屏幕上（`OH-1` 的判据），
   而 LLM 输出的可信度问题已经是既定的（`AR-15` / `AR-22` / `AR-31` / `AR-32`）。

## 候选

| 候选 | 内容 | 真实优势 | 代价 |
| --- | --- | --- | --- |
| **A** | **各消费方各自调模型**（`responder` / `decoy` / 未来沙箱各自接一套） | 贴合各自需求；不引入共享服务 | 🔴 护栏会被复制 N 份 ⇒ 总有一条路径忘了校验（`AR-15` / `AR-22` 无法用结构检查保证）；🔴 模型配额与提示词版本无法统一管理；🔴 与 `AR-32`（分析侧无执行面）的边界每处都要重证 |
| **B** | **集中式模型服务**（独立进程 / 网关，热路径与离线都调它） | 配额与审计统一；多消费方共享 | 🔴 新增一个**运行时依赖**（多一个进程、多一处失败点）；🔴 本项目的消费方**全在离线/近线**（内容预生成、诱饵再生成），热路径**永不调模型** ⇒ 为不存在的在线需求付进程成本（`NI-7` 的精神） |
| **C** | **库形态的共享出口**（一个 Python 包，唯一入口 `generate()`，护栏在内部强制；阶段 A 用确定性模板生成器，模型后端留接缝） | 无常驻进程 ⇒ 不新增运行时依赖；护栏**只有一处** ⇒ 可用**结构检查**（`make archcheck`）+ 单测把「无绕过路径」变成机器判据；离线生成 + 文件产物 ⇒ 与 `ContentStore` 的既有语义一致 | 🟡 每个消费方各自跑（多进程重复加载），但生成是离线批量任务，代价可接受 |
| **D** | **热路径实时生成**（请求时调模型） | 变体最多、最难指纹 | ❌ **违反 `AR-30`**（响应路径禁止非确定性：随机数 / 当前时间 / 采样）；❌ 违反 `AR-29`（5 ms 预算）；❌ `AR-32` 的精神（分析结论禁止直接回写响应） |

## 决定

**采纳 C**，并定下四条配套纪律：

### 决定 1 · 形态：库形态的共享出口（`ai-capability`，第 25 个模块）

- 唯一出口：`generate(TaskSpec) → Envelope{accepted, data}`（信封沿用 `AR-16`）；
- **强制护栏**（不依赖调用方自觉）：
  - 结构闸门：任务注册表**必须**为每个 `kind` 声明 `schema` + `guardrail_profile` + `limits`，
    缺声明 ⇒ **启动期断言失败**（fail-closed）；未登记的 `kind` 一律拒绝；
  - 前置闸门：提示词**必须**是资源文件的三段式（指令区 / 画像区 / **不可信数据区** `AR-31`），
    模板缺失或占位符不齐 ⇒ 启动期断言失败（`AR-24`）；
  - 后置闸门：独立代码层校验 schema（`AR-15`）→ 黑名单三类（`AR-22`）→ 长度（`AR-23`）→ 风格一致性，
    **任一不过即拒绝**，内容**不入库**、**不下发**。
- **可验证的「无绕过路径」**：`AR-33` 的判据是**门禁结构检查**
  （`analysis/` 下除 `aicap/service.py` · `aicap/model.py` · `llm/` 自身与测试外，**禁止** import 模型客户端）+ 单测。

### 决定 2 · 内容一致性：`(site, resource, variant_id, content_version)`，会话只参与选变体

- `variant = fnv1a(session_id) mod N`（N 默认 8）——**确定性**，同会话恒同槽位（与 [ADR-0016](0016-decoy-polymorphism.md) 的划界一致：
  **多态在会话边界选择、会话内冻结**）；
- 适配器侧**会话钉定**（session → `(variant_id, content_version)`，TTL = 判定缓存窗）：
  钉定命中即复用；轮换（清单 `version` 递增）后**新会话**取新内容、**老会话**沿用槽位；
- **响应路径永不调模型**（`AR-30` 字节一致 / `AR-29` 5 ms / `AR-32`）。

### 决定 3 · 内容通路：离线生成 → 过护栏 → 内容库 → 清单经策略面下发（阶段 A 直接携带内容体）

- 生成侧（离线）：`generate()` → 护栏 → `accepted` ⇒ 写内容库；产出**内容清单**文件；
- 核心侧：启动时装载清单（校验和逐条验证，不符即丢该条 + warn），投影进策略载荷（`inject_enabled` + `content_manifest`）；
- 边缘侧：适配器按 `(resource, variant)` **确定性命中** → 验证校验和 → 构造 per-request 规则 → `edge/injection` 改写
  **改道侧**响应（`INT-8`：业务侧零改写）；
- 阶段 A 的清单**直接携带内容体**（单条上限 64 KiB，超限该条不入清单 + warn）；**阶段 B** 内容变大时再引入分片拉取接口。

### 决定 4 · 开关三层，默认全关

| 层 | 键 | 关闭后 | 生效 |
| --- | --- | --- | --- |
| 能力级 | `ai.enabled` + `ai.kinds` | 不生成、不新增内容（存量仍在库） | 重启/重载 |
| 下发级 | `inject_enabled`（策略载荷） | 适配器停止注入（`inject=disabled`），判定与幻境转发照常 | 下一次 `Pull`（`ADR-0018`） |
| 兜底级 | `SHEN_PROXY_INJECT_CONTENT`（默认 `false`） | 同上一行（策略面不可达时的本地急停） | 适配器重启 |

**关闭 ≠ 回退改道**：只影响「我们改写多少」，幻境后端与判定链完全不变（`NI-1` 优先）。

## 后果

**正面**：

- 护栏**只有一处**，且「无绕过路径」是**机器判据**（门禁 + 单测），不是评审承诺；
- 热路径零模型调用 ⇒ `AR-30`（字节一致）与 `AR-29`（5 ms）**构造性成立**，不靠实测运气；
- 默认全关 ⇒ 本轮交付对既有部署**零行为变化**（默认与今天逐字节一致，验收判据 ①）；
- 生成侧是独立离线任务 ⇒ 模型选择（本地/自托管/外部）不进入运行时的可用性约束；
- 为阶段 C 的第二个消费方（动态沙箱生成规格）留了同一出口，不需再定一次形态。

**负面 / 代价**：

- **内容体会随策略载荷下发** ⇒ 载荷体积与内容量成正比（阶段 A 用 64 KiB/条 + 只带命中资源来缓解，阶段 B 必须做分片）；
- **变体数 N 与轮换节奏成为新的指纹面**（N 太小、措辞规律强都能被识别）——阶段 A 的模板生成器**只能证明通路**，
  真实多样性要等阶段 B 接模型；
- 核心**只在启动时装载清单** ⇒ 「秒级关闭」在适配器侧成立（下一次 `Pull`），核心侧改开关仍需重启
  （配置装载时机见 [`../../spec/config.md`](../../spec/config.md) §1；这是**已知边界**，不是新引入的缺口）；
- 新增一种「内容」概念（清单条目）增加 `policy` 的边缘投影面，需要 `spec/` 三处契约同步。

## 未解决

| # | 未决 | 阻塞什么 | 去向 |
| --- | --- | --- | --- |
| 1 | **模型后端与结构化输出框架**（Outlines / Instructor 等） | 阶段 B 的生成质量 | 阶段 B 单独评估（含许可证台账 `TB-16`） |
| 2 | **PII / 泄露检测**（Presidio 类） | `AR-22` 的泄露类覆盖度（当前只有正则 + 启动期注入的真实标识） | 阶段 B；先看许可证与是否可离线 |
| 3 | **风格画像的来源**（真实站点采样 → 去敏 → 入库） | 生成内容的「像不像」 | 阶段 B；与 [`../notes/threat-model.md`](../notes/threat-model.md) 的识破路径一起做 |
| 4 | **轮换与识破信号的接线**（`strategy` → 清单版本递增） | 内容被识破后的自愈 | 阶段 B；`strategy` 已产出识破信号，缺「谁消费它把清单版本 +1」 |
| 5 | **清单纯量上限与分片拉取接口** | 内容规模 | 阶段 B（阶段 A 的上限是 64 KiB/条 + 1 MiB/清单） |
| 6 | **核心侧内容库的真实后端**（`store.ContentStore` 换 PostgreSQL/Redis） | 重启不丢内容 | 与 `store` 的真实驱动一起做 |

### 失效条件（什么情况下应当重开）

1. **阶段 B 实测发现生成内容的多样性不够**（跨会话被指纹识别 ⇒ 多态失效）⇒ 需要重新评估「N 个静态变体」是否够用，
   可能要引入按时间窗的确定性生成（需保住热路径的**会话钉定**，而非生成期可复现 —— 见 ADR-0026 决定 2）；
2. **清单体积成为实际瓶颈**（单站点资源数 × N × 内容体 > 载荷承受力）⇒ 必须提前引入分片拉取，
   本文的「决定 3」需要改写；
3. **出现第二个**需要**在线**（请求路径内）生成的消费方 ⇒ 候选 B（集中式服务）重新进入比较；
4. **模型后端必须出网** ⇒ 需单独 ADR（观测数据外发的风险与合规不在本文范围内）。

## 补充

- 阶段 A 的交付边界：**通路 + 开关 + 强制护栏**；模型后端、风格画像、轮换接线、分片拉取**都不做**（阶段 B/C）。
- 阶段 A 的生成器是**确定性模板生成器**：它同时承担两个角色 —— 证明通路（可端到端验收）与
  保证 `AR-30`（无随机、无时间、无采样）。它**不是**最终的生成质量方案。

## 修正（2026-09-21）

上文「保证 `AR-30`」这句话**当时说得不准**：`AR-30` 的原文管的是**响应路径**
（「禁止在响应路径上引入非确定性」），它**不要求**生成期可复现。
「阶段 A 生成器确定性」是**阶段 A 的工程性质**（让通路可回归、清单可复现），不是规则要求。

- 真实模型实测：`temperature=0` 也**不可复现**（3 次 3 个 sha256），见
  [`../research/ai-live-probe/README.md`](../research/ai-live-probe/README.md) §1–§2；
- 热路径的字节一致改由三条保证：产物**冻结进清单** + `content_id` 由**内容体**算出 + **会话钉定**；
- 完整论证与失效条件见 [ADR-0026](0026-cloud-model-backend.md) 决定 2。
