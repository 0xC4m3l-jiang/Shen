## 背景

[ADR-0023](0023-deception-content-injection.md) 决定 1 承诺过：**「为阶段 C 的第二个消费方（动态沙箱生成规格）留了同一出口，不需再定一次形态。」**

**这个承诺当时只对了一半。** 注册表（`tasks/_registry.py`）在形式上是可插拔的 —— 加一个 `kind` 确实只是加一条登记。
但**出口本身绑死在「内容」上**，三处硬编码：

1. `service.generate()` 内部直接 `store.put(content)` —— 它认识 `ContentStore`；
2. `Task.build` 的返回类型被写成 `ContentObject` —— 内核知道产物的具体形状；
3. `guardrail/inspect.py` 的风格与黑名单检查写死读 `checked["body"]` —— 它知道内容任务的字段名。

后果：第二个消费方来了只有两条路 —— 要么改内核（于是内核每接一个消费方就被改一次，最终变成 `if kind == ...` 的分支堆），
要么自己复制一份护栏（**这正是 `AR-33` 要防的「绕过路径」**）。

用户已明确：**L4 的 AI 分析与后续的动态沙箱都要用这个能力**。所以现在必须把内核与消费方切开。

不决定的代价：每加一个消费方，`AR-33` 的「唯一出口」就从「一个函数」退化成「一份约定」，而
它的机器判据（`make archcheck` 的结构检查）只能证明「没人 import 模型客户端」，证明不了「没人复制护栏」。

## 候选

| 候选 | 它擅长什么 | 它的代价 | 什么条件下它最优 |
| --- | --- | --- | --- |
| **A** | **保持现状，第二个消费方各自实现**（`kind` 概念只服务内容）：① 每个消费方贴合自己需求，改动局部；② 不动既有代码，零回归风险 | 🔴 护栏被复制 N 份 ⇒ **总有一条路径忘了校验**（`AR-15`/`AR-22` 无法用结构检查保证）；🔴 模型配额、提示词版本、`Envelope` 语义各说各话；🔴 `AR-32`（无执行面）的边界每处都要重新论证 | 只有一个消费方，且**永远不会**有第二个 |
| **B** | **把出口做成服务**（进程边界 + gRPC），任何语言在线调用：① 真正的语言无关；② 配额与审计天然集中；③ 未来沙箱（大概率 Rust）可直接调 | 🔴 新增常驻进程与失败点（`NI-7` 的精神：不为不存在的在线需求付进程成本）；🔴 本项目的生成**全在离线/近线**（热路径永不调模型，`AR-30`/`AR-29`）；🔴 在线调用会诱导「请求时生成」，直接撞 `AR-30` | 出现**必须在请求路径内**生成的消费方 |
| **C** | **内核任务无关化 + 消费方登记 + 产物交给 `Sink`**（库形态不变；「独立」由门禁检查保证）：① 接第二个消费方 = 加一条登记，内核**一行不改**；② 护栏只有一处，且唯一出口仍是机器判据；③ 离线产物路径不变（`AR-30` 的字节一致构造性成立）；④ 不新增进程、不新增依赖 | 🟡 `Sink`/`Artifact` 两个 Protocol 是**为可预见的第二个实现**而抽的（今天只有一个实现 —— 这是最小实现纪律的**有意例外**，理由见下）；🟡 跨语言仍要经产物文件，不能在线调用 | 消费方在离线/近线，且护栏必须只有一处 |

## 决定

**采纳 C**，并定下四条配套纪律：

### 决定 1 · 内核与插件的分界：内核**不认识**任何具体任务

内核（`service.py` / `model.py` / `tasks/_registry.py` / `guardrail/`）只做五件事：
**取任务 → 渲染前置提示词 → 生成 → 后置四关 → 交 sink**。
它**不允许**出现任何具体任务的字段名、产物类型或存储类型。

判定「是不是内核」的实用标准：**把 `kind=content` 整块删掉，内核应当仍能通过启动期断言**（只剩空注册表会失败，那正是它该失败的地方）。

### 决定 2 · 产物出口是 `Sink`，不是「内容库」

- `Artifact`（Protocol）：`to_wire() -> dict`；
- `Sink`（Protocol）：`put(artifact) -> object`；
- `generate(spec, sink=…)` 的 `sink` 由**调用方**给；内核不知道它是不是内容库。

**为什么在只有一个实现时就抽接口**（对最小实现纪律的例外，必须写清理由）：
`ContentStore` 已经是第一个实现，而第二个实现**已被 ADR-0023 与用户明确预告**。
不抽接口的后果不是「少写两个 Protocol」，而是**内核继续认识 `ContentStore`** —— 那正是本轮要消除的耦合。
两个 Protocol 共 6 行；用它们换「接第二个消费方时内核零改动」是划得来的。

### 决定 3 · 声明即纪律：受检字段与上限**必须**真的生效

| 声明 | 今天的实际行为 | 本轮之后 |
| --- | --- | --- |
| `GuardrailProfile` 没有「受检字段」的概念，代码写死 `checked["body"]` | 非内容任务接入时会静默跳过黑名单与风格检查 | **新增必填** `checked_fields`；声明的字段**不在输出里或不是字符串 ⇒ 拒绝** |
| `TaskLimits.max_output` | **声明了却从不生效**（真上限来自 `PURPOSE_LIMITS[purpose]`） | 有效上限 = `min(用途上限, 任务上限)` |

`max_output` 那条是**已经存在的缺陷**（本轮顺带修）：一个声明了却不生效的上限比没有上限更坏 ——
它看起来像保护，评审时会被人当作「已经限住了」。

### 决定 4 · ✅ **已确认（2026-09-20）**：`AR-33` 的措辞放宽为「任何生成」

**原状**：`design/architecture.md` 的 `AR-33` 写的是「**欺骗内容生成**必须经 `ai-capability` 的唯一出口」。
**但**门禁的结构检查（`scripts/archcheck/main.go::checkGuardrailIsSoleExit`）是**全局的**：
`analysis/` 下除出口、接缝、`llm/` 自身与测试外，一律禁止 import 模型客户端。

于是出现一个缺口：`intent` / `chain` / `strategy` 今天不调模型（实测：三个包零 client 调用），
可一旦在阶段 3 接上模型，**门禁会拦它们**，但 `AR-33` 的**文字**并没有说它们必须走出口 ——
读者会以为「想接模型就接，只要别 import 客户端就行」。

**决定**：把 `AR-33` 的适用范围从「欺骗内容生成」改为「**任何** LLM 生成」——
**凡是要调模型的生成，都必须经本出口并过护栏**；同时把「未经护栏校验的**内容**禁止入库 / 下发」
泛化为「未经护栏校验的**产物**禁止交付给任何消费方（入库 / 下发 / 上报）」。

**已落地**（2026-09-20，用户确认后）：

| --- | --- |

## 理由

**为什么是 C 而不是 A**：A 的最强优点是「改动局部、零回归风险」——这条用**实现方式**回应了：
本轮对 `kind=content` **零行为变化**（同一组输入逐字节同产物，端到端 17/17 通过）。
也就是说 A 的好处被保住了，而它防止不了的坏处（护栏被复制）被消除了。

**为什么是 C 而不是 B**：B 的最强优点是「真正的语言无关」。这条被**部分**回应：
产物本身是语言无关的（跨语言经 `spec/ai-contract.md` 定义的清单文件，本项目的既有通路），
所以「沙箱（Rust）用得上」这一点**不需要**额外进程就成立。
B 真正多提供的只有**在线调用**，而在线生成会撞 `AR-30`（响应路径禁止非确定性）与 `AR-29`（5ms 预算）。

**为什么决定 3 是决定 1 的前提**：只把内核「看起来」通用化（换掉类型名）而不把**受检字段与上限声明化**，
第二个消费方接入后会发现：黑名单与风格检查**根本没作用在它的字段上**，而且**没有任何报错**。
那不是解耦，那是把 fail-open 藏到第二个消费方里。

## 后果

**正面**：

- 接一个新消费方 = 加 `produce`/`build` + 一条登记；内核零改动（这是可验证的：新单测里的假 kind 走完整内核）；
- 「解耦 / 独立」从承诺变成**门禁判据**（`MD-4`：`aicap` 的仓内依赖白名单 + `llm` 禁止反向依赖）；
- 修掉两处 fail-open（受检字段静默跳过、`max_output` 声明不生效）；
- 不新增进程、不新增依赖、不改 `design/`，`kind=content` 零行为变化。

**负面 / 代价**：

- **多两个 Protocol 与一个内核函数**（`run_task`）—— 在只有一个消费方的今天，这是**预置**。
  已用决定 2 的「例外理由」显式记录；若第二个消费方**一年内都不出现**，这两个 Protocol 应被视为可回收；
- `GuardrailProfile` 新增**必填**字段，是一处破坏性变更：任何既有的构造点都会立刻失败（这是刻意的 fail-closed）；
- `generate(store=…)` 改名为 `generate(sink=…)`：仓内 4 处调用点全部要改（无兼容别名，不预置兼容层）。

**引入的新风险**：

- 内核「不认识内容」之后，**跨模块的类型检查变弱**（`build` 的返回类型是 `Artifact` 而不是 `ContentObject`）。
  补偿：`kind=content` 的产物类型仍由 `tasks/content.py` 自己把住，且清单的字节由 `spec/ai-contract.md` 定义 + `make ai-check` 端到端守；
- `Sink` 是 Protocol，**运行期不做类型检查** —— 传错对象要到 `put()` 调用时才炸。补偿：`generate()` 的签名类型标注 + 单测覆盖。

**被排除掉的可能性**：

- 让每个消费方自己实现护栏（候选 A）—— 除非失效条件 1 触发；
- 把出口做成服务（候选 B）—— 除非失效条件 2 触发；
- 插件自动发现（entry-point / 目录扫描）：**本轮明确不做** —— 一个消费方时加发现机制就是预置抽象。

## 失效条件

写成可观测的触发条件：

1. **第二个消费方在 2026-12-20 之前仍未出现** ⇒ `Sink` / `Artifact` / `run_task` 三个预置缝隙应被重新审视，
   可能回退为「内核只服务内容」（候选 A）——**但仅限内核形态**：护栏仍只许一处、仍禁止绕过路径（`AR-33`）。
   ⚠️ **不再包括「把 `AR-33` 的措辞收回欺骗内容」**：口径放宽已于 2026-09-20 经用户确认成为规则，
   它的理由是「规则文字必须与全局门禁一致」，**不依赖**第二个消费方是否出现；
2. **出现必须在请求路径内生成的消费方**（不能等离线产物）⇒ 候选 B（进程边界）重新进入比较，
   且必须先回答「它怎么不违反 `AR-30`」；
3. **消费方数量 ≥ 3 且登记方式开始打架**（例如需要按消费方隔离配额、审计或开关）⇒ 引入注册机制（entry-point / 声明式清单）才有意义；
4. **出现跨语言的**产物校验需求（沙箱侧要用 Rust 校验 Python 写的清单）⇒ 需要评估把内部 `Schema` 换成
   [JSON Schema](https://json-schema.org/) 这类**跨语言标准**（本轮未做）；
5. **`GuardrailProfile.checked_fields` 在实践中被多数任务填成同一个字段名** ⇒ 说明「受检字段」本就该是固定约定而不是声明，应简化回固定字段。

**复查日期**：2026-12-20（或第二个消费方立项时，以先到者为准）。
