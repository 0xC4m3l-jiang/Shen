# 0012. 会话级判别的落点：会话特征注入（`judge` 保持纯函数）

- 状态：✅ **已采纳**
- 日期：2026-09-18
- 影响范围：`judge` 的输入契约（消费会话特征）；`session` 增加「会话状态」子能力；`store.SessionStore` 的消费
- 决策者：用户
- 依据：用户「核心是欺骗引擎的实现」+ 综述（[`../research/ai-agent-deception-defense-survey.md`](../research/ai-agent-deception-defense-survey.md) §8.1）+ 参考实现逆向 §3.1.1

---

## 背景

两个已确认的事实互相拉扯：

1. **单事件判别必然失效** —— 综述 `2606.20746`（代理侧时序累加器）与参考实现一致：判别**必须会话级有状态**
   （它用「会话 + IP 双轨 300s 滑窗 + 挑战逃逸累计」）。
2. **路由必须首跳确定** —— `D0` 推论 2（[`../notes/implementation-discussion.md`](../notes/implementation-discussion.md) §1）：
   「首跳决策 = 该会话终局」，判错只能靠**加重处置**补救，不能改道。

同时本项目有两条硬约束：`AR-9`（核心无状态多副本）与 `MD-6`（**禁止依赖系统时钟做判定**，时间必须由调用方注入）。
`judge` 当前是**纯函数**（`Observation → Verdict`），正是这两条约束的实现。

**问题**：会话级累积状态（计数、时序）放在哪里，才不破坏「纯函数 + 可回放」？

## 候选

| 候选 | 内容 | 真实优势 | 代价 |
| --- | --- | --- | --- |
| **A** | `judge` 自己持有会话状态（内部滑窗） | 调用方无感 | 🔴 破坏纯函数与可回放（同输入不同输出）；违反 `AR-9`（进程内可变状态）；时钟进入判定（违反 `MD-6`） |
| **B** | **`session` 计算会话特征，作为输入注入 `judge`** | `judge` 仍是纯函数（特征随输入进来）；状态外置到 `store`；可回放（特征可存进证据） | 需要一次会话状态读（延迟）；`Observation` 需扩展 |
| **C** | 独立的「会话判别」模块，与 `judge` 并列 | 关注点分离彻底 | 与 `AR-2`（判定一处）冲突：判定逻辑被拆成两处 |

## 决定

**采纳 B**：

1. **`judge` 保持纯函数** —— 它不持有任何状态，不读时钟；会话级信息**随 `Observation` 进来**；
2. **`session` 提供会话特征** —— 新增子能力「会话状态」：近 N 秒事件数（会话轨 + IP 轨）、挑战逃逸次数等，经接口从 `store.SessionStore` 读；
3. **服务面（`control`）负责编排** —— 提取身份 → 读会话特征 → 注入判定请求；时钟由服务面注入（`MD-6`）；
4. **会话累积只影响 `severity`，不影响路由** —— 路由由首跳判定决定（`D0` 推论 2）；会话级证据用于**加重处置**。

### 会话特征（`contract.SessionFeatures`）

| 特征 | 含义 | 用途 |
| --- | --- | --- |
| `events_60s` | 会话轨近 60s 事件数 | 速度信号（`high_request_velocity`） |
| `events_60s_ip` | IP 轨近 60s 事件数 | 抗 Cookie 轮换（无 Cookie 客户端） |
| `challenges_300s` | 近 300s 被挑战次数 | 挑战逃逸（`challenge_evasion`） |
| `first_seen` / `last_seen` | 会话起止 | 冷启动/返回客判据 |

> 双轨取 max，是参考实现验证过的正确设计：无 Cookie 客户端每请求获得新 `session_id`，
> 单靠会话轨会退化；IP 轨兜底。

## 理由

### 1. 保住「可回放」比省一次读更重要

判定出问题时，我们需要能回答「当时为什么这么判」。纯函数 + 特征入证据，使任何一次判定都能**离线重放**。
候选 A 会用一次状态读换掉这个能力，代价不成比例。

### 2. `AR-9` / `MD-6` 是硬约束，不是偏好

核心必须无状态多副本 —— 进程内滑窗会让多副本判定不一致（同一会话打到不同副本得到不同结论）。
把状态外置到 `store`（Redis TTL）后，多副本天然一致。

### 3. 路由与加重分离，是 `D0` 的直接推论

路由必须首跳确定（否则「同资源两个答案」立刻被识破）；
而「首跳看不出、后面越看越像」的慢热型 Agent，只能靠 `severity` 的**不可见加重**补救。
会话特征正好服务后者。

## 后果

| 类型 | 内容 |
| --- | --- |
| ✅ 正面 | `judge` 保持纯函数与可回放；多副本一致（状态外置）；路由与加重职责清晰 |
| ⚠️ 负面 | 每次判定多一次会话状态读（延迟预算内）；`Observation` 契约扩展；会话状态存储的可用性成为依赖（不可用时应回落，见 `NI-10`） |
| 🔧 需同步 | `judge.md` 输入契约；`session.md` 新增「会话状态」；`contract` 加 `SessionFeatures`；`store.SessionStore` 增加滑窗读写 |

## 失效条件

出现下列任一情形时**必须**重开本记录：

- **会话状态读的延迟超出 `AR-29` 的 P99 预算**，且无法用本地缓存缓解 → 重开，评估本地滑窗 + 最终一致；
- **`store` 不可用时的降级被证明会破坏判定稳定性**（特征时有时无导致判定抖动）→ 重开，评估特征缺失时的显式语义；
- **纯函数判定被证明无法表达关键判别**（需要跨请求的复杂状态机）→ 重开，评估候选 C。

## 未解决

- **会话状态存储**：本地 LRU vs Redis —— 与 [ADR-0012 之前的 `D6`](../notes/implementation-discussion.md) 同一未决项，本决策倾向 Redis（多副本一致），实现期实测确认；
- **特征窗口的具体时长**（60s / 300s）—— 属实测问题，需与判定阈值一起校准。
