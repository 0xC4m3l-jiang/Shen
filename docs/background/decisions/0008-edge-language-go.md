## 背景

[`language.md`](../../design/language.md) §1 原定：

> | **L1 边缘欺骗层** | 投毒 · 假路径 · 引流**执行** | **Lua (OpenResty) 或 Rust (Pingora)** | 七层代理内嵌，毫秒级，策略热更新；**判定逻辑不在此层** |

用户要求推进四个接入形态（① 旁路镜像 · ② DNS 引流 · ③ 反向代理 · ④ Sidecar），
并提出两条硬要求：

1. **不使用 Lua**；
2. **用最少的代码**，且**前置代理 + Pod 两种形态都要好容器化扩展**。

这两条直接冲撞现行的 L1 语言选型，因此必须按 `TB-4` 走决策流程，而不是直接改文档。

推进过程中还暴露一个事实：**③ 反向代理与 ④ Sidecar 的代码完全相同** ——
都是「监听端口 → 收请求 → 调核心判定 → 按结果转发」。差别只有两点，
都在配置里而不在代码里：

| | ③ 反向代理前置 | ④ Sidecar |
| --- | --- | --- |
| 部署位置 | 独立节点 / 独立 Pod | 业务 Pod 内 |
| upstream 指向 | 业务真实地址 | `127.0.0.1:<业务端口>` |

## 候选

| 候选 | 内容 | 真实优势 |
| --- | --- | --- |
| **A** | **OpenResty + Lua**（现行基线） | 能**内嵌进客户已有的 nginx**，接入摩擦最低 |
| **B** | **Go 反向代理**（`net/http/httputil.ReverseProxy`，标准库） | 静态单文件、与核心同语言、复用同一套门禁 |
| **C** | **Rust + Pingora** | 性能上限最高，内存安全 |
| **D** | **Envoy + Go `ext_proc` 服务** | 复用 Envoy 的 L0 能力；流式处理原生 |

候选 D 的可行性已由 `E1` spike 实测（`ext_proc` 的六阶段状态机实现正确、空载 P99 116 µs）。
它被否决的理由见下方「对候选 D 的回应」。

## 决定

采用 **候选 B**：

1. **L1 用 Go**；
2. **移除 Lua** —— 实现语言由 5 种（Lua / Rust / Go / Python / TypeScript）**降为 4 种**；
3. **③ 与 ④ 合并为一个模块 `adapter-proxy`**：一个二进制、两种部署形态（前置 / 边车），
   配置各一份。§1.1 保留第 11 行并改名，第 12 行登记为「已合并入第 11 行」（依据 `D-6`：ID 不得重新编号、不得复用）。

## 理由

### 1. 候选 B 用一份代码覆盖两种形态，A 的部署物却要两套

③ 与 ④ 的差异全在配置里（见上表）。Go 方案下它们是**同一个二进制 + 两份配置**；
Lua 方案下虽然也是同一份 Lua，但**部署物与运维技能是两套**：
前置形态要客户运维一套 OpenResty，边车形态要往每个 Pod 里塞一个 OpenResty 镜像，
且两种形态的 nginx 主配置、reload 方式、日志路径都不同。用户明确要求"方便后续容器化扩展"。

### 2. 容器化成本差一个数量级

Go 静态二进制可打成 `scratch` / `distroless` 单文件镜像，无运行时依赖。
OpenResty 镜像里是 nginx + LuaJIT + 一批 C 模块 + 主配置，
边车形态下每个业务 Pod 都要承担这份体积与攻击面 —— 而它恰恰部署在最敏感的位置。

### 3. Lua 侧没有任何静态检查能接进现有门禁

`TB-15` 要求 CI 必须通过**格式化检查 + 静态检查 + 单测 + 数据竞争检测**。
这套门禁（`make gate`：`gofmt` · `go vet` · `staticcheck` · `errcheck` · `archcheck` · `test -race`）
全部建立在 Go 工具链上。**现行基线对 Lua 侧没有任何静态检查** ——
Lua 一旦进入代码库，就等于在一片没有门禁的区域内写代码，而这块区域在请求路径上。

### 4. Lua 侧调核心要引入非官方 gRPC 依赖

适配器必须调用核心的判定面（`api/judge/v1`）。Go 侧直接用生成的 stub，零额外依赖。
LuaJIT 侧要用 gRPC 就得引入 `lua-resty-grpc` 一类**非官方**库 ——
那既是 `TB-16`（许可与漏洞审计）的风险点，也是长期无维护的风险点。

### 5. 与核心共享同一套契约与构建

`ST-3` 已由 Go 的 `internal/` 规则在编译期强制「适配器只能经 `api/` 调核心」。
适配器与核心同语言后，这条规则的强制方式、proto 生成流程（`make generate`）、
版本演进方式（`TB-26`：`api/<平面>/v1/`）全部共用一套，不需要两套心智模型。

### 6. 每多一门语言都是长期负债

`TB-21` 允许 ≤ 5 种，那是**上限不是目标**。Lua 在本项目中**只被 L1 使用**：
移除它等于整层语言的构建、测试、依赖审计与运维技能全部消失。

## 对「GC 抖动不适合毫秒级延迟」这条既有反对意见的回应

`language.md` §2 原来把 Go 列为 L1 的**被否决**候选，理由是：

> **Go** | 可用，但 GC 抖动对毫秒级延迟敏感场景不友好

这是现行文档里反对本决策的最强论据，必须正面回应：

1. **预算量级不符。** `AR-29` 给业务路径的额外延迟预算是 **P99 ≤ 5 ms**，不是「亚毫秒」。
   `E1` 实测核心侧 ext_proc 空载往返 P99 为 **116 µs**，即预算的 2.3%。
   在毫秒级预算下，GC 停顿不是决定项。
2. **L1 的堆压力天然小。** 会放大 GC 抖动的是「大堆 + 高分配率」，
   而 L1 的设计约束恰好是**不持有跨请求业务状态**（`structure.md` §4）。
   每请求分配的是请求头映射与少量缓冲区，短生命周期对象正是 Go GC 最擅长的形状。
3. **真正的抖动源不是 GC，而是跨进程调用。** L1 每请求要做一次 gRPC 调用（`S1` 接缝），
   网络与调度抖动远大于 GC 停顿。候选 A（Lua）同样要越过这个跳数 ——
   它省掉的是进程内开销，不是这个跳数。
4. **可验证，不是论证。** 形态 ③④ 的接入演练**必须**实测 `AR-29` 的 P99；
   若不达标，本记录的失效条件第 2 条即触发。

## 与 `AR-3` / `AR-4` 的关系（必须正面回答）

`AR-3` 规定 **L0 接入层禁止自研，必须复用现成组件**。Go 反向代理若不解释清楚，
会被看成「自研了 L0」。实际上不成立，理由是：

- **我们不自研代理本身。** 转发由 Go **标准库**的 `net/http/httputil.ReverseProxy` 完成 ——
  它与 nginx / Envoy 一样是现成、久经考验的实现，不是我们写的。我们写的只有 L1 的那部分：
  取观测、派生 `decision_id`、调核心、按结果选 upstream。这正是 `language.md` 定义的 L1 职责。
- **TLS 卸载与镜像仍由客户的现成组件做**（云 LB / 客户的 Envoy / nginx），
  形态 ③④ 里它们仍是 L0。形态 ④ 的边车模式下，L0 与 L1 合并在同一个 Go 进程里，
  此时 L0 的角色由标准库承担。

`AR-4` 规定 **每层只选一个组件，禁止多层代理叠加**。本决策下请求路径上
**只有一个代理进程**（我们的 Go 进程），不叠加第二个代理去争抢流量控制。
客户原有的 LB 属于 L0 且职责不同（TLS 与入口路由），与 `AR-4` 举例的
「Istio 与 Cilium 同时争抢流量控制」不是一类问题。

> 这两条要与现成组件一起评审：**若某形态下出现「客户的 nginx + 我们的 Go 代理」两级七层代理
> 且都要做路由决策，即为 `AR-4` 违规**，必须简化为一层。

## 对候选 A 最强优点的回应

候选 A 的真实优势是「**能内嵌进客户已有的 nginx**」—— 客户不必多跑一个进程。
这个优势成立，但它的代价被低估了：

1. **它并不真的"零改动"**：nginx 内嵌 Lua 需要客户装 OpenResty，或用 `lua-nginx-module`
   重新编译 nginx。对客户运维而言，这本身就是一次不小的变更；
2. **要在 Lua 里手写三样容易出错的东西**：`ST-10` 的 `decision_id` 派生、
   `INT-25` 的白名单（且必须**先于**引流判定生效）、`ST-11` 的超时降级 ——
   而且**没有静态检查兜底**（见理由 3）；
3. **多出的那个进程本来就是设计要求的形态**：`INT-9` 明确交付物**必须**是
   「一个独立服务 + 接入物料」，**禁止**做成需要嵌入业务进程的形态。
   嵌入客户 nginx 虽然不碰业务代码，但方向上是把逻辑塞进别人的进程，与本项目的交付形态不合。

## 对候选 C 的回应

Rust + Pingora 的性能上限最高，但本项目 L1 的工作量是**网络转发 + 一次 gRPC 调用**，
瓶颈在跨进程往返（`E1` 实测空载 P99 116 µs）而不在语言。
引入 Rust 的代价是「核心 Go + L1 Rust」两个工具链、两套门禁、两种依赖审计 ——
而 `ADR-0006` 已经论证过 Go 在核心层的收益超过了 Rust 的穷尽性优势。

## 对候选 D 的回应

Envoy + Go `ext_proc` 服务是可行的（`E1` 已实测），但：

- 它需要**两个组件**（Envoy + 我们的服务）才能完成形态 ③，而候选 B 只需要一个；
- 形态 ④ 的边车场景里，Envoy 边车 + 我们的服务 = 两个进程挤在业务 Pod 里，
  与「最少活动部件、最小镜像」的目标相反；
- `ext_proc` 的路由重定向**必须显式让 Envoy 的路由缓存失效**（`ClearRouteCache`），
  漏配就静默不生效 —— 这一类隐性前提在候选 B 下不存在。

**但候选 D 仍是 `api/judge/v1` 契约的合法调用方**：任何实现了该 gRPC 契约的组件
都能接进来（`INT-5`：四种形态各自独立工作）。本决策不排除它作为**客户自带组件**的接入方式。

## 失效条件

出现下列任一情形时**必须**重开本记录：

- **目标客户普遍已有 OpenResty，且明确拒绝新增一个进程** → 重开，评估「Go 核心 + Lua 薄壳」的双形态；
- **形态 ③④ 实测达不到 `AR-29` 的 P99 ≤ 5 ms 预算**，而候选 A/C 在同条件下达标 → 重开；
- **`edge-injection` 的投毒改写出现 Go 难以表达的 nginx 原生能力需求**
  （例如 `sub_filter` 级流式改写）→ 重开，可能回到「L1 用 Lua、仅投毒走内嵌」的混合方案；
- **客户环境禁止部署非 Go 之外的语言无关** —— 不构成失效条件，本决策已移除 Lua。
