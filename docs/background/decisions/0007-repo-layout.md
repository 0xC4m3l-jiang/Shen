# 0007. 仓库布局：按平面分组的扁平结构（否决 `src/` 单层）

- 状态：✅ **已采纳**
- 日期：2026-09-17
- 影响范围：[`../../design/structure.md`](../../design/structure.md) §1 的全部内容（含 `ST-1`（代码必须按 §1.1 的顶层目录组织）…`ST-5` 的路径）；[`../../design/modules.md`](../../design/modules.md) §1.1 的 21 行源码目录；`Makefile`
- 决策者：用户

## 背景

用户提出：**顶层目录太多**，希望"根目录只留 `docs` / `src` / `scripts` / `deploy`"，把代码全部收进 `src/`。

按此执行后（方案 B），暴露出三类代价。**其中一条不是主观判断，而是工具的客观失败**：

```console
$ go test ./...          # 在仓库根目录
# ./...
pattern ./...: directory prefix . does not contain main module or its selected dependencies
FAIL ./... [setup failed]
```

**自动化的 Go 测试运行器在仓库根目录直接失败** —— 因为 `go.mod` 在 `src/` 里。
这直接与用户「保证功能的单元测试」的要求冲突。

另有两条：

- `Makefile` 里 **8 个 target 全部要 `cd src &&`**（是布局的补丁，不是设计）
- 编辑器 / `gopls` 的工作区根必须设成 `src/`，否则 Go 代码导航失效

**不决定的代价**：模块的源码目录会随布局反复变动，而 `MD-19` 要求目录与清单一一登记 —— 布局不定则清单一直飘。

## 候选

| 候选 | 它擅长什么 | 它的代价 | 什么条件下它最优 |
| --- | --- | --- | --- |
| **A. 扁平 · 按平面分组** | 顶层目录名直接对应架构的层/平面；Go 工具链零摩擦（`go.mod` 在根）；每层天然是一个语言/构建单元 | 顶层 9 个目录，比 4 个多 | 多语言 + 分层架构同时存在时 |
| **B. `src/` 包一切** | 顶层目录少（4 个）；"代码都在一处"直觉直接 | **`go test ./...` 在根目录失败**；`Makefile` 需 8 处 `cd`；IDE 工作区根要改；`api/`（跨语言契约）被归入 Go 模块树 | 单一语言、且工具链不介意多一层时 |
| **C. 折中：只把 `api/` 与 `go.mod` 提到顶层** | 改动小 | `src/` 仍是零信息量的中间层，只是少包了一个 `api/` | 已大量投入 `src/` 且不想返工时 |

**另评估并否决**：在根目录放 `go.work`（`use ./src`）。实测它让根目录的 `go build ./...` 报
`directory prefix . does not contain modules listed in go.work` —— **错误信息比 `cd` 更令人困惑**。

## 决定

**采纳候选 A —— 顶层扁平、按架构平面分组。**

```text
Shen/
├── AGENTS.md   Makefile   go.mod  go.sum
├── docs/        本项目的设计与决策文档
├── api/         ★ 契约单一事实源（.proto + 生成的 Go）
├── core/        核心 —— 判定与响应生成的唯一实现（Go）
├── edge/        L1 数据平面 —— 四个接入适配器 + L1 处置（Lua / Wasm / 配置）
├── deception/   L2+L3 执行平面 —— 蜜罐、假 shell、网络策略
├── analysis/    L4 分析平面 —— 意图 / 攻击链 / 策略 / LLM 组件（Python）
├── console/     控制平面 —— 控制台（TypeScript）
├── deploy/
└── scripts/
```

阶段未到的目录（`deception/` `analysis/` `console/`）**不预建**（`MD-21`（MVP 只交付标记为阶段 1 的模块））。

## 理由

### 1. 候选 A 的目录名携带架构信息，B 的 `src/` 不携带任何信息

`AR-1` 的实际拓扑是五个部分：核心 + 数据平面(L1) + 执行平面(L2+L3) + 分析平面(L4) + 控制平面。
候选 A 让**每个顶层目录名就是其中一块** —— "代码在哪"与"架构图上的哪一块"是同一个答案。

候选 B 把五个有意义的目录换成**一个零信息量的 `src/`**。它没有减少目录数量，
只是把 5 个顶层目录变成 5 个二级目录，同时增加了两层路径。

### 2. 「一个顶层目录 = 一个可独立构建单元」是 `TB-25` / `TB-24` 的直接推论

- `TB-25`：一个进程只允许一种语言
- `TB-24`：跨语言禁止 FFI / CGO / 共享内存，只走 wire format

两者合起来意味着**语言边界就是进程边界与构建边界**。
因此每个顶层目录应当是一个能独立构建的单元 —— 而这正是候选 A 的形状。

### 3. 候选 B 的代价落在最贵的地方：开发内循环

`go test ./...` 在根目录失败，意味着**任何自动化测试运行器、CI 默认配置、编辑器集成都需要特判**。
而用户明确要求「保证功能的单元测试」。**用一个便利性收益换掉测试工具链的默认行为，不划算。**

### 对候选 B 最强优点的回应

B 的唯一优点是"顶层目录少"。但如前所述，**数量并没减少**（5 个去哪了？在 `src/` 里）。
真正被减少的是**信息量**。若要减少目录数，正确的做法是合并**职责相近**的目录，而不是加一层容器。

## 后果

- **正面**：`go build ./...` / `go test ./...` / `gopls` 全部按默认约定工作，`Makefile` 零 `cd`；目录名与架构平面一一对应；`api/` 如实处于跨语言位置。
- **负面**：顶层 9 个目录（含 `docs/`）。对不熟悉本项目的人来说，"为什么不是 `src/`"需要解释一次 —— 本记录就是那个解释。
- **引入的新风险**：无（这是收敛而非扩张）。
- **被排除掉的可能性**：单语言项目的常规形状（`src/` 或纯根目录）；用 `go.work` 做多模块 workspace。

## 失效条件

- 当**顶层目录增加到 12 个以上**，说明分组轴选错了 → 重开，考虑二级分组。
- 当 `deception/` 与 `analysis/` 被证明**应该合并**（例如 L2 的协议仿真改为 Python）时 → 重开。
- 当团队改为**单语言**（例如砍掉 Python 与 TypeScript 层）时 → 候选 B 的代价消失，可重新评估。
- 复查日期：**2027-03-17**
