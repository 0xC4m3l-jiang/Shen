# 0004. 术语体系：蜃系 vs L0–L4 / 蜜饵系

- 状态：✅ **已采纳**（2026-09-17）
- 日期：2026-09-17
- 影响范围：全部源码标识符、配置键、内部文档、内部日志、提交信息；`OH-1` 禁用清单的全文重算；仓库名与二进制名
- 决策者：用户

## 背景

`TM-1` 已确认的术语体系是一套**单一语源**（「海市蜃楼」）的中文命名 + ASCII 映射：

```text
蜃 director   蜃气 shenqi   海市 haishi   蜃楼 lou-<N>   蜃景 observe
山市 shanshi  鬼市 guishi   实景 origin
项目名 蜃 / Shen
```

`docs/research/deception-engine-design.md` 用的是**分层编号 + 安全业界术语**：

```text
L0 接入层 / L1 边缘欺骗层 / L2 高交互欺骗层 / L3 网络欺骗层 / L4 分析决策层
核心 / 适配器 / 蜜饵 / 蜜标（Canary Token）/ 会话水印 / 投毒 / 引流 / 态势去重
```

**为什么必须重开**：两套术语覆盖的**对象不同**，不是简单的措辞之争。

| | 蜃系 | L0–L4 / 蜜饵系 |
| --- | --- | --- |
| 命名对象 | **本项目的模块**（director / shenqi / haishi / observe） | **分层与业界通用概念**（接入层 / 蜜饵 / 蜜标） |
| 与 `TB-5` 三 crate 的关系 | 一一对应（模块边界 = crate 职责） | 不对应（设计稿的「核心」是一个 Go 进程，跨了本项目三个 crate） |
| 可读性 | 需查表 | 安全从业者零成本 |
| 对外泄漏风险 | 高（`OH-1` 列了 12 个禁用串） | 低（`honeypot` / `decoy` 等本就是行业词，不构成指纹） |

**不决定的代价**：术语一旦进入代码标识符，改名成本随代码量线性上升（`TM-8` 要求先改文档再改代码）。
且 `TM-1` 与 `OH-1` **强耦合** —— 每新增一个术语，`OH-1` 禁用清单必须同步复核（`TM-9`（术语变更必须同步复核泄漏清单））。

## 候选

| 候选 | 它擅长什么 | 它的代价 | 什么条件下它最优 |
| --- | --- | --- | --- |
| **A. 维持蜃系** | 与 `TB-5` 三 crate 一一对应（模块边界 = crate 职责，见 `M-1`）；单一语源，内部辨识度高，且**对外无任何语义泄漏**（攻击者看到 `haishi` 猜不出 honeypot）；命名已定稿（`research/naming-design.md` 有语源考据与撞名实测） | 新人需查表；`OH-1` 禁用清单必须与术语表同步维护（12 个串） | 模块命名需要强辨识度、且希望内部代号对对手完全无信息时 |
| **B. 改用 L0–L4 / 蜜饵系** | 安全从业者零成本；`蜜饵` / `蜜标` / `会话水印` 是本项目**确实需要**的概念（`TM-1` 目前没有对应词） | 设计稿的「核心」跨了本项目三个 crate，与 `TB-5` / `M-1` 不兼容；`L0–L4` 是**部署分层**而非**模块**，两者混用会让 `docs/modules/` 的划分失焦；`TM-1` 作废，`OH-1` 需全量复算 | 团队完全由安全背景构成，且不介意术语与 crate 职责解耦时 |
| **C. 混合：模块名用蜃系，通用概念用业界词** | 保留 `TB-5` 的一一对应；同时补上 `TM-1` 缺失的概念（蜜饵 / 蜜标 / 会话水印 / 幂等键）；且**这些业界词本身就是行业通用语，不构成指纹**（`OH-2` 判据下允许） | 两套语汇并存，新人需知道「哪些位置用哪套」——但这条边界是清晰的：**模块 = 蜃系，通用概念 = 业界词** | 需要同时满足「模块边界对齐 crate」与「概念可被安全从业者直接理解」时 |

## 决定

**采纳候选 B —— 全部改用 `设计.md` 的行业术语体系。** 详见 [`../../design/terminology.md`](../../design/terminology.md)：

```text
分层：      L0 接入层 / L1 边缘欺骗层 / L2 高交互欺骗层 / L3 网络欺骗层 / L4 分析决策层
架构：      核心（core）/ 适配器（adapter）/ 控制面 / 数据面 / 欺骗执行面
概念：      判定（Judge）/ 蜜饵 / 蜜标（Canary Token）/ 蜜罐 / 会话水印 / 投毒 / 引流 / 隔离
工程：      幂等键 / 态势去重 / fail-open / 契约 / 核心状态
```

原「蜃 / 蜃气 / 海市 / 蜃楼 / 蜃景 / 山市 / 鬼市 / 实景」语汇格**全部停用**（原 `TM-1` 已废弃）。

**与候选倾向的差异（如实记录）**：本记录的倾向是候选 C（模块名用蜃系、概念用业界词）。
**用户选择了 B（全部用行业术语）**。理由：语言改成分层多语言后，`L0–L4` 会自然出场，
两套语汇并存反而增加了「哪个位置用哪套」的认知成本。

## 理由

**对候选 A（维持蜃系）最强优点的回应**（对外零语义泄露、模块边界强辨识度）：
该优点在**新的威胁模型下不成立** —— `honeypot` / `decoy` 这类行业词**本身不构成可被指纹推断的内部信息**，
它们真正的风险是「出现在攻击者可见面上直接自曝」—— 而那一层已由 `OH` 段单独管理（OH-1 / OH-2）。
也就是说：**A 用「生僻代号」防的事，OH-1 用「禁用清单」已经防住了。**

**对候选 C 最强优点的回应**（保住与 crate 职责一一对应）：
该对应关系在分层架构下本就变了（不再有三个 Rust crate）。`MD-1`（一个模块只属于一层）
已经提供了边界约束，不需要靠命名来实现。

**诚实记录的代价**：

- 行业术语**丧失内部辨识度**，且**部分术语在中文里极易误读**（如「引流」在网络营销语境有另一义）。
- `OH-1` 禁用清单**全文重算**（`TM-9`），且新术语与行业词高度重合，**禁用词数量显著增加**。
- 项目名（仓库名 / 二进制名 / 产品名）**未在 `设计.md` 中定义**，成为新的未决项。

## 后果

- **正面**：安全从业者零成本理解；与 `设计.md` 全文对齐；不再需要为「哪个位置用哪套语汇」做判断。
- **负面**：丧失内部辨识度；`OH-1` 禁用词数量显著增加；`research/naming-design.md` 的全部语源考据**对新代码失去指导意义**（仅存历史价值）。
- **引入的新风险**：行业术语与「实在的蜜罐系统」用词重叠 —— 对手看到 `honeypot` 字串时**无法区分这是本项目的内部命名还是它真的闯进了一个蜜罐**，但只要它出现在响应面上就是自曝，因此风险由 OH-1 承担。
- **被排除掉的可能性**：一个**对内独一无二、对外零语义**的命名体系。

## 失效条件

- 当**行业术语导致实际误读**（如命名冲突、团队沟通歧义、与外部组件同名）时 → 重开。
- 当**代码量超过约 5k 行**时 → 改名的边际成本超过收益，本记录必须结案（无论维持还是再改）。
- 当**对外品牌需要一套与内部术语解耦的命名**时 → 另开 ADR（属品牌决策，不在本记录范围）。
- 复查日期：**2026-12-17**

## 未解决

- ⚠️ **项目名与仓库名**：`设计.md` 只定义了技术术语，**没有定义项目叫什么**。
  原命名体系（基于「海市蜃楼」）随之失去对象。**这是当前最明显的空白**。
  在拍板前，仓库与二进制**应当**使用中性的临时名，**禁止**把任何候选名写进契约或指标名。
- `L0–L4` 与「核心」「适配器」的层级关系需在 [`../../design/architecture.md`](../../design/architecture.md) 保持一致（已保持）。
- 原记录提到的既有不一致（`蜃气` 无对应 crate 位置）**随本次重构消失**。
