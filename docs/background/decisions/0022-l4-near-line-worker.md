## 背景

L4（`llm-components` / `intent` / `chain` / `strategy`）此前只有**库 + 单测**：模块按设计实现了，但**运行时没有任何东西会调用它**
（`architecture.md` §2 的链路是「遥测事件 → 态势去重 → 意图 → 攻击链 → 策略生成 → `policy` 版本化」）。
这构成「整体功能不准确」：设计里 L4 是链路的一环，实际却是死代码。

## 候选

| 候选 | 内容 | 优势 | 代价 |
| --- | --- | --- | --- |
| **A** | **近线 worker 进程**：独立 Python 进程读核心的 `ListEvents`，去重后分析，把结论**作为事件**上报（采纳） | 合设计（L4 是近线/离线，不在请求路径）· 读侧契约已存在（`ListEvents`）· 结论复用既有观测面，控制台立刻可见 · 挂了不影响业务（`NI-1`） | 多一个进程；Python 侧需要 gRPC 依赖 |
| **B** | 核心内嵌触发（判定后同步调用 L4） | 延迟低 | **违反分层**：L4 是 Python，核心是 Go；且近线分析塞进请求路径会撞 `AR-29` 延迟预算 |
| **C** | L4 暴露 HTTP 接口，核心反向调用 | 无 Python 侧 gRPC 依赖 | 核心要新增出站依赖与重试语义；仍要解决「谁去重、谁存储」 |
| **D** | 继续不接 | 无改动 | 目标不达成（模块存在但链路不通） |

## 决定

1. **采用候选 A**：`python -m analysis.worker`（`make analysis` 跑一轮；不带 `--once` 则常驻轮询，默认 30s）；
2. **只读 + 只上报**：worker 只调 `ListEvents` 与 `Report`；**不写**存储（`MD-20`），**不持有执行能力**（`AR-32`），**不直接改策略/回写响应**（结论经 `policy` 间接生效）；
3. **去重在 L4 侧**（`AR-14`）：worker 内部用 `SituationDedupe` 按 `(来源, 会话, 方法, 路径)` 窗口去重，**禁止**随事件量线性触发；
4. **证据校验真的会咬人**（`AR-12`）：worker 维护有界的已见证据缓存，链里引用缓存外的 ID 即整条链作废；
5. **降级语义**：遥测不可达 → **本轮不分析**并记错误（近线，不在业务路径，`NI-1`）；`--once` 模式返回非 0 以便门禁与人工测试发现；
6. **结论可见**：结论以 `analysis` 事件上报，控制台新增 `分析结论（L4）` 块与 `/api/analysis` 接口。

## 后果

| 类型 | 内容 |
| --- | --- |
| ✅ 正面 | 设计里的 L4 链路**真的通了**（实测：真流量 → 判定事件 → 去重 3 条 → `intent` 接受 + `strategy` 拒绝 → 控制台可见 2 条结论） |
| ⚠️ 负面 | 多一个进程与一份 Python gRPC 依赖（`grpcio` / `grpcio-tools`，已锁版本） |
| 🔧 需同步 | [`../spec/events.md`](../spec/events.md)（事件契约）· `console` 的结论块 · `make dev`（第 6 步跑一轮 L4） |

## 失效条件

1. `NI-13`（存储与保留期）落地后改用持久化的分析队列 → 重开，评估是否换成长驻消费者 + 断点续读；
2. L4 需要**秒级**响应（例如参与在线会话对抗）→ 重开：那时延迟预算与语言选择都要重新算；
3. 出现第二个 L4 消费方（如离线报表）→ 重开，把「读侧 + 去重」下沉为共享能力，避免每个消费方各写一份。

## 未解决

- **无断点续读**：worker 每轮只取最近 `--limit` 条，进程重启后不会回补更早的事件（靠 `event_id` 幂等保证不重复，但可能漏掉窗口外的事件）；
- **未接真实 LLM**：`UnconfiguredClient` 显式失败（`AR-15` 禁止模板冒充模型输出）；接模型后双阶段收尾（`AR-19`…`AR-21`）才会真正被走到；
- **结论尚未回写 `policy`**：`strategy` 产出只是数据，接策略面（`AR-13` 版本化 + 灰度）是下一步。
