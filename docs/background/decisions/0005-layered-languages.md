# 0005. 语言改为分层多语言（L0–L4），不再是「在线全 Rust」

- 状态：✅ **已采纳** —— 取代 [ADR-0001](0001-language-rust.md)
- 日期：2026-09-17
- 影响范围：全部实现语言、仓库布局、跨语言接缝、CI 工具链、`docs/design/language.md` 与 `docs/design/structure.md`
- 决策者：用户

## 背景

`ADR-0001` 定的基线是「在线全 Rust + 离线 Python，两种语言」。它的**核心收益**是：

> `shen-core` 是纯逻辑 crate，**一处实现、两个编译目标**共用（ext_proc 服务 + Envoy WASM filter），
> 因此判别与调度逻辑只写一遍（原 `TB-7`（已废弃·判别逻辑只在 shen-core 实现一次））。

同期存在一份外部设计稿（`docs/research/deception-engine-design.md`，v1.7，1442 行），
主张按 **L0–L4 分层选型**：接入层复用现成组件、边缘层 Lua/Rust、核心 Go、AI 层 Python、控制台 TypeScript。

用户先裁定「维持 Rust × 2」（上一轮），随后在本次设计文档重构中**改为采纳分层多语言**。

**不决定的代价**：语言决定仓库布局（`structure.md`）、接缝形态（`ST-6`（api/ 是契约唯一事实源，客户端必须生成））、CI 门禁（`TB-15`（CI 必须过格式化 / 静态检查 / 单测 / race））、
构建与发布流程 —— 全部无法落地。

## 候选

| 候选 | 它擅长什么 | 它的代价 | 什么条件下它最优 |
| --- | --- | --- | --- |
| **A. 在线全 Rust + 离线 Python**（原基线） | 一处实现两个编译目标（判别逻辑只写一遍）；编译期排除整类缺陷；无 GC 抖动 | 异步 Rust 迭代成本高；AI 生成代码陷入编译—修复长循环；**前提是"确实需要第二个编译目标"** | 确实需要把同一套判定编译进 Envoy WASM 时 |
| **B. 分层多语言（L0–L4）** | 每层用该层生态最成熟的库；边缘层热更新（Lua）；核心开发与测试快（Go 内建 `-race` / `-fuzz` / `-bench` / `pprof`）；AI 层完整 Python 生态 | 5 套工具链与 CI；跳语言可观测性需统一；**判定逻辑有分裂风险** | 分层职责清晰、且各层确有独立演进需求时 |
| **C. 折中：边缘 Lua + 核心 Rust + AI Python** | 保留 Rust 在核心的编译期保证，同时获得边缘热更新 | 仍需 3 套工具链；核心无法复用现有 Rust ext_proc 生态经验 | 核心是性能与安全双瓶颈时 |
| **D. Go 主体 + Python AI（不分层）** | 工具链最少（2 套） | L1 边缘层缺毫秒级延迟与热更新能力；控制台无法用 Go 替代 | 单体服务、无边缘层需求时 |

## 决定

**采纳候选 B —— 分层多语言（L0–L4）。** 详见 [`../../design/language.md`](../../design/language.md)：

```text
L0 接入层    C / Rust（不自研，复用 Envoy / Nginx / HAProxy）
L1 边缘欺骗层 Lua (OpenResty) 或 Rust (Pingora)   ← 只做处置执行，不做判定
核心          Go                                   ← 判定与响应生成的唯一实现
L2 高交互层   Python (LLM) + Go / Rust (协议)
L3 网络层     Go (编排) + Rust / eBPF (数据面)
L4 分析决策   Python
安全底座      Rust
控制台        TypeScript
```

**语言总数上限 5**（`TB-21`），**禁止**引入第 6 种。

## 理由

**对候选 A 最强优点的回应**（判别逻辑只写一遍，这是它唯一的硬优势）：
这个收益**不依赖单一语言** —— 它由架构纪律提供：**判定与响应生成只写在核心一处**（`AR-2`（判定逻辑只在核心一处，适配器禁止实现判定） / `AR-5` / `TB-22`（判定与响应生成必须用 Go 写在核心内）），
L1 边缘**只执行处置、不含判定**（设计稿 §2.1 明确写了「判定逻辑不在此层」），适配器只做搬运（`MD-9`（适配器只做四件事，禁止越界））。
换句话说：**A 用一个共享 crate 达成的事，B 用一个架构约束达成** —— 而 B 额外拿到了
边缘热更新、核心的开发测试速度、完整的 Python AI 生态。

**对候选 C 最强优点的回应**（Rust 的编译期保证）：
保留在**真正需要它的地方** —— 安全底座（`TB-23`（Rust 组件必须声明禁止 unsafe） 要求 `#![forbid(unsafe_code)]`）与 eBPF 数据面。
核心不需要它：核心是「无状态多副本 + 内存查表 + 外部存储访问」的形状，Go 的类型系统足够。

**诚实记录的代价**：

- 5 套工具链与 CI，运维面翻倍。
- 跳语言问题定位需要统一 OTel + W3C `traceparent`。
- **判定逻辑分裂风险是真实的** —— 它是本决策最大的负面后果，靠 `AR-2` / `TB-22` / `MD-9` 三条规则压住。
- Go 的 `switch` **不强制穷尽** —— 漏改分支不报错。**对冲**：`MD-8` 要求判定器分支枚举有穷尽性测试。

## 后果

- **正面**：每层用最成熟的生态；边缘可热更新；核心的开发/测试/剖析工具链内建；AI 层完整；判定逻辑只在核心一处（由规则保证）。
- **负面**：5 套工具链与 CI；跨语言可观测性成本；**判定逻辑可能被实现者在边缘层重写一遍**（最需要防的失败模式）。
- **引入的新风险**：跨语言接缝增多 → **禁止 FFI / CGO / 共享内存**（`TB-24`）；一个进程只能一种语言（`TB-25`（一个进程只允许一种语言））。
- **被排除掉的可能性**：Rust 全栈的编译期保证；「一处实现两个编译目标」这条路径（`shen-core` 共享 crate 不再存在）。

## 失效条件

- 当**判定逻辑被证明在核心之外出现了第二份实现**时 → 本决策的架构前提已破，**必须**重开并回到候选 A（共享 crate 的强制力更强）。
- 当**工具链维护成本超过团队承受能力**（如 CI 时长翻倍、跳语言问题占比超预期）时 → 重开，优先合并 L1 与核心。
- 当**确认必须把判定逻辑编译进 Envoy WASM**（而非经 `ext_authz` 旁路调用）时 → 候选 A 的硬优势重新成立，重开。
- 复查日期：**2026-12-17**

## 未解决

- **核心层的语言（Go vs Rust）** —— 已由 [ADR-0006](0006-core-language-go.md) **正式复查并确认维持 Go**（含三候选对比与 `E1` spike 判定标准）。
- **L1 边缘层用 Lua 还是 Rust（Pingora）** —— 未拍板，倾向按客户环境定（传统虚机 → OpenResty；云原生 → Rust/Wasm）。
- **核心与 L1 的判定边界如何在 CI 中强制** —— 需要一条「L1 源码中不得出现判定相关标识符」的静态检查，尚未设计。
- **原 `TB-18` 的回退条款失去对象**：它规定「若 Rust 迭代成本不可接受则回退 Go」—— 而 Go 现在就是基线。
- **Go 的核心选型未做 spike**：本决策**没有**实验数据支撑，它是**论证，不是数据**。
  实验设计与判定标准见 [`../notes/pending-experiments.md`](../notes/pending-experiments.md) 的 **E1**
  （含 bidi streaming 阶段状态机的正确性、每流内存、P99 开销三项针对本决策风险的新增指标）。
