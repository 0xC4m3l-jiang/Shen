# 0006. 核心层的语言：复查 Go vs Rust

- 状态：✅ **已采纳**（复查结论：**维持 Go**）
- 日期：2026-09-17
- 影响范围：`core/internal/` 全部 8 个模块；`deception/edge/` 与 `adapters/` 的语言选择；[`../../design/language.md`](../../design/language.md) 的 `TB-20`（各层必须按选型用语言，禁止跨层混用）…`TB-26`（跨语言接缝必须带版本号）
- 决策者：用户
- 与本目录其他记录的关系：**补充** —— [ADR-0005](0005-layered-languages.md) 决定的是「分层多语言」这个**结构**；本记录决定的是「核心那一层用哪个语言」这个**层内选择**。两者不是取代关系。

## 背景

`ADR-0005` 把核心定为 **Go**，但它在自己的「未解决」段里写明：

> **Go 的核心选型未做 spike**：本决策**没有**实验数据支撑，它是**论证，不是数据**。

而更早的 `ADR-0001`（已废弃）主张**在线全 Rust**，其核心论据是「判别与调度逻辑一处实现、两个编译目标共用」。
用户要求正式复查这一层选择。

**为什么这次复查与 ADR-0001 时期的结果不同**：`ADR-0001` 的判断建立在「L1 也用 Rust（Wasm）」之上；
而 `ADR-0005` 把 L1 定为 Lua 或 Rust 之后，**共享 crate 的收益消失**，其论据的作用面随之改变。

**不决定的代价**：核心是 `ST-1` 目录布局的第一层，也是所有模块的依赖目标。它未定则 `core/internal/` 无法创建。

## 候选

| 候选 | 它擅长什么 | 它的代价 | 什么条件下它最优 |
| --- | --- | --- | --- |
| **A. 核心 Go**（现行基线） | 测试与开发工具链**内建**（`-race` / `-fuzz` / `-bench` / `pprof`）；隐式接口使测试替身极轻；增量编译 1–5 s，AI 参与的改—编—测循环快；gRPC 生态是参考实现 | `switch` 不强制穷尽；错误返回值靠 `errcheck` 而非编译器；有 GC | 判定规则以**数据**形式存在（`ST-24`），且判定缓存不在核心（`AR-6`）时 |
| **B. 核心 Rust + L1 也用 Rust/Wasm（去掉 Lua）** | 「判定一处实现」由**共享 crate + 编译器强制**，而非 CI 检查；语言总数降到 3–4 种 | 迭代 10–40 s；L1 失去 Lua 的策略热更新；异步 Rust + gRPC bidi streaming 是 AI 生成代码迭代最痛的形状 | 确实存在两个以上编译目标、且必须共用同一套判定逻辑时 |
| **C. 核心 Rust + L1 仍用 Lua** | 核心拿到编译期保证，L1 保留热更新 | 本组合下 Rust 的优势**最小**（无共享 crate）、代价**最大**（迭代慢 + 语言数不降） | —— （本组合不具备可取性） |

> 候选 B 是本次复查**首次摆出**的选项 —— 前两轮只比过「Go 还是 Rust 占核心」，没比过「去掉 Lua」这条路。

## 决定

**采纳候选 A —— 核心维持 Go。**

```text
核心（判定 judge · 调度 director · 响应生成 responder · 会话 session
     隔离 isolation · 策略 policy · 遥测 telemetry · 存储访问 store）  → Go
L1 边缘（edge-injection / 四个适配器）                                  → Lua 或 Rust/Wasm
L2 / L4 与协议仿真                                                     → Python（+ Go/Rust）
控制台                                                                 → TypeScript
```

## 理由

### 1. 这不是性能题 —— 先排除最容易走偏的比法

`AR-29` 的预算是「业务路径 P99 额外延迟 ≤ 5 ms = 缓存 1 + Judge 3 + 处置 1」。
核心在那 3 ms 里要做的是：**读一次 Redis + 查表 + 算一个判定**。

该负载量级下，Go 与 Rust **都远超需求**（两者都能做到远低于 100 μs）。在一个宽松约 30 倍的预算里比谁的尾延迟更低，不构成决策依据。

### 2. Rust 的两个优势，被架构本身抵消了

| Rust 的优势 | 被谁抵消 | 抵消后剩余的作用面 |
| --- | --- | --- |
| **enum 穷尽性**把 `MD-8` 变成编译错误 | **`ST-24`**：策略**必须**是数据（禁止编译进代码）→ **判定规则不是代码分支** | 只剩**决策枚举本身**（3 个值或 5 个值）与少量引擎分支。收益作用在一个约 5 值的枚举上，而非"上百条规则" |
| **无 GC**（尾延迟不抖动） | **`AR-6`**：判定缓存放在**适配器**（与代理同进程），核心不持有缓存 | 核心堆很小 → Go 的 GC 停顿落在亚毫秒级，而预算给核心留了 3 ms |

这两条是 `ADR-0001` 的核心论据，但在当前分层架构下**权重显著下降**。

### 3. 用户的三个要求里，两条指向 Go

用户明确要求「保证工程化、模块化、**功能的单元测试**」。

| 能力 | Go | Rust |
| --- | --- | --- |
| 数据竞争检测 | ✅ `go test -race` 内建 | 🟡 类型系统更强，但无运行时检测 |
| 模糊测试 | ✅ `go test -fuzz` 内建 | 🟡 `cargo-fuzz` 外挂 |
| 基准测试 | ✅ `-bench`，直接 ns/op | 🟡 `criterion` 外挂 |
| 性能剖析 | ✅ `net/http/pprof` 零配置 | 🟡 `pprof-rs` / `tokio-console` 外挂 |
| **写测试替身** | ✅ 隐式接口，随手写 | 🟡 trait object + `async` 约束，`mockall` 外挂 |

`MD-22` 要求「每个模块**必须**有独立可运行的测试套件，测试**禁止**依赖其他模块的真实实例」——
这条在 Go 里是"写个假实现"，在 Rust 里要处理 `Send` / `Sync` / 生命周期。

**模块化与语言无关**（由 `MD-1`…`MD-22` 保证），所以用户三条要求中，实际参与本决策的是两条，两条都指向 Go。

### 4. 迭代速度对「AI 参与开发」是复利效应

核心的对外接口 `S1` 是 **gRPC bidi streaming**：ext_proc 按
`request_headers → request_body → response_headers → response_body → trailers` 分五阶段响应，
**每流的状态机需要自己写**。这是 AI 生成 Rust 代码迭代次数最多的形状
（`tokio` + 跨 `await` 持有状态 + `Pin` + `Send` bound）。

`ADR-0005` 已对此做过权重判断，本记录确认该判断成立。

### 对候选 B 最强优点的回应（它是本次复查中最有价值的反对意见）

**候选 B 的收益是真的**：只有 L1 也用 Rust 时，「判定一处实现」才能从 **CI 检查**（可绕过）升级为**编译器强制**。这是 `AR-2` 目前唯一的实现手段差异。

**但仍不采纳，理由有二**：

1. **`AR-2` 已有三层防线** —— `AR-2`（架构）+ `AR-5`（实现）+ `MD-9`（适配器只做四件事，禁止越界）+ `MD-19`（目录）+ `TB-22`（语言）。缺的是"编译器强制"这一层，而非"没有防线"
2. **代价落在最贵的地方** —— L1 失去 Lua 的策略热更新（`ST-24` 要求策略是数据，热更新是其兑现方式），且核心迭代成本上升。用一个可绕过的检查的空缺，换两个实打实的代价，不划算

### 对候选 C 的处理

候选 C（核心 Rust + L1 仍用 Lua）在**收益最小、代价最大**的角上：拿不到共享 crate，却要付 Rust 的迭代成本，语言总数还不下降。**直接排除。**

## 后果

- **正面**：测试与剖析工具链内建；替身编写成本低；迭代快；gRPC 参考实现；语言上限维持 5 种不变。
- **负面**：`switch` 不强制穷尽（`MD-8` 只能靠 CI 测试强制，可绕过）；未处理的错误返回值靠 `errcheck` 而非编译器；有 GC。
- **引入的新风险**：**Go 在 `ext_proc` 的 bidi streaming 形态下是否适用，仍无数据** —— 见「未解决」。
- **被排除掉的可能性**：「判定一处实现」的**编译器级**强制；语言总数降到 3–4 种。

## 失效条件

- 当 **`E1` spike 显示 Go 的 bidi streaming 阶段状态机写不对或流泄漏**时 → **必须**重开，改候选 B。
- 当 **`E1` 显示每流内存超 `NI-7` 的资源围栏**（并发 1k 流）时 → **必须**重开。
- 当 **`E1` 显示 P99 超 `AR-29` 预算，且 Rust 显著更优**时 → 重开。
- 当 **出现第二个编译目标**（例如 L1 改回 Rust/Wasm 并需要共用判定逻辑）时 → 候选 B 的最强优点重新成立，重开。
- 复查日期：**2026-12-17**

## 未解决

- **`E1` spike 只跑了主臂（Go）** —— 2026-09-17 执行。
  ⑦（阶段状态机）正确、⑧（P99 **116 µs**）远在 `AR-29` 的 5 ms 预算内、③（增量编译 0.08 s）可接受
  → **本记录的失效条件未触发，维持 Go**。
  但 **Rust 对照臂未跑**（工具链未安装）→ 「若 Rust 显著更优」这一条**仍无法评估**，
  ①④⑤⑥ 的人工计时也缺。原始数据见 [`../notes/pending-experiments.md`](../notes/pending-experiments.md) 的 **E1 · 结果**。
