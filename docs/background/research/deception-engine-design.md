## 一、总体设计原则

```txt
┌─────────────────────────────────────────────────────┐
│  选型三原则                                          │
│  ① 贴近职责：性能敏感用系统级语言，AI 推理用 Python  │
│  ② 贴近生态：哪层的库最成熟就用哪层的语言            │
│  ③ 贴近运维：能用现成中间件就不自己造轮子            │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│  接入三原则                                          │
│  ① 业务零改造：改基础设施，不改业务代码              │
│  ② 真实流量不受影响：欺骗是"旁路"或"引流"，非阻断    │
│  ③ 可灰度、可回滚：先镜像观察，再逐步接管            │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│  复用三原则                                          │
│  ① 基础设施层（代理/网关/边车/隔离）全部复用开源     │
│  ② 智能决策层（判定/欺骗/编排）全部自研              │
│  ③ 中间用胶水层（遥测聚合/策略回写）连接             │
└─────────────────────────────────────────────────────┘
```

## 二、分层语言选型

### 2.1 分层技术选型总表

| 层级 | 职责 | 推荐语言 | 备选 | 关键理由 |
| ------ | ------ | ---------- | ------ | ---------- |
| **L0 接入层** | 流量镜像、TLS 卸载 | **C / Rust**（或用现成组件） | Go | 直接复用 Envoy/Nginx，无需自研 |
| **L1 边缘欺骗层** | 投毒 + 假路径 + 引流执行 | **Lua (OpenResty) / Rust** | Go、C++ | 七层代理内嵌，毫秒级，热更新；判定逻辑不在此层 |
| **核心（判定 + 响应生成）** | 决策、内容生成、遥测、会话、隔离、策略 | **Go** | Rust | 无状态多副本、低延迟、gRPC 生态（见 §8.2） |
| **L2 高交互欺骗层** | 协议仿真 + LLM 交互 | **Python**（主体）+ **Go/Rust**（协议层） | Node.js | AI 生态在 Python，性能瓶颈在协议层 |
| **L3 网络欺骗层** | 蜜网 + 微隔离 + SDN | **Go / Rust** | C、P4 | 高并发、网络编程生态强 |
| **L4 分析决策层** | 意图识别 + 攻击链 + 策略 | **Python**（绝对主力） | C++（推理加速） | LLM/GNN/RL 生态全在 Python |
| **安全底座** | 隔离 + 零信任 + 沙箱 | **Rust / Go** | C | 内存安全、并发强 |
| **前端/控制台** | 可视化、编排 | **TypeScript** | — | 生态成熟 |

### 2.2 逐层说明

#### L0 接入层 —— 不要自己写

```txt
方案：直接复用现成组件
  • Envoy / Nginx / HAProxy（C/C++，工业级）
  • 或 eBPF（C/Rust）做内核态流量镜像
理由：这层是基础设施，自研纯属浪费，直接接入即可。
```

#### L1 边缘欺骗层 —— Lua (OpenResty) 或 Rust

```txt
首选：OpenResty + Lua
  • Nginx 内嵌 Lua，请求处理零网络跳转
  • 热更新：改策略不用重启
  • 生态：lua-resty-* 系列库成熟
  • 代表：konterfAI 就是反向代理模式

进阶：Rust + Hyper / Pingora
  • 内存安全，无 GC 停顿
  • Cloudflare 的 Pingora 就是 Rust 写的代理框架
  • 适合高并发 + 复杂欺骗逻辑

为什么不用 Python/Go？
  • Python：GIL 限制，高并发下性能塌方
  • Go：可以，但 GC 抖动对毫秒级延迟敏感场景不友好
```

#### L2 高交互欺骗层 —— Python 主体 + Go/Rust 协议层（混合）

```txt
┌──────────────────────────────────────────────┐
│  协议仿真（SSH/MySQL/HTTP）                    │
│    → Go 或 Rust：高并发连接、低延迟、内存安全  │
│    → 用现成库：gliderlabs/ssh (Go)、         │
│      russh (Rust)                            │
├──────────────────────────────────────────────┤
│  响应生成（LLM 推理）                          │
│    → Python：vLLM / Transformers / LangChain  │
│    → 通过 gRPC/HTTP 与协议层通信              │
├──────────────────────────────────────────────┤
│  会话状态管理（多轮记忆）                      │
│    → Redis + Python 状态机                    │
└──────────────────────────────────────────────┘

代表：VelLMes 就是 Python 为主，LLM 驱动多协议仿真。
关键：协议层用 Go/Rust 扛并发，AI 层用 Python 出智能。
```

**本层关联规范（§九）**

| 条目 | 内容 |
| --- | --- |
| §9.1.1、§9.1.18 | 输出契约层与内容黑名单（禁止泄露真实信息 / 禁止自曝蜜罐） |
| §9.1.6 | 双阶段 fallback（LLM 超时后用同一会话收尾，避免直接断开暴露异常） |
| §9.1.11 | 会话延续抽象（会话抽取用模板方法收敛，不散落在各协议实现里） |
| §9.1.20 | 输出长度分级上限（防止单次输出撑爆蜜罐连接） |

#### L3 网络欺骗层 —— Go 或 Rust

```txt
首选：Go
  • 网络编程生态极强（gRPC、SDN 控制器）
  • 并发模型简单，适合蜜网编排
  • K8s 生态原生（CNI、Service Mesh）

进阶：Rust
  • 内存安全，适合安全敏感的网络组件
  • 适合做高性能数据面

特殊场景：P4（数据平面编程）
  • 需要线速包处理、动态注入假拓扑时用
```

#### L4 分析决策层 —— Python（无争议）

```txt
这是整个系统的"大脑"，Python 是唯一合理选择：

  • LLM 推理：vLLM、Transformers、llama.cpp
  • 强化学习：PyTorch、Stable-Baselines3
  • 图分析：NetworkX、PyG（图神经网络）
  • 攻击链还原：MITRE ATT&CK 映射库

性能不够怎么办？
  → 用 C++/CUDA 写算子，Python 调用
  → 或用 Rust 重写推理服务，Python 做编排
  → 但逻辑层坚决留 Python，否则生态全丢
```

**本层关联规范（§九）**

| 条目 | 内容 |
| --- | --- |
| §9.1.19 | 引用可验证性（攻击链结论引用的证据 ID 必须真实存在于遥测存储） |
| §9.1.4 | 生成结果数量硬截断（防止单次输出生成大批策略条目） |
| §9.1.10 | 失败即整体作废（不写入半成品攻击链结论） |

#### 安全底座 —— Rust 优先

```txt
  • 沙箱隔离、零信任代理、单向通道
  • Rust：内存安全，无 GC，适合安全关键组件
  • 备选 Go：开发快，但需注意内存安全
  • 绝不用 C：手动内存管理，漏洞风险高
```

### 2.3 语言对比速查

| 语言 | 优势 | 劣势 | 最适合的层 |
| ------ | ------ | ------ | ----------- |
| **Rust** | 内存安全、无 GC、高性能 | 学习曲线陡、开发慢 | L1/L3/底座 |
| **Go** | 并发强、生态好、开发快 | GC 抖动、表达力弱 | L2 协议/L3 编排 |
| **Python** | AI 生态无敌、开发快 | 性能差、GIL | L2 智能/L4 决策 |
| **Lua** | 内嵌代理、热更新 | 生态小、不适合大逻辑 | L1 边缘 |
| **C/C++** | 极致性能 | 内存不安全、开发慢 | L0 接入/推理加速 |
| **TypeScript** | 前端生态 | 不适合后端核心 | 控制台 |

### 2.4 如果只能选一种语言

```txt
按团队能力选：

① 团队是 AI 背景 → 全 Python + 现成代理组件
   代价：性能有限，但最快出原型

② 团队是后端背景 → Go 主体 + Python 做 AI 微服务
   平衡：性能与生态兼顾，最推荐

③ 团队是系统/安全背景 → Rust 主体 + Python 做 AI
   极致：性能与安全最好，但开发最慢
```

## 三、Web 服务接入方案

### 3.1 五种接入方式（按侵入性从低到高）

#### 方式 1：旁路镜像（最推荐起步）★ 零风险

```txt
                    ┌──────────────┐
   用户 ──► LB ──┬──►│  真实 Web 服务 │
                 │   └──────────────┘
                 │
                 └──►（镜像复制）──► 欺骗引擎（只观察不响应）
```

**原理**：用 `iptables TEE`、eBPF、或 LB 的镜像功能，把流量**复制一份**给引擎。

- 业务完全无感，引擎只"看"不"答"
- 先积累攻击样本，验证识别准确率
- **零风险**，适合第一步

```bash
# iptables 流量镜像示例
iptables -t mangle -A PREROUTING -p tcp --dport 443 \
  -j TEE --gateway 欺骗引擎IP
```

#### 方式 2：DNS / 智能解析引流（针对特定目标）

```txt
   攻击者/爬虫 ──► DNS ──► 解析到欺骗引擎 IP
   真实用户   ──► DNS ──► 解析到真实服务 IP
```

- 适合"诱捕特定攻击者"
- 业务不改，只在 DNS 层做文章
- 缺点：需要 DNS 可控，对已建立连接的无效

#### 方式 3：反向代理前置（主流方案）★★

```txt
   用户 ──► [欺骗引擎/反向代理] ──┬──► 真实 Web 服务（正常流量）
                                  │
                                  └──► 蜜罐/假响应（可疑流量）
```

```nginx
upstream real_backend {
    server 10.0.0.10:8080;   # 真实业务
}

server {
    listen 443 ssl;

    location / {
        access_by_lua_block {
            -- 调用欺骗引擎判定
            local decision = judge_request()
            if decision == "deceive" then
                -- 引流到蜜罐
                ngx.exec("@honeypot")
            end
        }
        proxy_pass http://real_backend;   # 正常透传
    }

    location @honeypot {
        proxy_pass http://deception_engine;  # 引流到引擎
    }
}
```

**优点**：能主动欺骗、能改写响应、能投毒
**缺点**：单点（需 HA）、有性能损耗

#### 方式 4：Sidecar / Service Mesh（云原生）★★★

```txt
┌─────────────────────────────────────┐
│  Pod                                │
│  ┌──────────┐    ┌──────────────┐   │
│  │ 业务容器  │◄──►│ 引擎 Sidecar │   │
│  └──────────┘    └──────────────┘   │
└─────────────────────────────────────┘
         ▲
         │ 流量经 Sidecar 拦截
```

```yaml
# 用 Istio 的 EnvoyFilter 或自定义 Gateway 插件
apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: deception-filter
spec:
  workloadSelector:
    labels:
      app: my-web
  configPatches:
    - applyTo: HTTP_FILTER
      patch:
        operation: INSERT_BEFORE
        value:
          name: deception-engine
          typed_config:
            "@type": type.googleapis.com/.../DeceptionFilter
```

- 业务代码零改动
- 随 Pod 生命周期，天然高可用
- 适合微服务架构

> 实现说明：`DeceptionFilter` 需编译进 Envoy（C++）或用 Wasm 插件实现；若不想改代理二进制，
> 走 ext_authz 由旁路服务提供判定，代理侧只做转发与执行（推荐，见 §8.2 Sidecar 适配器）。

#### 方式 5：SDK 嵌入式（侵入性最高，慎用）

- 需要在业务代码里调用 SDK
- 只有前面几种都做不到时才用
- 缺点：侵入业务、升级麻烦、多语言适配难

### 3.2 推荐接入路径（分阶段）

```txt
┌──────────────────────────────────────────────────────────┐
│ 阶段 1（1周）：旁路镜像                                    │
│   → iptables TEE / eBPF 复制流量                          │
│   → 引擎只观察，验证识别率，零风险                         │
│                                                            │
│ 阶段 2（2-3周）：反向代理前置                              │
│   → 引擎上线为反向代理，先只处理 1% 流量（灰度）           │
│   → 正常透传 + 可疑引流，观察误伤率                        │
│                                                            │
│ 阶段 3（1-2月）：全量接管 + 分层欺骗                       │
│   → 全流量经适配器（缓存命中不调用核心），                  │
│     L1投毒 + L2引流 + L3蜜网                                │
│   → 接入 SIEM/SOAR，闭环响应                               │
│                                                            │
│ 阶段 4：云原生 Sidecar 化                                  │
│   → 如果上 K8s，改成 Sidecar/Ingress 插件                  │
│   → 弹性伸缩，高可用                                       │
└──────────────────────────────────────────────────────────┘
```

### 3.3 接入时必须解决的 5 个问题

| 问题 | 解决方案 |
| ------ | ---------- |
| **HTTPS 解密** | 引擎持有证书，或 LB 卸载 TLS 后透传明文 |
| **单点故障** | 引擎集群化 + Keepalived/VIP，或 LB 健康检查自动摘除 |
| **性能损耗** | 引擎无状态化 + 本地缓存判定结果 + 异步上报 |
| **真实 IP 丢失** | 透传 `X-Forwarded-For` / `X-Real-IP`，或用 PROXY protocol |
| **误伤正常用户** | 灰度 + 白名单 + 只对"高置信可疑"引流 |

### 3.4 流量判定逻辑

> 本节给出判定分支的简化视图；请求级数据流（含缓存、fail-open、幂等上报）见 §8.5。

```txt
请求进入引擎
    │
    ▼
┌─────────────────┐
│ 1. 白名单检查    │──是──► 直接透传（内部IP、健康检查）
└────────┬────────┘
         │ 否
         ▼
┌─────────────────┐
│ 2. 特征识别      │  UA、指纹、行为、频率
└────────┬────────┘
         │
    ┌────┴────┐
    ▼         ▼
 正常流量   可疑流量
    │         │
    ▼         ▼
 透传业务   投毒/引流
             │
             ▼
        ┌─────────┐
        │ 记录遥测 │──► L4 分析
        └─────────┘
```

## 四、核心与适配器架构

### 4.1 核心结论

> **不需要实现"两种能力"，而要实现"一个核心 + 可插拔的接入适配器"。**
>
> **反向代理与 Pod（Sidecar）逻辑，正是实现"零侵入"的两条正道——本质都是"基础设施层拦截 + 重逻辑外置"。**
>
> 传统环境用反向代理，云原生用 Sidecar，由接入方按环境自选。

### 4.2 核心能力 vs 接入形态

```txt
┌─────────────────────────────────────────────────────┐
│  别把"核心能力"和"接入形态"混为一谈                   │
│                                                      │
│  核心能力（只做一遍）：                              │
│    • 流量判定（识别可疑）                            │
│    • 欺骗响应生成（投毒/引流）                       │
```

### 4.4 两种接入形态对应关系

| 维度 | 反向代理（传统） | Sidecar（K8s） |
| ------ | ------------------ | ---------------- |
| 部署位置 | LB 和业务之间 | 业务 Pod 内 |
| 流量拦截点 | 七层代理 | Envoy/Istio |
| 业务改动 | 无 | 无 |
| 升级方式 | 改代理配置 | 改 CRD / 镜像 |
| 高可用 | Keepalived + VIP | K8s 原生 |
| 弹性伸缩 | 手动/脚本 | HPA 自动 |
| 适用环境 | 虚机/物理机 | 云原生 |

### 4.5 该不该两种都实现？

| 你的目标客户 | 建议 |
| -------------- | ------ |
| 只有传统虚机客户 | **只做反向代理适配器**，够用 |
| 只有 K8s 客户 | **只做 Sidecar 适配器**，够用 |
| 混合客户 / 想做成产品 | **两个都做**，但共享核心 |
| 想做成商业化产品 | 做**适配器插件体系**，让第三方扩展 |

### 4.6 适配器该多薄

```txt
适配器的职责（仅此而已）：
  1. 拦截请求
  2. 调用核心的判定接口（或读本地缓存）
  3. 按判定结果：透传 / 投毒 / 引流
  4. 异步上报遥测

适配器不该做的事：
  ✗ 不自己实现判定逻辑
  ✗ 不自己做 LLM 推理
  ✗ 不自己维护会话状态
  ✗ 不自己写入核心状态（遥测可上报，状态变更必须经核心）

→ 适配器本质是"流量搬运工"，核心才是"大脑"

第 4 条的权衡：
  优点：写入路径唯一，可全量审计与限流；适配器重启或重放不产生状态冲突。
  缺点：核心成为写入瓶颈与单点，需单独设计高可用与恢复流程；
        适配器无法依据中间结果即时调整自身行为。
```

组件级职责与工程约束见 §8.2。

### 4.7 接口设计示意（核心 ↔ 适配器）

```protobuf
// 核心暴露给所有适配器的统一接口（三个平面，清单见 §8.6）
service DeceptionJudge {
  // 判定请求是否可疑 + 返回处置动作
  // ★ 适配器侧 deadline ≤ 3ms；超时本地降级为 Action.PASS（fail-open）
  rpc Judge (JudgeRequest) returns (JudgeResponse);
}

service DeceptionTelemetry {
  // 上报遥测（异步、幂等）
  rpc Report (TelemetryEvent) returns (ReportAck);
  rpc ReportBatch (TelemetryBatch) returns (ReportAck);
}

message JudgeResponse {
  // 动作集合须完整覆盖五档决策；决策在核心内部完成，适配器只执行动作
  enum Action {
    PASS      = 0;  // 透传（对应 allow）
    OBSERVE   = 1;  // 透传 + 重点记录（对应 observe）
    CHALLENGE = 2;  // 返回挑战响应（对应 challenge）
    POISON    = 3;  // 返回投毒内容
    REDIRECT  = 4;  // 引流到蜜罐
    ISOLATE   = 5;  // 本地短路，后续同源请求不再调用核心（对应 isolate）
    BLOCK     = 6;  // 直接拒绝（对应 block）
  }
  Action action        = 1;
  string decision_id   = 2;  // ★ 幂等键：同一请求重试返回同一 decision_id
  string payload       = 3;  // 动作载荷：POISON=投毒内容；CHALLENGE=挑战参数
  string honeypot_addr = 4;  // 蜜罐地址（当 action=REDIRECT）
  uint32 ttl_seconds   = 5;  // OBSERVE / ISOLATE 的生效时长
}

// 五档决策 → 动作映射
//   allow → PASS        observe → OBSERVE     challenge → CHALLENGE
//   isolate → ISOLATE   block → BLOCK

// ★ 接口约束：
//   1. Judge 必须声明超时降级语义 = fail-open(allow)
//      核心抖动/网络分区时不得让欺骗面整体 5xx
//   2. Report 必须幂等：同一 event_id 重复上报不产生重复记录
//      适配器重启后重放未确认的遥测，不应污染数据
//   3. 冲突码语义：核心返回 409/403 时，适配器视为"该决策已失效"，
//      按 fail-open 处理，不得重试或阻塞请求
//   4. 适配器只读不写：状态变更（隔离名单、策略版本）只由核心写入
```

### 4.8 适配器开发顺序

> 与 §3.2「接入灰度节奏」是两个维度：本节讲**先做哪个适配器**，§3.2 讲**接入方何时切换到下一步**。

```txt
┌──────────────────────────────────────────────────────────┐
│ 阶段 1：先做核心 + 一个适配器                              │
│   → 选主要客户环境（传统→反向代理，K8s→Sidecar）          │
│   → 把核心逻辑打磨好，验证欺骗效果                         │
│                                                            │
│ 阶段 2：抽离适配层，做成插件接口                           │
│   → 核心与适配器之间定义清晰接口（gRPC/HTTP）              │
│   → 为第二种接入形态预留位置                               │
│                                                            │
│ 阶段 3：按需实现第二个适配器                               │
│   → 客户有需求时，写个薄适配器即可（1-2周）               │
│   → 核心完全复用，不用改                                   │
│                                                            │
│ 阶段 4：开放适配器生态（可选）                             │
│   → 提供 SDK / 文档，让接入方自己写适配器                  │
│   → 你只维护核心 + 官方适配器                              │
└──────────────────────────────────────────────────────────┘
```

## 五、开源项目调研与复用

> **核心结论：基础设施层全部复用，智能决策层全部自研，中间用胶水层连接。**

### 5.1 L1 边缘欺骗层 —— 反向代理 / API 网关

=> 说明：下表的 QPS / 延迟为调研期参考值，未附测试环境与压测方法；正式选型前需按 §11.4 自行复测。

| 项目 | 语言 | 单机 QPS | 延迟 | 扩展方式 | 适合的理由 |
| ------ | ------ | ---------- | ------ | ---------- | -------------- |
| **Nginx** | C | 12万+ | 0.8ms | Lua/模块 | 性能王者，稳定，生态最广 |
| **OpenResty** | C+Lua | 接近 Nginx | ~1ms | Lua 脚本 | **最佳选择**：内嵌 Lua，热更新欺骗策略 |
| **Envoy** | C++ | 9万 | 1.2ms | Wasm/Filter | 云原生，可做 ext_authz 外挂判定 |
| **APISIX** | Nginx+Lua+etcd | 8.5万 | 1.5ms | Lua/Go/Wasm | 动态热加载，国产活跃，插件丰富 |
| **Kong** | OpenResty | 7万 | 2.1ms | Lua 插件 | 插件生态最全，但依赖 PG |
| **Traefik** | Go | 6.5万 | 1.8ms | 中间件 | K8s 自动发现，零配置 |
| **HAProxy** | C | 极高 | 极低 | ACL | L4 负载均衡最强 |

**选型建议**：

```txt

云原生环境（K8s）      → Envoy（ext_authz 外挂判定）+ 或 Traefik
需要 API 管理能力      → APISIX / Kong
```

### 5.2 K8s Sidecar / 服务网格层

| 项目 | 架构 | 代理 | 延迟开销 | 资源/边车 | 特点 |
| ------ | ------ | ------ | ---------- | ----------- | ------ |
| **Istio** | Sidecar (Envoy) | C++ | ~2-5ms | ~128Mi | 功能最全，最复杂 |
| **Istio Ambient** | 无边车（ztunnel） | — | ~8% | 低 | 新架构，推荐新部署 |
| **Linkerd** | Sidecar (Rust) | Rust | ~1-2ms | ~20Mi | **最轻量**，最简单 |
| **Cilium** | 无边车（eBPF） | 内核 | ~0.1-0.5ms | 零 | 最低延迟，兼做 CNI |

**选型建议**：

```txt
追求简单 + 低开销     → Linkerd（Rust 代理，20Mi/边车）
已有 Cilium 作 CNI    → Cilium Service Mesh（eBPF，零边车，延迟最低）
需要高级 L7 流量治理  → Istio / Istio Ambient
```

> 对欺骗引擎而言：Sidecar 只做"轻量判定 + 引流"，因此 **Linkerd 或 Cilium 更合适**——开销小，不拖累业务 Pod。

## 七、风险与坑

### 7.1 接入层

接入层的 5 类问题与对应解决方案统一维护在 §3.3，本节不重复：HTTPS 解密、单点故障、性能损耗、真实 IP 丢失、误伤正常用户。

### 7.2 架构层

> 本节列出易踩的坑与规避方式；可强制执行的条目已转为 §十 的约束清单（含检测方法与缺失后果）。

| # | 坑 | 不可执行的做法 | 应执行的做法 | 强制约束位置 |
| --- | --- | --- | --- | --- |
| 1 | Sidecar 装重逻辑 | 把 LLM 推理、蜜罐仿真全塞进 Sidecar，拖垮业务 Pod | Sidecar 只做轻量判定 + 引流，重逻辑外置到核心与蜜罐集群 | §4.6 |
| 2 | 开源组件叠加"打架" | Istio 与 Cilium 同时争抢流量控制；多层代理叠加导致延迟累积与排查困难 | 每层只选一个组件，职责边界清晰 | §4.1 |
| 3 | 判定逻辑写两遍 | 反向代理版用 C/Lua、Sidecar 版用 Go 各实现一套判定，逻辑重复且行为不一致 | 核心唯一（判定与响应生成只写一次），适配器只做搬运 | §4.1 / §4.6 |
| 4 | 开源蜜罐直接暴露公网 | 高交互蜜罐公网裸露、无沙箱、无单向通道；开源蜜罐有可识别指纹（如 Kippo Detect） | 强隔离沙箱 + 单向数据通道 + 定期更新 | §10.1.11 / §10.1.12 |
| 5 | 复用前未核验 License | 未确认许可证即集成，被 GPL / AGPL 传染 | 逐项核验 LICENSE 与商业使用限制后再选型（见下表） | 下表 |

**License 台账（复用前必须逐项核验）**

| 组件 | License | 可否商用 | 备注 |
| --- | --- | --- | --- |
| Nginx、OpenResty | BSD | ✅ | |
| Envoy / Istio / Linkerd / Cilium | Apache 2.0 | ✅ | |
| Falco / Tetragon | Apache 2.0 | ✅ | |
| T-Pot | GPL 3.0 | ⚠️ | 传染性，二次分发需开源 |
| Beelzebub、Cowrie、OpenCanary、Canarytokens、Honeynet、HFish | ★ 待核实 | ? | §5.3 / §6.2 中拟复用的组件，尚未核验 |

核验方式：① 仓库根目录 LICENSE 与包元数据；② 是否存在 AGPL / SSPL / BSL 等限制性条款；③ 有无附加的商业授权要求或 CLA 约束。

> **AGPL 约束强于 GPL**：仅"通过网络提供服务"即触发披露义务。
> 结论：AGPL 项目的行为与设计事实可作为调研输入，**代码不得复制**；内部实现细节的复用需取得商业授权或替换为自研实现。

### 7.3 什么情况下不该用代理/Sidecar

| 场景 | 原因 | 替代方案 |
| ------ | ------ | ---------- |
| 需要业务逻辑级欺骗（如 API 越权诱捕） | 代理看不懂业务语义 | 业务内埋"蜜点"（有限侵入） |
| 极低延迟要求（如高频交易） | 多一跳不可接受 | 旁路镜像 + 异步分析 |
| 遗留系统无法改网络 | 改不了流量路径 | SDK 嵌入式（最后手段） |

**适配器职责边界**（依据 §4.6）

```txt
适配器只做四件事：
  1. 拦截请求
  2. 查本地判定缓存；未命中则调用核心 Judge（deadline ≤ 3ms，超时 fail-open）
  3. 按结果执行：透传 / 投毒 / 引流
  4. 异步上报遥测（幂等）

适配器不做的事：
  1. 不实现判定逻辑
  2. 不做 LLM 推理
  3. 不维护会话状态
  4. 不写入核心状态（遥测可上报，状态变更必须经核心）
```

### 8.4 数据模型

| 实体 | 存储 | 主键 | 关键字段 | 写入语义 |
| --- | --- | --- | --- | --- |
| decision | Redis（缓存）+ ClickHouse（归档） | `decision_id`（幂等键） | source_ip、session_id、score、signals、action、created_at | 两级去重：Redis 按 decision_id 在 TTL 窗口内去重；ClickHouse 用 ReplacingMergeTree 按 decision_id 最终去重 |
| event | ClickHouse | `event_id`（幂等键） | event_type、actor_id、session_id、payload、created_at | 只增不改，批量写入；去重同上（Redis 窗口去重 + ReplacingMergeTree 最终去重） |
| session | Redis（TTL） | `session_id` | actor_id、first_seen、last_seen、watermark_token、state | 有 TTL，过期自动回收 |
| actor | PostgreSQL | `actor_id` | 指纹、置信度、来源、画像标签、首次与最近出现时间 | 可更新 |
| decoy | PostgreSQL | `decoy_id` | 类型（API 路由 / 文件 / 凭证）、投放位置、绑定关系 | 可更新 |
| honeypot | PostgreSQL | `honeypot_id` | 协议、端口、所在节点、运行状态 | 状态与实况对账 |
| isolation | Redis（生效）+ PostgreSQL（审计） | `(kind, value)` | reason、expires_at | TTL 生效，到期自动解除 |
| policy | PostgreSQL | `(policy_id, version)` | payload、checksum、灰度比例、生效范围、回滚指针 | 版本只增，回滚即发布新版本 |
| chain | PostgreSQL | `chain_id` | 阶段、置信度、结论 | 结论写入前校验引用证据存在（§9.1.19） |
| chain_node | PostgreSQL | `(chain_id, event_id)` | 引用关系 | 只增不改，构成证据链 |

关系：

```txt
actor 1 ──< session 1 ──< event >── 1 decision
  │                          ▲
  └──< chain 1 ──< chain_node ┘        （证据引用，多对多）
decoy 1 ──< honeypot                   （蜜饵与蜜罐绑定）
policy ──► 下发至 L1 / L2 / L3          （按版本与灰度比例）
isolation ──► L1 短路判定               （命中即不再调用核心）
```

存储选型依据：

| 存储 | 承载数据 | 选择理由 | 代价 |
| --- | --- | --- | --- |
| Redis | 会话、判定缓存、限流、幂等去重 | 低延迟读、原生 TTL | 容量受内存限制；需定义持久化与丢失后的降级行为 |
| ClickHouse | 遥测事件 | 写入吞吐高、聚合查询快 | 主键去重非强一致（依赖 ReplacingMergeTree 与查询期 FINAL）；不适合频繁更新；需按时间分区与保留策略 |
| PostgreSQL | 策略、资产、画像、攻击链 | 事务与关系完整性 | 写入吞吐低于前两者，不适合承载逐请求数据 |

### 8.5 关键数据流

**链路 1：正常流量（缓存命中时不经核心）**

```txt
用户 → L0 接入（Nginx / Envoy）
     → L1 适配器：查本地判定缓存
         ├ 命中 allow → 直接透传真实业务（不调用核心）
         └ 未命中     → gRPC Judge（deadline ≤ 3ms）
                         ├ 正常返回 → 按结果处置 + 写缓存
                         └ 超时/失败 → fail-open = allow
     → 异步 Report（批量、幂等）
```

| 特性 | 说明 |
| --- | --- |
| 业务可用性 | 业务路径不依赖核心可用性；核心故障时全局降级为 allow |
| 延迟开销 | 缓存命中时无网络跳转；未命中时增加一跳 gRPC |
| 风险 | fail-open 期间判定能力下降，攻击窗口等于核心恢复时间 |

**链路 2：可疑流量（投毒 / 引流）**

```txt
请求 → L0 接入 → L1 适配器
     ├ 命中隔离名单 → 直接短路（不再调用核心）
     └ 未命中 → Judge，按返回的 7 种 Action 之一执行（§4.7）：
         ├ PASS / OBSERVE → 透传（OBSERVE 额外重点记录）
         ├ CHALLENGE      → 返回挑战响应
         ├ POISON         → 改写响应体（内容由核心生成并过黑名单校验）
         ├ REDIRECT       → 改写转发目标至蜜罐地址
         ├ ISOLATE        → 本地短路并按 ttl_seconds 记录
         └ BLOCK          → 直接拒绝
     → 记录 event（携带 decision_id，幂等）
     → 高风险决策触发告警
```

> Redis 不可用时的降级：隔离名单读不到即回退到调用核心判定（fail-open，不阻断业务）；隔离能力暂时失效需计入告警。

**链路 3：攻击者与高交互蜜罐交互（多轮）**

```txt
被引流流量（链路 2 的 REDIRECT）或直连 → L2 协议仿真蜜罐（Go / Rust）
       → 会话建立：签发 session_id + 会话水印令牌
       → 多轮交互：
           ├ 快路径：规则与模板响应（毫秒级，蜜罐进程内完成）
           └ 慢路径：LLM 会话仿真（经 gRPC/HTTP 调用 Python 组件，规范见 §九）
               ├ 阶段 1 执行（超时 T1）
               └ 超时 / 解析失败 → 阶段 2 同会话收尾（超时 T2）
                                   └ 两阶段均失败 → 整体作废，不写半成品
       → 逐命令转录、凭证捕获、文件投递写入 event
       → 会话结束 → 归档（保留策略见 §10.1.14）
```

**链路 4：遥测 → 分析 → 策略回写**

```txt
event（ClickHouse）
  → 触发分析（按态势去重：仅当新增证据数达阈值或攻击阶段跃迁）
  → L4 分析决策（Python）
      ├ 意图识别
      ├ 攻击链还原 → 结论引用须校验 event 存在性（§9.1.19）
      └ 策略生成 → policy 新版本
  → 控制面审核（可选）
  → 按灰度比例下发：L1 / L2 / L3 通过 Policy.Pull / Watch 获取
  → 各层回执写入审计
```

| 特性 | 说明 |
| --- | --- |
| 触发去重 | 避免每次事件写入即重算，控制 LLM 成本 |
| 灰度 | 策略按比例生效，可回滚至任意历史版本 |
| 风险 | 策略版本与各层实际生效版本不一致时行为不可预期，需回执对账 |

### 8.6 接口契约

| 平面 | 服务 | 方法 | 幂等键 | 超时与降级 |
| --- | --- | --- | --- | --- |
| 判定面 | DeceptionJudge | Judge | decision_id | deadline ≤ 3ms；超时 fail-open = allow |
| 遥测面 | DeceptionTelemetry | Report / ReportBatch | event_id | 适配器侧仅做受限长度的尽力转发，不阻塞请求路径；可靠重放由核心侧接收缓冲 + 落库补偿承担 |
| 策略面 | DeceptionPolicy | Pull / Watch / Ack | (policy_id, version) | 拉取失败沿用本地缓存版本 |

```protobuf
// 判定面与遥测面见 §4.7；此处补充策略面
service DeceptionPolicy {
  rpc Pull  (PolicyPullRequest)  returns (PolicySnapshot);      // 全量拉取
  rpc Watch (PolicyWatchRequest) returns (stream PolicyDelta);  // 增量订阅
  rpc Ack   (PolicyAck)          returns (PolicyAckReply);      // 回执（审计用）
}

message PolicySnapshot {
  string policy_id = 1;
  uint64 version   = 2;   // 单调递增；回滚即发布新版本
  bytes  payload   = 3;   // 适配器可直接消费的策略体
  string checksum  = 4;   // 完整性校验
}
```

契约约束：

| 约束 | 依据 |
| --- | --- |
| 契约以 `api/` 为唯一事实源，文档由定义生成 | §10.1.7 |
| 判定面不在对外响应中回显分值、规则名、决策枚举 | §10.1.3 |
| 策略面必须携带版本号与校验和，支持回滚 | §8.5 链路 4 |
| 遥测面幂等：同一 event_id 重复上报不产生重复记录 | §4.7 |
| 判定面未命中缓存时才调用；适配器侧必须实现超时降级 | §8.5 链路 1 |
| decision_id 由适配器按（来源标识, 会话, 路径, 时间窗）派生并随请求传入；核心在响应中原样回传，重试复用同一 ID | §4.7 |

### 8.7 部署拓扑与进程边界

**传统虚机形态**

```txt
用户 → LB → OpenResty（含 L1 插件）─┬─► 真实业务集群（不经核心）
                                     └─► 蜜罐集群（引流目标）
        核心集群（无状态 × N） ← gRPC ─ L1 插件 / 适配器
        Redis · ClickHouse · PostgreSQL
```

**K8s 形态**

```txt
用户 → Gateway / Ingress（Envoy）
         └─► 业务 Pod（含 Sidecar 适配器）→ 真实业务容器
         └─► 蜜罐 Deployment / StatefulSet（协议仿真，按需扩副本）
        核心 Deployment（无状态 × N）
        Cilium（微隔离 + 网络策略）· Tetragon（运行时检测）
        Redis · ClickHouse · PostgreSQL（Operator 管理）
```

**进程边界**

| 组件 | 进程形态 | 边界约束 |
| --- | --- | --- |
| L1 适配器 | 与代理同进程（Lua / Wasm） | 不得引入阻塞调用；不得持有跨请求的**业务**状态（判定缓存与策略缓存为例外，须有容量上限与失效规则） |
| 核心 | 独立进程，无状态多副本 | 进程内无模块级可变容器（§10.1.1） |
| 分析决策 | 独立进程（Python） | 按任务队列并发，不直接写判定缓存 |
| 蜜罐 | 每协议独立进程 / 容器 | 连接数与线程数设上限（§10.2.8）；启停资源对称回收（§10.1.10） |
| 控制台 | 独立进程 | 以只读为主，写操作走策略平面并留审计 |

**部署形态对比**

| 形态 | 适用 | 优势 | 代价 |
| --- | --- | --- | --- |
| 传统虚机 + OpenResty | 存量虚机 / 物理机站点 | 业务改造仅追加代理配置；无容器依赖 | 弹性伸缩需自建；高可用依赖 VIP 或 LB 健康检查 |
| K8s + Sidecar / Gateway | 云原生微服务 | 弹性与自愈由编排系统提供 | 增加一层代理开销；需处理 Sidecar 与业务容器的资源竞争 |
| 混合 | 迁移过渡期 | 可分批接入 | 跨环境通信需统一 gRPC over mTLS；运维面翻倍 |

### 8.10 非功能指标

| 指标 | 目标值 / 约束 | 说明 |
| --- | --- | --- |
| 适配器判定耗时（缓存命中） | ≤ 1 ms | 与代理同进程，无网络跳转（§8.5 链路 1） |
| Judge RPC deadline | ≤ 3 ms | 超时本地降级 fail-open = allow（§4.7） |
| 业务路径额外延迟（P99） | ≤ 5 ms | 构成：缓存查询 ≤ 1 ms + Judge ≤ 3 ms + 本地处置 ≤ 1 ms；相对未接入前。超预算则回退到旁路镜像（§3.1 方式 1） |
| 核心可用性 | 核心故障不阻塞业务 | fail-open 降级窗口 = 核心恢复时间，期间判定能力缺失 |
| 隔离生效延迟 | 本适配器即时（随 Judge 响应生效）；其他适配器 ≤ 1 s | 本地短路即时；跨适配器传播依赖名单缓存的刷新周期 |
| 策略下发延迟 | ≤ 30 s | Policy.Watch 增量订阅；回执用于版本对账（§8.6） |
| 遥测写入 | 异步批量；单批 ≤ N 条，核心侧接收缓冲上限 M 条 | 适配器侧不承担持久缓冲（Lua/Wasm 环境不适合）；缓冲溢出时的丢弃策略需显式定义，建议按决策风险优先级保留 |
| 蜜罐并发连接 | 按协议分别设上限，超限即拒绝并记录 | 禁止无上限创建线程或事件循环（§10.2.8） |
| 判定缓存容量 | 按活跃缓存键数估算（键 = 来源标识 / 会话 / 路径 的组合），超出按 LRU 淘汰 | 未命中率上升会线性放大 RPC 调用量，需纳入监控 |
| 事件保留 | 按数据类型分别配置（事件 30 / 心跳 7 / 登录 90 / 会话转录 60 天） | 见 §10.1.14 |
| LLM 调用量 | 由态势去重后触发，不随事件写入量线性增长 | 去重规则见 §8.5 链路 4 |
| 存储容量 | ClickHouse 按天分区 + 保留策略 | 容量 ≈ 事件量 × 保留天数，按接入站点数预估 |

> N、M 及各协议连接上限等具体数值需在压测阶段实测确定；本表固定的是**指标项与约束关系**，不预设未经验证的数字。

> **适用范围**：L2 高交互欺骗层的会话仿真与响应生成、L4 分析决策层的意图识别与策略生成、话术与模板生成。
> **记录格式**：仅记录两类信息 —— 「应执行的具体做法」与「不可执行的具体做法」；每条记录给出具体实施内容、优点、缺点。

### 9.1 应执行的具体做法

| # | 做法 | 具体实施内容 | 优点 | 缺点 / 代价 |
| --- | --- | --- | --- | --- |
| 9.1.1 | **契约层与提示词分离** | 提示词只描述任务与上下文；输出结构由独立代码层校验。校验失败抛异常，不返回 `None`、不返回默认值、不静默降级 | 契约可单元测试、可版本化；提示词改写不影响校验逻辑；模型输出偏差时调用方被迫走显式失败分支 | 校验层与提示词需同步演进，二者不一致时表现为"模型持续失败"；增加一次解析与字段校验开销 |
| 9.1.2 | **统一响应包裹层** | 所有 LLM 输出统一为 `{"accepted": bool, "data": {...}}`；`accepted=false` 走独立分支并记录拒绝原因 | 正常路径与拒绝路径分离；拒绝原因可统计；下游只需处理一种外层结构 | 多一层解包；模型偶发省略外层字段时需额外兼容分支 |
| 9.1.3 | **契约保留兼容点** | 新字段为主，旧字段名保留为回退解析分支 | 契约演进不会使存量部署立即失效；支持灰度切换 | 兼容分支长期累积形成隐式契约；需为每个兼容分支标注引入版本与废弃期限 |
| 9.1.4 | **生成结果数量硬截断** | 策略列表、意图列表等字段超过配置上限时直接截断；截断数量写入日志与事件字段 | 防止单次输出生成大批条目压垮判定缓存、策略下发与查询 | 截断静默发生，上游若不自报数量会丢失"已被截断"这一事实，必须显式记录截断数 |
| 9.1.5 | **三段式 JSON 提取** | ① 整段按 JSON 解析；② 从 markdown 代码围栏内提取；③ 对每个 `{` 位置尝试 `raw_decode` | 容忍模型在 JSON 前后夹带自然语言与 markdown 围栏；单段 `json.loads` 在真实链路上失败率高 | 第 ③ 段逐 `{` 尝试，超长输出下最坏 O(n²)；须设最大扫描位置上限或改为括号配平扫描 |
| 9.1.6 | **双阶段执行 + 收尾** | 阶段 1 执行（超时 T1）；超时或解析失败后进入阶段 2，**复用同一会话**执行收尾（超时 T2） | 任务超时不等于任务失败；可抢救部分成果，避免整轮算力与上下文浪费 | 单任务最坏耗时变为 T1+T2；收尾产出的完整度低于正常阶段；依赖会话可恢复能力 |
| 9.1.7 | **收尾提示词限定范围** | 收尾提示词显式声明"不继续推进、不等待未完成任务、只总结已完成部分" | 防止模型重新执行主任务导致二次超时，避免超时—重试—再超时的长尾 | 提示词约束强度依赖模型遵从度，弱模型仍可能继续探索；需在超时上兜底 |
| 9.1.8 | **收尾阶段跳过前置检查** | 进入收尾阶段时跳过程序性前置步骤（健康检查、权限探测等），直接执行 | 收尾路径最短；任何额外前置失败都会直接导致已有成果丢失 | 前置条件在收尾期间失效时（如凭据过期）会得到一次无意义失败，须接受该失败并走最终作废分支 |
| 9.1.9 | **收尾阶段使用独立契约** | 收尾阶段的输出结构只允许"事实"类字段，不包含"完成 / 成功"类字段 | 收尾阶段不承担目标达成判定，避免部分成果被误判为完整结论 | 需为两类阶段定义不同 schema，契约维护量增加一倍 |
| 9.1.10 | **失败即整体作废** | 两阶段均失败时不写入任何中间数据，并释放已占用的标记（认领、租约） | 不产生半成品污染遥测与策略存储；下游无需处理不完整记录 | 已消耗算力无法回收；长任务重试成本高，须另行设定重试上限与放弃条件 |
| 9.1.11 | **会话差异收敛到模板方法** | 基类负责编排（执行 / 收尾 / 解析 / 超时），子类只实现 1~2 个方法（会话预生成，或从输出中正则提取） | 新增一种协议仿真或推理后端只需实现少量方法；共性逻辑单点维护 | 差异过大的后端会被迫写适配层或绕过基类，导致模板方法退化；继承层级增加调试成本 |
| 9.1.12 | **会话标识显式化** | 会话 ID 作为任务上下文的一等字段传递，在会话建立、心跳、收尾三个阶段保持一致 | 多轮欺骗上下文可追踪；超时后可按 ID 恢复；会话与攻击者行为可关联审计 | 需后端支持按 ID 续跑；不支持的后端只能退化为单阶段模式 |
| 9.1.13 | **话术与模板资源启动期校验** | 启动时扫描并校验仓库内话术模板、策略文件是否存在、占位符是否齐全 | 资源缺失与占位符缺失在启动期暴露，而非首次欺骗请求时暴露 | 启动耗时增加；资源清单需与代码同步维护，新增资源须同步登记 |
| 9.1.14 | **启动期断言关键周期关系** | 启动时断言两条关系，不满足即启动失败：① 判定超时 ≤ 业务路径延迟预算（§8.10）；② 心跳 / 租约周期 > 遥测采集上报周期 | 时序配置错误立即暴露；避免"租约先于上报过期"或"判定超时突破延迟预算"这类仅在运行期体现的失效 | 运维调整单个周期参数时受约束，需同步调整其他参数 |
| 9.1.15 | **话术模板随代码分发 + 组切换** | 话术与提示词作为代码仓库内资源文件，通过配置项选择模板组，运行时按组加载 | 模板可 diff、可评审、可回滚；部署版本与可回滚版本一致 | 模板修改需走发布流程，无法运行期热改；资源须打包进发布物 |
| 9.1.16 | **欺骗链路端到端测试** | 以进程内测试客户端 + 模拟攻击者驱动，跑通判定 → 投毒 / 引流 → 遥测 → 策略回写全链路，含五档决策分支 | 覆盖跨模块协作路径；不依赖真实攻击流量，可纳入 CI 快速回归 | 需维护模拟攻击者与测试夹具；真实环境特有行为（真实代理、真实蜜网）不在覆盖范围内 |
| 9.1.17 | **蜜罐进程与文件边界专项测试** | 用假可执行文件启动真子进程，测试进程组回收与超时；对蜜饵文件分发做路径穿越专项测试 | 覆盖进程与文件系统边界，此类缺陷在纯模拟测试中不可见 | 测试执行时间与资源占用高于纯单测；跨平台行为差异需额外处理 |
| 9.1.18 | **生成内容黑名单校验** | 对 LLM 生成内容做规则校验，至少覆盖三类：泄露类（内网地址、真实主机名、真实文件路径、真实业务标识）、自曝类（"我是 AI"、"这是蜜罐"、"作为语言模型"）、超长类 | 阻断内容型风险，不依赖模型自身遵守；规则可审计、可单元测试 | 黑名单不可能完备；规则过严会误杀合法输出，需保留灰度与人工复核通道 |
| 9.1.19 | **引用可验证性校验** | 生成结论若引用证据 ID，须在写入前校验该 ID 真实存在于遥测存储中 | 阻断无依据的关联，防止编造数据进入攻击链与策略存储 | 增加一轮批量存在性查询；证据在生成期间被清理时会产生合法失败，需定义该情形下的处理策略 |
| 9.1.20 | **输出长度分级上限** | 按用途设定不同的最大长度：面向攻击者的会话响应、面向存储的结论、面向分析的中间产物各自独立上限 | 防止单次输出撑爆蜜罐连接、取证存储或控制台渲染；上限可按用途独立调整 | 上限设置需要实测依据；过低会导致合法输出被截断，需配套截断告警 |

### 9.2 不可执行的具体做法

| # | 做法 | 具体表现 | 可观察到的优点 / 适用条件 | 存在的缺点 |
| --- | --- | --- | --- | --- |
| 9.2.1 | **契约只写在提示词里** | 提示词中声明"请返回如下 JSON"，代码侧直接解析，不做字段校验 | 实现成本低，无额外代码；仅适用于一次性原型验证 | 提示词与解析逻辑无强绑定，任一侧改动即静默失效；模型偏差直接污染下游；无法单元测试 |
| 9.2.2 | **校验失败静默降级** | 解析失败返回空字典或默认值，调用方无感 | 避免异常中断主流程；对确实非关键的字段可容忍 | 失败不可观测，问题被推迟到更下游；无法统计失败率；无法区分是模型问题还是契约问题 |
| 9.2.3 | **无上限接受列表字段** | 直接接受模型返回的任意长度策略、意图列表并全部写入 | 不丢数据 | 单次输出即可写入大量条目，压垮判定缓存与策略下发；限流若放在上层则代价更高 |
| 9.2.4 | **超时后直接丢弃整轮结果** | 超时即终止会话、不写入任何数据、不进入收尾 | 实现简单、语义清晰、无额外分支 | 已完成的欺骗上下文与推理结论全部浪费；长任务重试成本高 |
| 9.2.5 | **收尾阶段重新执行完整任务** | 超时后重新下发原任务，期望本次执行完成 | 若本次成功则产出完整成果 | 大概率二次超时，形成超时—重试—再超时的长尾；总耗时不可预测，无法设定稳定的对外时延 |
| 9.2.6 | **收尾阶段可写"完成"信号** | 收尾输出与正常输出共用 schema，允许返回完成标记 | 无需为两个阶段维护不同 schema | 部分成果被误判为结论完整，攻击链进入错误终态；纠错需人工介入 |
| 9.2.7 | **失败时保留部分写入** | 两阶段均失败但保留阶段 1 的部分写入 | 保留全部已获得的信息，不做丢弃 | 下游需处理不完整记录；遥测与策略存储出现无法判定完整性的条目；对账逻辑复杂度上升 |
| 9.2.8 | **话术模板运行期可任意修改** | 话术存放于可变存储，运营可直接修改，与代码版本无绑定 | 运营灵活，改文案无需发版 | 线上行为与代码版本解耦，故障无法按版本回滚；变更不可评审、不可 diff；多实例间内容可能不一致 |
| 9.2.9 | **时序关系仅写在文档中** | 只在文档说明周期关系，代码不做校验 | 实现简单，不限制运维调参 | 配置错误仅在实际运行中体现，且表现为静默失效而非报错，定位成本高 |
| 9.2.10 | **只测主路径** | 测试仅覆盖成功返回，不覆盖超时、解析失败、拒绝、五档决策边界 | 测试编写速度快 | 异常路径无回归保护，重构即失效；而异常路径是生产事故的主要来源 |
| 9.2.11 | **在异步框架中执行同步阻塞 I/O** | 异步请求处理函数内直接执行同步数据库、网络或 LLM 调用 | 可直接复用同步代码与既有驱动，无需异步化改造 | 阻塞事件循环，并发无法转化为吞吐；须在同步框架中实现或改为异步驱动才能解除 |

## 十、运行时与安全约束

> **适用范围**：引擎核心、接入适配器、协议蜜罐、部署单元。
> **记录格式**：仅记录两类信息 —— 「应执行的具体做法」与「不可执行的具体做法」；每条记录给出具体实施内容、优点、缺点。

### 10.1 应执行的具体做法

| # | 约束 | 具体实施内容 / 检测方法 | 优点 | 缺点 / 成本 | 缺失后果 |
| --- | --- | --- | --- | --- | --- |
| 10.1.1 | **核心状态外置** | 核心进程内不存在模块级可变容器；会话、隔离名单、策略版本统一存放于外部存储 | 可水平扩展；进程重启不丢状态；多副本行为一致 | 每次状态读写需跨进程调用，延迟高于内存访问；需引入外部存储及其高可用 | 多副本状态不一致或功能冲突，无法扩容 |
| 10.1.2 | **密钥与口令无默认值** | 密钥、口令类配置项无默认值；缺失时进程启动失败并给出明确错误 | 杜绝默认凭据进入生产；配置缺失在部署阶段即暴露 | 首次部署与本地调试需额外准备配置步骤 | 默认凭据被直接用于生产，形成未授权访问入口 |
| 10.1.3 | **不回显内部判定信息** | 对外响应头与响应体中不出现风险分值、规则名、决策枚举 | 调用方无法依据响应反向调优以规避判定 | 问题排查需依赖服务端日志，无法从客户端响应直接判断 | 攻击方可迭代调整请求特征以压低分值，判定失效 |
| 10.1.4 | **出网默认拒绝** | 克隆、抓取、回调类能力配置目标白名单；私网地址段与云元数据地址默认阻断，并有单元测试覆盖 | 服务端请求伪造面收敛到白名单内 | 新增外呼目标须走白名单变更流程，灵活性下降 | 服务端可被诱导访问内网或云元数据地址 |
| 10.1.5 | **判定阈值集中管理** | 判定阈值、隔离有效期、去重窗口集中在一处定义，且可由配置覆盖 | 阈值调整一处生效；可对不同环境使用不同阈值 | 集中定义处成为热点文件，并发修改易冲突 | 阈值散落各处，调整时遗漏部分位置，行为不一致 |
| 10.1.6 | **判定规则单测覆盖** | 每条判定规则至少有一个正样本与一个负样本用例（含伪造 UA、补齐人类请求头的绕过样本） | 重构具备回归保护；判定阈值可安全调整 | 测试编写与维护占用开发工时；样本需随规则演进同步更新 | 判定阈值不可调整（调整即风险），规则长期不敢优化 |
| 10.1.7 | **接口契约单一事实源** | 判定、遥测上报、策略回写的 schema 只有一处定义；对外文档由该定义生成 | 契约变更一处生效，文档与实现不会偏离 | 需引入代码生成或校验环节 | 多处并行维护的契约出现漂移，表现为"文档与实现不一致" |
| 10.1.8 | **子进程按进程组回收** | 蜜罐与协议仿真子进程启动时创建独立进程组；超时后先发 SIGTERM，宽限后发 SIGKILL，并按进程组终止 | 子进程派生的孙进程一并回收，不留残留进程 | 需处理信号时序与宽限期；跨平台信号语义存在差异 | 超时后仅终止直接子进程，孙进程残留并持续占用资源 |
| 10.1.9 | **双层超时** | 外层 watchdog 超时 + 内层执行体级超时（如容器内 `timeout -k`）双重设置，内层略短于外层 | 外层失效时内层仍能终止；两层互为兜底 | 两层超时值需协调设置，不当组合会导致内层先杀导致无法取得输出 | 单一超时失效（如进程不响应信号）时任务永久挂起 |
| 10.1.10 | **蜜罐资源创建与释放对称** | 启动监听端口、事件循环、线程时登记；停止时按登记逆序回收；资源清理在独立线程池执行，不阻塞主循环 | 反复启停不累积泄漏；主循环节奏稳定 | 资源台账需额外维护；进程退出时未完成的清理需下次启动补偿 | 反复启停后线程与事件循环持续累积，最终耗尽资源 |
| 10.1.11 | **高风险能力不在同一部署单元叠加** | 容器运行时套接字挂载、宿主网络模式、免密提权、无沙箱本地执行模式，四者不得同时出现在一个部署单元中，CI 中做组合检查 | 单点被突破后的影响范围被限制在单层 | 部署架构复杂度上升，可能需要拆分多个部署单元 | 多层高风险能力叠加后，单点突破即获得宿主级权限 |
| 10.1.12 | **无沙箱执行模式显式标注** | 以宿主权限运行蜜罐或执行体的模式，在配置项、启动日志、文档中均显式标注；启动时输出权限提示 | 使用者对被授予的权限范围有明确认知 | 需要额外的标注与提示维护成本 | 使用者误以为存在隔离，将不可信负载投入无沙箱模式执行 |
| 10.1.13 | **敏感配置不落仓库** | 含密钥的配置文件加入忽略清单；配置模板中只保留占位符 | 密钥不会随代码分发 | 新环境部署需手动补全配置；模板与真实配置存在漂移风险 | 密钥进入版本历史，泄露后需全量轮换 |
| 10.1.14 | **取证数据保留策略可配置** | 按数据类别（事件、会话转录、凭证、登录日志）分别配置保留天数；启动时执行一次清理并启动周期性清理 | 存储增长可控；合规留存期限可配置 | 清理逻辑需与查询逻辑协调，避免读到已清理数据的引用 | 存储持续增长直至耗尽磁盘；含敏感信息的历史数据长期保留 |
| 10.1.15 | **健康检查与就绪检查分离** | 存活探针只反映进程存活；就绪探针反映依赖（遥测存储、策略存储）可用 | 依赖故障时不会误杀进程；编排系统可正确摘除流量 | 需维护两套探针及其阈值 | 依赖故障被误判为进程故障，触发重启循环 |
| 10.1.16 | **日志按状态变化输出** | 稳定轮询、正常心跳、重复跳过按降噪处理；状态跃迁、决策变更、失败、超时按事件输出 | 日志量可控，关键事件不被淹没；便于按状态变化做告警 | 需维护"上次状态"缓存与比较逻辑；降噪规则不当会漏掉重要中间状态 | 日志被周期性输出淹没，故障时无法快速定位状态变化点 |

### 10.2 不可执行的具体做法

| # | 做法 | 具体表现 | 可观察到的优点 / 适用条件 | 存在的缺点 |
| --- | --- | --- | --- | --- |
| 10.2.1 | **用进程内全局状态承载业务数据** | 蜜罐运行时注册表、部署表、隔离缓存等以模块级字典维护 | 读取零延迟、实现简单；单进程单副本演示场景下可用 | 无法水平扩展；进程重启丢状态；多副本行为冲突；难以测试 |
| 10.2.2 | **默认凭据随部署模板分发** | 容器编排模板、部署脚本中内置默认口令与默认密钥 | 开箱可用，降低首次部署门槛 | 默认凭据极易进入生产；部署脚本打印默认口令会进入日志与终端历史 |
| 10.2.3 | **判定与上报接口无幂等设计** | 重复调用即重复写入遥测或重复下发策略 | 实现简单、写入路径短 | 适配器重试与重放产生重复数据，攻击链口径失真，需额外对账 |
| 10.2.4 | **读取接口执行写操作** | 列表、详情、导出等读取接口内部执行过期清理等写入 | 省去独立清理任务 | 读取接口不再幂等；并发读产生写竞争；读压力放大写压力 |
| 10.2.5 | **异常静默吞没** | 使用空 `except` 或不记录日志的异常捕获 | 避免异常向上传播导致中断；对确实可忽略的清理操作可接受 | 故障不可观测，问题在下游以无关形式出现；无法统计错误率 |
| 10.2.6 | **路径校验使用字符串包含判断** | 以"目标路径包含根路径字符串"判断是否越界 | 实现一行代码即可完成 | 同前缀的兄弟目录可绕过校验，越权读取目录外文件（蜜饵分发作攻击面） |
| 10.2.7 | **上传接口无体积上限** | 一次性读取完整请求体到内存后再落盘 | 实现简单，无需流式处理 | 大体积请求可直接耗尽进程内存（蜜饵文件上传作攻击面） |
| 10.2.8 | **监听与连接线程无上限** | 协议蜜罐每连接创建一个线程且不设并发上限 | 实现简单，无需连接管理 | 连接数增长即耗尽线程资源，形成拒绝服务 |
| 10.2.9 | **创建的资源缺少对称释放** | 启动监听时创建事件循环或线程，停止时只关闭监听套接字，不回收循环与线程 | 停止操作响应快 | 反复启停后线程与事件循环持续累积，最终耗尽资源 |

## 附录 A：术语速查

| 术语 | 含义 |
| --- | --- |
| L0 接入层 | 流量入口（代理 / 网关 / LB），负责 TLS 卸载与流量分发，直接复用开源组件 |
| L1 边缘欺骗层 | 代理内嵌的**处置**插件（Lua / Wasm）：按核心判定结果执行投毒、假路径、引流；不实现判定逻辑 |
| L2 高交互欺骗层 | 协议仿真蜜罐与 LLM 多轮会话，承接已识别的可疑流量 |
| L3 网络欺骗层 | 蜜网编排、微隔离、假拓扑（Cilium / Tetragon） |
| L4 分析决策层 | 意图识别、攻击链还原、策略生成（Python） |
| 核心 | 判定与响应生成的唯一实现，无状态多副本，经 gRPC 对外提供服务 |
| 适配器 | 接入形态的薄封装（反向代理 / Sidecar / SDK），只做拦截、查缓存、处置、上报 |
| 判定（Judge） | 对单次请求给出风险分值、信号列表与处置动作 |
| 五档决策 | 核心内部的风险分级：allow / observe / challenge / isolate / block；执行时映射为 JudgeResponse 的 7 种 Action（见 §4.7） |
| 投毒（POISON） | 向可疑方返回伪造或误导性内容 |
| 引流（REDIRECT） | 把可疑流量转发至蜜罐 |
| 蜜饵 | 投放给攻击者的诱饵资产（假 API 路由 / 假文件 / 假凭证） |
| 蜜标（Canary Token） | 可回显追踪的令牌，被回显即判定为自动化客户端 |
| 会话水印 | 嵌入蜜罐会话的标识；凭证被复用时回溯到具体会话 |
| 隔离（Isolate） | 对来源 IP 或会话在 TTL 内短路判定，不再调用核心 |
| 幂等键 | decision_id / event_id / (policy_id, version)，用于重试与重放去重 |
| 态势去重 | 仅当新增证据达阈值或攻击阶段跃迁时才触发 L4 重算 |
| fail-open | 判定不可用时默认放行（allow），业务可用性优先 |
| 契约（Contract） | LLM 输出的结构与内容约束，由独立代码层校验，与提示词分离 |
| 核心状态 | 隔离名单、策略版本、会话归属等需唯一写入方的数据 |
| 控制面 | 策略编排、蜜饵资产管理、人工干预与审计的集合，不参与请求级判定 |
| 数据面 | 核心运行所依赖的存储集合（Redis / ClickHouse / PostgreSQL） |
| 欺骗执行面 | 实际产生欺骗效果的组件集合（L1 处置模块、L2 蜜罐、L3 网络策略） |

---

## 附录 B：一句话总结

> **没有"最好的一种语言"，只有"最适合每层的语言"：**
> 边缘用 Lua/Rust，协议用 Go/Rust，AI 用 Python，底座用 Rust；跨层用 gRPC/Protobuf 粘合。
>
> **Web 服务接入的推荐路径是"透明引流"：**
> 旁路镜像（零风险观察）→ 反向代理前置（主动欺骗）→ Sidecar/Ingress（弹性高可用），核心是业务零改造。
>
> **不需要实现"两种能力"，而是"一个核心 + 可插拔的接入适配器"：**
> 核心只写一遍，接入形态做成薄适配层，由接入方按环境自选。
>
> **基础设施层全部复用开源，智能决策层全部自研，中间用胶水层连接：**
> 复用的 70-80% 负责"接得住、骗得真、困得住"，自研的 20-30% 负责"看得懂、想得深、变得快"。

> **LLM 输出不可直接信任，契约层必须与提示词分离：**
> 三段式容错提取；超时后以同一会话收尾救回部分成果；两阶段均失败即整体作废，不写半成品；
> 生成内容须过黑名单（不泄露真实信息、不自曝蜜罐）。

> **约束必须自带检测方法：**
> "核心状态外置""密钥无默认值""禁止回显判定""出网默认拒绝""启动期断言关键周期关系"
> —— 每条均给出可执行的检测手段，缺失后果明确。
