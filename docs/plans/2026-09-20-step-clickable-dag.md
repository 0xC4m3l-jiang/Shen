## 1. 需求与验收

**用户要什么**：DAG 图**每一步都能点开**，看到该步对应的**请求信息**、**返回（响应）信息**、以及**为什么会执行到这一步**（分析/依据），方便整理哪儿要优化。

**验收判据**：

1. 链路里每一步（节点）可点，点开显示三段：请求 / 响应 / 为什么；
2. 三段里写的是**这条请求**的具体值（不是模板话术），并说明依据与约束（规则匹配、影子模式、回落、缓存、白名单等）；
3. 点步与点卡片不互相打架（点步只出步详情，点卡片出四段详情）；
4. 数据随链路接口一起返回，点开**不再发请求**（一屏内逐条排查不产生 N+1）；
5. `make gate` 绿。

**不做什么**：不改契约与适配器 · 不引入前端库 · 不做实时推送。

---

## 2. 设计逻辑

| # | 问题 | 决定 | 理由 |
| --- | --- | --- | --- |
| ① | 三段的文案从哪来 | 后端在逐请求链路里**逐步生成**（`ChainNode.request/response/why`） | 依据（规则/约束/取舍）属于业务语义，放前端会漂 |
| ② | 点开要不要再请求 | **不请求**：三段随 `/api/graphs` 一起下发 | 一屏几十条请求，逐步再查会产生 N+1 |
| ③ | 为什么的写法 | 写明**依据 ID**（AR-2/AR-6/AR-7/NI-1/NI-3/NI-5/INT-8/INT-11/INT-25/ST-10）与已知取舍（K-20/K-24） | 让人能顺着规则去查，而不是只看到一句解释 |
| ④ | 点击冲突 | 步点击 `stopPropagation()`，卡片空白处仍出整条详情 | 两种粒度共存，互不干扰 |

## 3. 追溯矩阵

| 规则/取舍 | 在"为什么"里的落点 |
| --- | --- |
| AR-2 / AR-7 | 客户端与适配器两跳：判定只在核心，适配器只执行处置 |
| AR-6 | 适配器四件事的顺序（白名单 → 缓存 → 调核心 → 异步上报） |
| INT-25 | 白名单跳：内部探针/健康检查必须在引流判定前放行 |
| ST-10 / K-20 | 缓存跳：判定键与"同窗谁先到谁定调"的取舍 |
| NI-3 / NI-4 / K-24 | 判定失败跳：业务优先于观测，该条没有判定记录 |
| INT-11 | 决策跳与源站跳：影子模式只算不执行 |
| INT-8 | 源站跳：业务响应原样透传，注入只在改道侧 |
| NI-1 / NI-5 | 回落跳：宁可漏改道，不可断业务 |
| AR-12 / AR-14 | L4 跳：引用必须真实存在；不在请求路径上 |

| # | 场景 | 期望 | 实测 |

```console
$ curl -s "http://127.0.0.1:19444/api/graphs?limit=20"   # 取探针那条

     为什么: 决策可能是放行，也可能是改道/拦截但**影子模式**不执行（INT-11）

$ make gate
门禁通过。
```
