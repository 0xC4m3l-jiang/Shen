# docs/plans —— 实施计划

> **效力等同 [`../background/notes/`](../background/notes/)：待确认的提案，不作实现依据。**
> 其中的**决定**经用户确认后才升格到 [`../design/`](../design/README.md)（升格流程见 [`../../AGENTS.md`](../../AGENTS.md) §3.1）。
>
> ⚠️ **本目录不是需求文档，也不是设计文档。** 它记录的是「访谈问出了什么、打算怎么做」，
> 是开发循环第 ① 段（设计访谈）的产物。见 [`../../AGENTS.md`](../../AGENTS.md) §4。

## 目录策略（2026-09-20 起）

**已实现并验证的变更包不再单独留文件** —— 归档为 [`ARCHIVE.md`](ARCHIVE.md) 里的一行（含日期 · 主题 · 状态 · 追溯入口），
原文仍可取回（`git show <提交>:docs/plans/<原文件名>`）。本目录只保留：**未实现/待确认**的变更包 · 模板 · 归档表。

## 怎么读（历史说明）

**每轮开发一份**，是**历史留痕**（追溯用），不是需要通读的文档：

- **想知道当前状态** → [`../progress.md`](../progress.md)（完成度唯一维护处）+ [`../log.md`](../log.md)（每轮一条，最新在最上）；
- **想复核某一轮改了什么** → 按日期找本目录对应那份（含追溯矩阵与证据）；
- **想读懂整体逻辑** → [`../logic.md`](../logic.md)，不需要翻计划；
- 旧计划**不删除**：`docs/log.md` 的历史条目引用它们，删了会造成悬空引用（门禁会拦）。

## 这里放什么

开发循环第 ① 段（设计访谈）之后的实施计划。每份计划来自一次访谈，包含：

| 要素 | 说明 |
| --- | --- |
| 决策树 | 这次要定哪些事，彼此的依赖关系 |
| 已定的决定 | 用户已经答过的 |
| **仍未定的** | 明确标出 —— 它们**阻塞**对应部分的实现 |
| 打算怎么改 | 改动范围、涉及哪些模块、不做什么 |

## 命名与形状

`YYYY-MM-DD-<主题>.md`。同一主题的后续访谈**追加**进原文件的新一节，不要另开文件 ——
否则决策树会被拆散，读者看不出某个决定是在什么前提下做出的。

**新计划必须用 [`_change-package.md`](_change-package.md) 模板**（五段齐全，不留空小节）：
需求与验收 → 设计逻辑 → **追溯矩阵**（规则 ID ↔ 模块文档章节 ↔ 代码 ↔ 测试）→ 代码实现 → 测试与场景表 → 验证证据。
它同时是**事后复核的入口**：`make trace` 会核模板与变更日志的存在与形状；
每轮的索引与结果追加一条到 [`../log.md`](../log.md)。

> 2026-09-17 及之前的计划（如 `director` 2a）写在模板定稿之前，**不追溯改写**；
> 但它们仍受「**已确认后才可作实现依据**」这条约束。

## 与相邻目录的区别

| 目录 | 区别 |
| --- | --- |
| [`../design/`](../design/README.md) | **已确认、必须遵守**的规则。计划里的内容**没有**这个效力 |
| [`../background/notes/`](../background/notes/) | 讨论记录与倾向。计划更结构化、有明确的未决清单与改动范围 |
| [`../background/decisions/`](../background/decisions/README.md) | 单个**取舍**的决策记录（ADR）。计划里若有真实取舍，应另开 ADR 并在计划里链接它 |
| [`../modules/`](../modules/) | 模块的**设计**（职责、契约、失败模式）。计划是「这一次要做什么」，模块文档是「这个模块是什么」 |

## 怎么写

1. **未定的明确标出**，不要用「后续再定」这类没有动作的话；
2. **每条决定都要能追到来源** —— 是用户答的，还是我从环境里查出来的事实；
3. **改动范围要写清「不做什么」** —— 划界比列清单更有用；
4. 计划落地的过程中若发现某个前提不成立，**回本文件修订**，不要闷头实现。
