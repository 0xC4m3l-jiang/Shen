## 1. 为什么现在做 `director`

四个接入形态的适配器已实现完毕，按 `route_origin` / `route_mirage` / `block` 三值分流。
但核心当前是 `control.ShadowDecider`，**恒返回 `route_origin`** —— 适配器永远只会放行。

`director` 是让引流真正生效的那一块。它同时是 `structure.md` §1.6.4 接缝表里**改动量最小的一条**：
`main.go` 换一个构造调用。

## 4. 第 1 轮的 6 个问题（⚠️ 全部未定）

### Q1 · 本次交付到哪？

| 选项 | 内容 |
| --- | --- |
| **A（推荐）** | 最小 + 灰度 + 熔断：阈值→三值 + 后端名 · `GrayPct` 逐级放开 · `NI-10` 熔断 |
| B | 最小 + 灰度，不含熔断 |
| C | 只做最小（阈值→三值 + 后端名） |
| D | 只写文档与接口，代码下轮再写 |

**推荐 A 的理由**：灰度是 `INT-12`「放开必须逐级推进」的前提 —— 没有灰度就无法从影子模式安全放开；
熔断是 `NI-1`（最高优先级）在引擎进入请求路径后的必要条件，而 2a 正是上路径的那一步。

### Q2 · 决策函数什么形状？

| 选项 | 内容 |
| --- | --- |
| **A（推荐）** | 纯阈值：`score ≥ block` → `block`；`≥ mirage` → `route_mirage`；否则 `route_origin` |
| B | 阈值 + 证据门槛（`Signals` 非空才允许改道） |
| C | 数据驱动的决策规则（像 `judge` 那样可配置） |
| D | 阈值 + 会话维度（同会话累计到某分才改道） |

**推荐 A 的理由**：`ST-24`「策略是数据」管的是**判定规则**（在 `judge` / `policy`），不是决策阈值；
阈值已由 `ST-23` / `INT-24` 要求集中定义 + 配置覆盖。加证据门槛会让阈值失去可解释性；
数据驱动是过度设计 —— 目前没有第二个决策策略。

### Q3 · 阈值从哪来？

| 选项 | 内容 |
| --- | --- |
| **A（推荐）** | 定义导出的 `ThresholdSource` 接口：2a 由配置实现，`policy` 就绪后换实现 |
| B | 直接用具体类型读配置，不定义接口（`policy` 就绪时再改 director 内部） |
| C | 直接依赖 `policy` 模块（本次阻塞） |

**推荐 A 的理由**：与 `structure.md` §1.6.4 的既有接缝模式同构（`judge.RuleSource` 就是这么做的），
替换时改动只在 `main.go` 一行。

### Q4 · 灰度的方向与确定性？

| 选项 | 内容 |
| --- | --- |
| **A（推荐）** | 「本会改道的请求按比例**降级为放行**」（0% 起步往上放）；按 `decision_id` 哈希**确定性**判定 |
| B | 「本会放行的请求按比例**升级为改道**」；同样确定性 |
| C | 不用 `GrayPct`，放开靠整体开关 |
| D | 用随机数按比例决定 |

**推荐 A 的理由**：影子模式本来就是「0% 改道」，所以 0 起点自然对应全放行。
**确定性是硬要求**：`ST-10` 规定同一 `decision_id` 重试复用同一结果 —— 用随机数会让重试得到不同决策，
直接破坏幂等。

### Q5 · `block` 在 2a 要不要真的产出？

| 选项 | 内容 |
| --- | --- |
| **A（推荐）** | 默认**不产出**（配置开关默认关）；只在「改道不可行」时才用 |
| B | 按阈值正常产出（`score ≥ 0.95` → `block`） |
| C | 彻底不做产出路径，只留枚举值 |
| D | 只对白名单外的请求生效 |

**推荐 A 的理由**：项目的全部价值在**透明改道**；可见拦截会把对手推走、也暴露了我们存在
（`MD-23` 的同一精神）。但保留能力 —— 改道不可行时它是最后手段，符合 `NI-1`。

### Q6 · 熔断（`NI-10`）落在哪一层？

| 选项 | 内容 |
| --- | --- |
| **A（推荐）** | 放在 `control` 的 gRPC 服务面（它看到全部请求，天然能统计错误/超时率） |
| B | 放在 `director`（决策流水线内部统计） |
| C | 本次不做，另开一项（适配器的 fail-open 先顶着） |

**推荐 A 的理由**：熔断是「服务整体降级」的语义，属于服务面而不属于决策逻辑；`director` 只做决策。
状态是**各副本本地**的（每个副本独立跳闸），不违反 `AR-9` 的无状态多副本。

## 6. 验收标准（做完怎么算完）

1. `make gate` 全绿（含 `-race`）；
2. `director` 的单测覆盖：三值 × 阈值边界 · 灰度确定性（同 `decision_id` 同结果）· 未识别取值回落 `route_origin`（`NI-5`）· 分支穷尽性（`MD-8`）；
3. 测试**只用替身**，不依赖 `judge` / `store` 的真实实例（`MD-22`）；
4. 端到端：置一个蜜罐后端 + 把阈值降到 0，看到请求真的被改道（用 `edge/proxy` 的 `SHEN_PROXY_MIRAGE`）；
5. 影子模式下**行为与现在完全一致**（恒 `route_origin`）—— 这是回归判据。

**时间量级**：前 4 项若 6 个决策按推荐确认 —— **约 1 小时**（新建 3 个文件 + 改 1 行）。
若灰度与熔断都要做，**再加 1–2 小时**（灰度是纯函数，熔断要跨请求统计与状态机）。
