## 1. 需求与验收

**用户要什么**：更新完整的 README 与 docs —— 「让我知道每个目录是做什么的，每个模块在哪个目录，对应用了什么能力，怎么和其他模块接入」。

**验收判据**：

1. **目录**：顶层十个目录逐个有一句话说明（含语言与"是否源码"），并指出白名单规则（`ST-1`）与产物形态（`vendor/` · `scripts/bin/`）。
2. **模块 → 目录**：22 个模块逐个给出目录，且目录真实存在。
3. **能力**：每个模块一句话能力（取自模块文档 §1，不重写规则）。
4. **接口**：给出**对外接口名**（取自各模块 `iface.go` 的实测导出，不凭记忆）。
5. **接入**：进程边界（3 个 Go 二进制 + L4 worker + 控制台）与**接缝表**（S1 判定 · 遥测上报 · 观测读取 · S4 策略面 · 注入 · 存储 · 以及"不存在的接缝"），并给出请求时序。
6. **不重复权威**：完成度指向 [`../progress.md`](../progress.md)，规则指向 [`../design/`](../design/README.md)，本文只做索引与接线。
7. 导航接通：README §5、[`../README.md`](../README.md)、[`README.md`](README.md) 三处都能点到它。

**不做什么**：不改任何规则正文 · 不改代码 · 不重复进度表（避免两处维护）。

## 2. 设计逻辑

| # | 问题 | 决定 | 理由 |
| --- | --- | --- | --- |
| ① | 地图放哪 | `docs/modules/_map.md` | 与模块文档同目录便于就近查阅；`_` 前缀是既有的**元文档**约定（同 `_template.md`），不会被 `MD-2`（一模块一文档）误判 |
| ② | 事实从哪来 | 全部**实测/既有权威**：清单取 `modules.md` §1.1，接口名取 `iface.go`，进程与依赖方向取 `structure.md` §1.6，rpc 取 `api/*.proto` | 记忆会漂；地图一旦漂就把人带错 |
| ③ | 完成度要不要写 | **不写**，只给"源码/配置/声明式/第三方"的**产物形态**，完成度指向 `progress.md` | 避免同一事实两处维护（该文件已声明是完成度唯一维护处） |
| ④ | 要不要写"怎么加新模块" | 写（七条要件表） | 这是读者最需要、却最少被写下来的那部分 |

## 3. 追溯矩阵

| 规则 | 在本文怎么体现 |
| --- | --- |
| `MD-2`（一模块一文档） | 地图以 `_` 前缀登记为元文档；模块文档仍是一模块一份 |
| `MD-17` / `MD-18`（先文档后实现 · 先登清单） | 「一个模块的标准形状」七条要件表 |
| `ST-1`（顶层目录白名单） | 顶层目录表 + 指出 `vendor/`、`scripts/bin/` 不是源码平面 |
| `ST-3`（适配器不得 import 核心内部） | 接缝表末行「不存在的接缝」：由 `internal/` 规则编译期挡住 |
| `ST-4`（接口单独成文件） | 接口名一律标注来自各模块的 `iface.go` |
| `AR-2` / `AR-10` / `AR-32` | 一分钟看懂里写明「判定与响应生成只在核心一次」「控制台只读」「L4 不持有执行能力」 |
| `D-3`（规则 ID 唯一） | 全文只引用既有 ID，不新造 |
