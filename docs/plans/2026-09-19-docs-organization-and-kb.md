## 1. 需求与验收

**用户要什么**：整理 `docs/` 下的内容，按**设计 / 知识库 / 模块信息 / 开发运维**分类；**减少不必要的内容**；
保证是"后续能快速进项目学习、项目运行、项目开发定位"的文档；**主要是 `docs/kb/` 的更新**。

**验收判据**：

1. **新人一条线**：从 `docs/README.md` 或 `docs/kb/README.md` 出发，三步内能拿到「项目是什么 / 能力点在哪 / 怎么跑 / 怎么定位」；
2. **能力点定位表**存在且准确：每个能力 → 模块 → 代码目录 → 模块文档（取自实测清单，不凭记忆）；
3. **kb 分层清楚**：现行 vs 历史标注，历史条目说明"为什么留、能不能照做"；
4. **减冗余**：同一主题不在多处重复；过期状态标记（"待建"其实已建）全部改准；
5. **表格与链接不坏**：表格列数一致、无悬空链接（`make trace` 的 `TC-3`）；
6. `make gate` 绿。

**不做什么**：不动 `design/` 任何规则正文 · 不删历史留痕（`plans/`、ADR、已移除技能）· 不新建"运营看板"类文档（`analytics/` 仍待建）。

## 2. 设计逻辑

| # | 问题 | 决定 | 理由 |
| --- | --- | --- | --- |
| ① | kb 该承担什么 | **快速上手 + 踩坑**（不是规则、不是契约） | 规则在 `design/`、契约在 `spec/`、操在 `ops/`；kb 只做"进来就能用"的入口与经验 |
| ② | 能力点怎么给 | 一张**能力 → 模块 → 目录 → 文档**的表（[`quick-tour.md`](../kb/quick-tour.md) §3） | 新人最缺的是"我要改 X 去哪"，而不是再读一遍架构 |
| ③ | 历史条目怎么办 | **保留 + 显式标注**（`known-issues.md` 开头分类表；`K-9`/`K-10`/`K-11` 标"历史（ext_proc 方案，已被 ADR-0017 取代）"） | 直接删会丢掉当时的理由；不标会让人照着改今天的代码 |
| ④ | 冗余怎么减 | 只留"指针"，不复制内容（如运行类全部指向 `ops/`） | 同一事实两处维护必然漂移（`progress.md` 已因这点立过规矩） |
| ⑤ | `spec/` 缺索引 | 新增 [`spec/README.md`](../spec/README.md)（5 份文件 + 改一处要同步哪几处） | 原先只能靠 `docs/README.md` 的一行描述；改契约时容易漏同步 |
