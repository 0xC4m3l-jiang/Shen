## 1. 需求与验收

**用户要什么**：① 梳理**蜜罐以外**的所有逻辑；② 把整体逻辑与功能、相关技术点与实现参考补进 docs；③ 整合 docs —— 合理合并、减少不必要的信息与文件。

**验收判据**：

1. 新增一份**从请求进入到回包**的全链路文档：每一步的**逻辑 / 技术点 / 实现位置 / 规则依据 / 怎么验**；
2. 明确圈出**不在范围**的部分（蜜罐内容与协议栈、L3 声明式细节），避免与模块文档重复；
3. 整合只做**减法且不断链**：被 `docs/log.md` 或 `AGENTS.md` 引用的文件一律保留；
4. 表格与链接不再有格式问题（`MD060` / `TC-3`）；
5. `make gate` 绿。

## 2. 设计逻辑

| # | 问题 | 决定 | 理由 |
| --- | --- | --- | --- |
| ① | 新文档放哪 | 顶层 `docs/logic.md` | 与 `progress.md` / `log.md` 同级；`modules/` 下会被 `MD-2`（一模块一文档）当成模块文档 |
| ② | 与既有文档的分工 | `logic.md` = **行为逻辑**；`modules/_map.md` = **目录/能力**；`ops/runbook.md` = **操作**；`design/` = **规则** | 四者读者与用途不同，互不重复 |
| ③ | 能不能合并 `docs/plans/`（54 份） | **不能** | `docs/log.md` 的历史条目引用它们，合并会造成悬空引用（门禁 `TC-3` 会拦） |
| ④ | 能不能删 `kb/removed-skills.md` | **不删** | 被 5 处引用（含 `AGENTS.md` 与一份历史计划） |
| ⑤ | 那"整合"做什么 | 做**减重复信息**：把 kb 里与 `ops/runbook.md` 重复的两节改成指针；给 `plans/` 加"怎么读"说明 | 减少需要维护的第二份事实，同时不动引用图 |
