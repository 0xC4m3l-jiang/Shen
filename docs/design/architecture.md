## 1. 总体设计原则

```text
选型三原则   ① 贴近职责：性能敏感用系统级语言，AI 推理用 Python
             ② 贴近生态：哪层的库最成熟就用哪层的语言
             ③ 贴近运维：能用现成中间件就不自己造轮子

接入三原则   ① 业务零改造：改基础设施，不改业务代码
             ② 真实流量不受影响：欺骗是"旁路"或"引流"，非阻断
             ③ 可灰度、可回滚：先镜像观察，再逐步接管

复用三原则   ① 基础设施层（代理/网关/边车/隔离）全部复用开源
             ② 智能决策层（判定/欺骗/编排）全部自研
             ③ 中间用胶水层（遥测聚合/策略回写）连接
```

## 2. 分层架构（L0–L4）

```text
        攻击方 AI / 爬虫 / APT / 普通用户
                    │
                    ▼
  L0 接入层   流量镜像 · TLS 卸载 · 路由        ← 100% 复用开源（Envoy / Nginx / HAProxy）
                    │
                    ▼
  L1 边缘欺骗层  投毒 · 假路径 · 引流执行        ← 复用代理底座 + 自研插件；★ 判定逻辑不在此层
                    │
                    ▼
  L2 高交互欺骗层  协议仿真蜜罐 · LLM 多轮会话    ← 承接已识别的可疑流量
                    │
                    ▼
  L3 网络欺骗层  蜜网编排 · 微隔离 · 假拓扑      ← 复用 Cilium / Tetragon
                    │
                    ▼
  L4 分析决策层  意图识别 · 攻击链还原 · 策略生成  ← 自研为主，复用 AI 框架
                    │
                    └── 策略回写 ──► 反馈 L1 / L2 / L3
```

| ID | 规则 | 验证方式 |
| --- | --- | --- |
| **AR-1** | 系统**必须**按上图的 L0–L4 五层划分；**禁止**跨层直接调用（L1 不得调用 L4，L4 不得直接写判定缓存）。 | 架构评审 + 依赖方向检查 |
| **AR-2** | **判定逻辑必须只存在于核心一处**；L1/L2/L3 与适配器**禁止**实现任何判定逻辑。 | 代码评审 + 适配器职责清单核对 |
| **AR-3** | L0 接入层**禁止**自研，**必须**复用现成组件。 | 选型评审 |
| **AR-4** | 每一层**必须**只选一个组件，**禁止**多层代理叠加（如 Istio 与 Cilium 同时争抢流量控制）。 | 部署拓扑评审 |

## 3. 核心与适配器

> **不需要实现「两种能力」，而是「一个核心 + 可插拔的接入适配器」。**

```text
┌─ 核心（Core）—— 判定与响应生成的唯一实现 ──────────────────
│  判定 judge · 决策与调度 director · 响应生成 responder
│  会话 session · 隔离 isolation · 策略 policy
│  遥测 telemetry · 存储访问 store（唯一的 I/O 出口）
│  形态：无状态多副本，状态全部外置（AR-9）
│  对外：gRPC（Judge / Telemetry / Policy）
└──────┬────────────────────┬────────────────────┬──────────
       │ S1 判定 / 遥测      │ S3 分析任务          │ 状态外置
       ▼                    ▼                    ▼
  适配器（薄）           L4 分析（Python）       数据面
  镜像 · DNS ·           意图识别 · 攻击链        Redis
  反向代理 · Sidecar     还原 · 策略生成          ClickHouse
  只做四件事（AR-6）                             PostgreSQL
       │                    │
       │ 处置执行            │ 策略（S4）
       ▼                    ▼
┌─ 欺骗执行面 ────────────────────────────────────────────────
│  L1 处置（作为适配器内模块，ST-5）· L2 蜜罐 · L3 网络策略
└─────────────────────────────────────────────────────────────
```

| ID | 规则 | 验证方式 |
| --- | --- | --- |
| **AR-5** | **判定与响应生成必须只实现一次**（核心内）；适配器**禁止**重复实现。 | 代码评审 + §4 的适配器职责清单核对 |
| **AR-6** | 适配器**只允许**做四件事：① 拦截请求 ② 查本地判定缓存，未命中才调核心 Judge ③ 按结果执行（透传 / 投毒 / 引流）④ 异步上报遥测。 | 适配器代码评审 |
| **AR-7** | 适配器**禁止**：① 实现判定逻辑 ② 做 LLM 推理 ③ 维护会话状态 ④ 写入核心状态（遥测可上报，状态变更必须经核心）。 | 同上 |
| **AR-8** | **业务路径不得依赖核心可用性** —— 核心故障时全局降级为放行（fail-open）。 | 故障注入（见 [`constraints.md`](constraints.md) 的 V-1…V-5） |
| **AR-9** | 核心**必须**无状态多副本，状态**必须**全部外置；核心进程内**禁止**模块级可变容器。 | 代码评审 + 多副本一致性测试 |
| **AR-10** | 控制面（策略编排、蜜饵资产管理、人工干预、审计）**禁止**参与请求级判定。 | 架构评审 |

## 4. 数据流要点（规则）

> **流程图不在这里。** 完整的请求流（含每一步的模块与语言）见 **§8**；
> 遥测与策略闭环见 §7.3。本节只保留**无法从图上读出、必须写成规则的要点**。

| # | 要点 | 依据 |
| --- | --- | --- |
| 1 | **缓存命中时不经核心** —— 适配器直接处置并透传；核心故障不影响业务路径 | `AR-8` · `AR-6` |
| 2 | **超时 / 失败一律 fail-open = 放行** —— 判定不可用不得阻断业务 | `NI-4` · `NI-5` |
| 3 | **隔离名单命中即短路**，不再调用核心 | `AR-6` |
| 4 | **Redis 不可用时**：隔离名单读不到即回退到调用核心判定（fail-open，**不得**阻断业务）；隔离能力暂时失效**必须**计入告警 | `NI-10` · `ST-15` |
| 5 | **蜜罐会话建立时必须签发** `session_id` + 会话水印令牌；逐命令转录、凭证捕获、文件投递均写入 `event` | `AR-25` · `NI-13` |
| 6 | **蜜罐响应的快慢两条路**：快路径为规则与模板响应（毫秒级，蜜罐进程内）；慢路径为 LLM 会话仿真（调用 L4，规范见 §5） | `MD-16` · §5 |
| 7 | **遥测上报异步、批量、幂等**；适配器侧不承担持久缓冲 | `AR-11` |
| 8 | **触发 L4 分析必须经态势去重** —— LLM 调用量不得随事件量线性增长 | `AR-14` |

| ID | 规则 | 验证方式 |
| --- | --- | --- |
| **AR-11** | 遥测上报**必须**幂等（同一 `event_id` 重复上报不产生重复记录）；判定**必须**有幂等键 `decision_id`。 | 单元测试 + 重放测试 |
| **AR-12** | L4 生成结论若引用证据 ID，**必须**在写入前校验该 ID 真实存在于遥测存储中。 | 单元测试 + 注入不存在的 ID |
| **AR-13** | 策略下发**必须**版本化、可灰度、可回滚；各层**必须**回执以便版本对账。 | 集成测试 |
| **AR-14** | 触发 L4 分析**必须**经过态势去重，**禁止**随事件写入量线性触发。 | 指标断言（LLM 调用量不随事件量线性增长） |

## 5. LLM 交互组件规范

> **适用范围**：L2 会话仿真与响应生成、L4 意图识别与策略生成、话术与模板生成，以及**未来任何**要调模型的生成能力（例如动态沙箱规格）——
> **凡生成必经 `ai-capability` 出口并过护栏**（`AR-33`，口径 2026-09-20 由「欺骗内容」放宽）。
> **核心纪律**：**LLM 输出不可直接信任** —— 契约层必须与提示词分离。

| ID | 规则 | 验证方式 |
| --- | --- | --- |
| **AR-15** | 提示词只描述任务与上下文；**输出结构必须由独立代码层校验**，校验失败**必须**抛异常 —— **禁止**返回默认值、**禁止**静默降级。 | 单元测试（喂坏输出必失败） |
| **AR-16** | 所有 LLM 输出**必须**统一为 `{"accepted": bool, "data": {...}}`；`accepted=false` **必须**走独立分支并记录拒绝原因。 | 契约层单元测试 |
| **AR-17** | JSON 提取**必须**三段式容错：① 整段解析 ② markdown 代码围栏内提取 ③ 对每个 `{` 位置尝试解析；第 ③ 段**必须**设扫描位置上限。 | 单元测试（含超长输出） |
| **AR-18** | 列表类字段**必须**有硬截断上限；**必须**显式记录截断数量。 | 单元测试 + 日志断言 |
| **AR-19** | 超时处理**必须**为双阶段：阶段 1 执行（超时 T1）→ 阶段 2 **复用同一会话**收尾（超时 T2）。**禁止**超时后直接丢弃整轮结果，**禁止**重新执行完整任务。 | 超时注入测试 |
| **AR-20** | 收尾提示词**必须**显式限定范围（不继续推进、不等待未完成任务、只总结已完成部分）；收尾阶段**必须**使用与正常阶段**不同的契约**（只允许"事实"类字段，**禁止**"完成 / 成功"类字段）。 | 契约评审 + 单元测试 |
| **AR-21** | 两阶段均失败时**禁止**写入任何中间数据；**必须**释放已占用的标记（认领、租约）。 | 单元测试 |
| **AR-22** | 生成内容**必须**过黑名单校验，至少覆盖三类：**泄露类**（内网地址、真实主机名、真实文件路径、真实业务标识）、**自曝类**（"我是 AI"、"这是蜜罐"、"作为语言模型"）、**超长类**。 | 单元测试 + 规则可审计 |
| **AR-23** | 输出**必须**按用途设不同长度上限（面向攻击者的会话响应 / 面向存储的结论 / 面向分析的中间产物各自独立）。 | 单元测试 |
| **AR-24** | 话术与提示词**必须**作为代码仓库内资源文件、随版本分发；**禁止**存放于运行期可变存储。启动时**必须**校验模板存在与占位符齐全。 | 启动期断言 + 部署评审 |
| **AR-25** | 会话 ID **必须**作为任务上下文的一等字段，在会话建立、心跳、收尾三阶段保持一致。 | 集成测试 |
| **AR-26** | 启动期**必须**断言两条周期关系，不满足即启动失败：① 判定超时 ≤ 业务路径延迟预算（§6）；② 心跳 / 租约周期 > 遥测采集上报周期。 | 启动期断言 |
| **AR-27** | 欺骗链路**必须**有端到端测试：以进程内测试客户端 + 模拟攻击者驱动，跑通判定 → 投毒 / 引流 → 遥测 → 策略回写全链路，**必须**覆盖全部决策分支。 | CI |
| **AR-30** | 任何伪造响应**必须**按 `(会话, 资源)` 命中同一内容 —— 重试 / 重放 / 翻页都得到同一答案。**禁止**在响应路径上引入非确定性（随机数、当前时间、LLM 采样）。依据 [ADR-0014](../background/decisions/0014-generative-deceptive-response.md)。 | 重放测试（同会话同资源两次必须逐字节一致） |
| **AR-31** | 送入 L4 的**攻击者可控内容必须**以结构化数据传入，**禁止**进入提示词的指令区；提示词**必须**显式标注其为**不可信数据**。原始观测**禁止**为「净化」而丢弃（证据链要求）。依据 [ADR-0015](../background/decisions/0015-indirect-prompt-injection.md)。 | 提示词评审 + 注入样本回归（结论不得改变） |
| **AR-32** | 分析用 LLM **禁止**持有执行能力（不下发指令 / 不生成载荷 / 不调外部系统），只输出**结构化结论**；分析结论**禁止**直接回写响应（只经 `policy` 间接生效）。依据 [ADR-0015](../background/decisions/0015-indirect-prompt-injection.md)。 | 接口清单核对（`SB-1` / `SB-2`） |
| **AR-33** | **任何 LLM 生成必须经 `ai-capability` 的唯一出口**（`generate(TaskSpec) → Envelope`）并**强制过护栏**（前置提示词三段式 + 后置独立校验）；**禁止**任何绕过路径 —— 模型客户端**只能**被该能力自身 import（`service.py` 是出口、`model.py` 是模型接缝；**能力自身与客户端所在层（`analysis/llm/`）之外一律禁止**，判据 = 门禁结构检查），未登记的任务种类与缺护栏档案的任务**必须**在启动期断言失败。**未经护栏校验的产物禁止交付给任何消费方**（入库 / 下发到边缘 / 上报均禁止 —— 校验**拒绝记录**不属「产物」，按 `AR-16` 必须记录原因）。依据 [ADR-0025](../background/decisions/0025-generic-guardrailed-outlet.md)（口径由 [ADR-0023](../background/decisions/0023-deception-content-injection.md) 自「欺骗内容」放宽，**2026-09-20 用户确认**）。 | 门禁结构检查（`make archcheck` 的 `AR-33` 项：`analysis/` 下除 `aicap/service.py` · `aicap/model.py` · `llm/` 自身与测试外，禁止 import 模型客户端）+ 单元测试（未登记 kind / 缺护栏档案必拒） |

## 6. 非功能指标

| 指标 | 目标值 / 约束 | 说明 |
| --- | --- | --- |
| 适配器判定耗时（缓存命中） | **应当** ≤ 1 ms | 与代理同进程，无网络跳转 |
| Judge RPC deadline | **必须** ≤ 3 ms | 超时本地降级为放行（fail-open） |
| **业务路径额外延迟（P99）** | **必须** ≤ 5 ms | 构成：缓存查询 ≤ 1 ms + Judge ≤ 3 ms + 本地处置 ≤ 1 ms。**超预算则回退到旁路镜像** |
| 核心可用性 | 核心故障**禁止**阻塞业务 | fail-open 降级窗口 = 核心恢复时间，期间判定能力缺失 |
| 隔离生效延迟 | 本适配器即时；其他适配器**应当** ≤ 1 s | 跨适配器传播依赖名单缓存刷新周期 |
| 策略下发延迟 | **应当** ≤ 30 s | 增量订阅 + 回执对账 |
| 遥测写入 | 异步批量；**必须**定义缓冲溢出时的丢弃优先级 | 适配器侧不承担持久缓冲 |
| 蜜罐并发连接 | **必须**按协议设上限，超限即拒绝并记录 | **禁止**无上限创建线程或事件循环 |
| 判定缓存容量 | **必须**有容量上限与 LRU 淘汰 | 未命中率上升会线性放大 RPC 调用量，**必须**纳入监控 |
| 事件保留 | **必须**按数据类型分别配置 | 见 [`constraints.md`](constraints.md) |
| 存储容量 | ClickHouse **必须**按天分区 + 保留策略 | 容量 ≈ 事件量 × 保留天数 × 站点数 |

> 表内**指标项与约束关系是规则**；具体数值（上限 N/M、各协议连接数）**必须**在压测阶段实测确定。

| ID | 规则 | 验证方式 |
| --- | --- | --- |
| **AR-28** | §6 的指标项**必须**全部有采集点与告警阈值；**禁止**只定义不采集。 | 指标清单评审 + 看板核对 |
| **AR-29** | 业务路径 P99 额外延迟**必须** ≤ 5 ms；超预算**必须**回退到旁路镜像接入（见 [`integration.md`](integration.md)）。 | 压测 + 接入演练 |

## 7. 拓扑视图（多视角）

> 本节是 §2 / §3 / §4 / [`structure.md`](structure.md) 的**图形化重述**，**不新增规则**；规则编号见对应章节。
> ⚠️ §2 的 L0–L4 是**职责分层叙事**；§7.1 给出**实际拓扑**。两者的差异登记在 §10。

### 7.1 平面视图（实际拓扑）

> 画法说明：不用右边框，避免中文双宽字符导致的错位。

```text
┌─ 控制平面 ─────────────────────────────────────────────────────────────
│  控制台(TypeScript) · 策略编排 · 蜜饵资产管理 · 人工干预 · 审计
│  约束：禁止参与请求级判定（AR-10）
└──────────┬──────────────────────────────────────────────────────────────
           │  策略下发（版本 + 灰度 + 回执，AR-13 / S4）
           ▼
┌─ 数据平面（L0 + L1）───────────────────────────────────────────────────
│  L0 代理（Envoy / Nginx / HAProxy）—— 禁止自研（AR-3）· 单一组件（AR-4）
│    └─[S2 适配器]─ 适配器（Go 反向代理 / DNS 解析 / 镜像）—— 只做四件事（AR-6）
│    ⚠ 形态 ③④：TLS 终结落在**引擎进程内**（内嵌 Caddy，[ADR-0017](../background/decisions/0017-caddy-l1-base.md)），
│       客户的 L0 可省或只做入口路由 —— 仍满足 AR-4（单个七层组件）
│         ├─ 查本地判定缓存（AR-6）
│         └─[S1 gRPC  deadline ≤ 3ms]─► 核心（Go，无状态多副本）
└──────────┬──────────────────────────────────────────────────────────────
           │  透传（缓存命中时直达真实业务，不经核心）
           ▼
┌─ 执行平面（L2 + L3）───────────────────────────────────────────────────
│  L2 协议仿真蜜罐（Go / Rust）· 假 shell · LLM 会话   ← 承接引流流量
│  L3 蜜网编排 · 微隔离 · 假拓扑（Cilium / Tetragon）  ← L2 的运行底座
└──────────┬──────────────────────────────────────────────────────────────
           │  事件写入
           ▼
```

### 8.2 四条接入形态的差异（同一次请求）

```text
                    ① 旁路镜像       ② DNS 引流      ③ 反向代理      ④ Sidecar
                   ─────────────   ─────────────   ─────────────   ─────────────
L0 谁做接入         LB 镜像规则      DNS 解析        客户 LB/Envoy     Gateway/Ingress
引擎在请求路径？    ❌ 不在          ✅ 在           ✅ 在            ✅ 在
能处置吗？          ❌ 只观察        ✅ 能           ✅ 能            ✅ 能
步骤 1→2 走什么     TEE/eBPF 复制    正常转发        正常转发         正常转发
步骤 2 适配器       adapter-mirror   adapter-dns     adapter-proxy    adapter-proxy
步骤 3-4 核心       调用（只算不处置） 调用            调用            调用
步骤 5 处置         无（只记录）     投毒 / 引流     投毒 / 引流     投毒 / 引流
步骤 6 遥测         ✅ 最完整        ✅              ✅              ✅

MVP（阶段 1）       ← 只做这个
阶段 2 加入                          ✅              ✅              ✅
```

> **① 旁路镜像下引擎不在请求路径上** → 下列规则**全部不适用**：
> `NI-3`（失败放行）· `NI-4`（硬超时）· `NI-10`（熔断）· `AR-6`（拦截）· `AR-7`（处置）。
> 见 `INT-6` 与 §10.2 缺口 8。
> 
> ⚠ **③④ 的 L0 是「可省的」**：TLS 终结已收进引擎进程（内嵌 Caddy，`SHEN_PROXY_TLS_MODE`），
> 客户侧的 LB / Gateway 仍可保留，但只做入口路由与四层转发，**不得再叠一层做七层路由决策**（`AR-4`）。
> 依据 [ADR-0017](../background/decisions/0017-caddy-l1-base.md)。
>
> ⚠️ **但核心仍然被调用** —— 镜像模式要**算判定分**（供阈值校准），只是**不处置**。
> 这正是 `control.ShadowDecider` 恒返回放行的原因：算分，但永不改道。

### 8.3 三条处置分支（步骤 5 展开）

```text
【分支 A】action = route_origin   （放行）

   适配器 ──► 直接转发到真实业务集群
             （缓存命中时连核心都没调用过）

【分支 B】action = route_mirage   （悄悄改道 —— 项目的全部价值）

   核心 responder（Go）      生成投毒内容 / 选引流目标 / 渲染话术
          │
          ▼
   适配器 edge-injection（Go） 改写响应 —— ★ 只能改蜜罐侧（INT-8）
          │
          ├─► 蜜罐后端池：honeypot-protocol（Go / Rust）
          │      · 协议仿真（SSH / MySQL / Redis / FTP）
          │      · honeypot-shell（假 shell + 内存文件系统）
          │      · 逐命令转录、凭证捕获
          │
          └─► 多轮会话时调用 L4（Python）：
                 llm-components  ← 契约校验 · 容错解析 · 双阶段收尾 · 内容黑名单
                              （AR-15 … AR-27 共 13 条规则约束这一段）

   ★ 客户端看到：同域名 · 同 TLS · 同 URL · 同会话语义 —— 分不出真假

【分支 C】action = block   （拦截）

   适配器 ──► 直接拒绝
   ⚠️ MVP 阶段（旁路镜像）执行不到 —— 引擎不在路径上（ADR-0002）
```

### 10.2 画 §7 / §8 视图时暴露的结构缺口

> 下列各项是**规则之间的关系尚未定义**，不是规则本身有错。
> 每一项若要修改已确认规则，**必须**按 [`README.md`](README.md) §3.2 的重开流程走。

| # | 缺口 | 涉及规则 |
| --- | --- | --- |
| 4 | **§2 的 L0–L4 是职责叙事，§7.1 的实际拓扑是四个平面**（数据平面 L0+L1 · 执行平面 L2+L3 · 分析平面 L4 · 控制平面）。具体差异：L3 是 L2 的**运行底座**而非下游；L4 与 L1/L2 是**双向反馈**而非链尾。两种视图的取舍未定 | §2 ↔ §7.1 |
| 5 | **适配器不属于 L0–L4 任何一层** —— 它是承载 L1 处置模块（`ST-5`）并桥接核心的**部署单元**；但 §4.1 / §4.2 又写作“L1 适配器”。层与部署单元的关系未定义 | AR-1 ↔ ST-5 |
| 6 | **策略未区分两类** —— 影响**判定**的策略必须下发到核心（判定只存在于核心，AR-2 / AR-5）；影响**执行**的策略下发到 L1/L2/L3（AR-13）。当前只定义了后者，缺乏前者 | AR-13 ↔ AR-2 / AR-5 |
| 7 | **三处接缝在 `S1`…`S5` 之外**：① L2 蜜罐与协议仿真的凭证 / 文件 / 转录如何写入 `event`；② L3 的事件如何上报；③ 控制面审核的接口 | ST-6 |
