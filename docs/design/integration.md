# 接入形态

> 规则 ID 前缀 `INT`。写作要求见 [`README.md`](README.md) §2。
>
> **已确认**：用户于 2026-09-17 确认 **INT-1…INT-25 全部通过**；批准 **① 旁路镜像 / ② DNS 引流 / ③ 反向代理前置 / ④ Sidecar** 四种形态，
> **⑤ 应用内 SDK 不批准**（[ADR-0003](../background/decisions/0003-integration-forms.md)）。
> **来源**：外部设计稿 [`../background/research/deception-engine-design.md`](../background/research/deception-engine-design.md) §三。
> **已确认**：用户于 2026-09-17 确认 **INT-1…INT-25 全部通过**（其中 18 条为重构前已确认规则的换号版本）。
> ⚠️ **TLS 终结是启用误导处置的硬前提**（见 INT-22）：TLS 透传接入只能观察。
> ✅ **形态 ③④ 的落点（2026-09-19）**：TLS 由**引擎进程内嵌的 Caddy** 终结
> （`SHEN_PROXY_TLS_MODE=off|manual|acme`），因此这两种形态具备启用误导处置的前提；
> 形态 ①② 仍依赖客户 L0。依据 [ADR-0017](../background/decisions/0017-caddy-l1-base.md)。
> 未解决项：四种形态先做哪个、Sidecar 形式、多租户粒度 —— 见 [ADR-0003](../background/decisions/0003-integration-forms.md)。

## 1. 批准的四种形态

| # | 形态 | 客户侧改造 | 引擎在请求路径上？ | 能主动欺骗？ |
| --- | --- | --- | --- | --- |
| **INT-1** ① | **旁路镜像** —— iptables `TEE` / eBPF / LB 镜像，把流量复制一份给引擎 | 加镜像规则 | ❌ 不在（只收副本） | ❌ 只观察 |
| **INT-2** ② | **DNS / 智能解析引流** —— 把可疑来源解析到引擎 IP | 改 DNS 记录 | ✅ 在 | ✅ |
| **INT-3** ③ | **反向代理前置** —— 业务 upstream 指向引擎，由引擎转发 | 改 upstream | ✅ 在 | ✅ |
| **INT-4** ④ | **Sidecar / Service Mesh** —— 业务 Pod 内注入边车（或经 `ext_authz` 旁路服务判定） | 改 CRD / 注入边车 | ✅ 在 | ✅ |

```text
① 旁路镜像（零风险起步）
   用户 ──► LB ──┬──► 真实 Web 服务
                 └──►（镜像复制）──► 引擎（只观察不响应）

② DNS 引流
   攻击者/爬虫 ──► DNS ──► 引擎 IP
   真实用户     ──► DNS ──► 真实服务 IP

③ 反向代理前置
   用户 ──► [引擎/反向代理] ──┬──► 真实业务（正常流量）
                              └──► 蜜罐 / 假响应（可疑流量）

④ Sidecar
   Pod: [业务容器] ◄──► [引擎边车]     流量经边车拦截
```

| ID | 规则 | 验证方式 |
| --- | --- | --- |
| **INT-5** | 四种形态**必须**各自独立工作；**禁止**把其中一种实现为对另一种的依赖。 | 分别单独部署并各自通过故障注入测试 |
| **INT-6** | **不在请求路径上的形态（①）不适用**依赖"引擎在路径上"的规则（`NI-3` fail-open、`NI-4` 决策硬超时、`NI-10` 熔断）。 | 接入检查单逐项标注适用性 |
| **INT-7** | 引擎**禁止**要求客户修改业务应用代码。 | 接入演练（全程不改业务仓库） |
| **INT-8** | 引擎**禁止**对业务侧响应做任何改写；改写**只能**作用于蜜罐侧。 | 单元测试 + 差异哨兵（见 [`modules.md`](modules.md)） |
| **INT-9** | 交付物**必须**是**一个独立服务 + 接入物料**，**禁止**做成需要嵌入业务进程的形态。 | 部署清单评审 |

## 3. 上线步骤（强制）

| ID | 规则 | 验证方式 |
| --- | --- | --- |
| **INT-11** | 任何接入的**首次上线必须为影子模式**：只观测、不处置、不回写。**旁路镜像形态天然满足此要求**。 | 上线检查单 |
| **INT-12** | 从影子模式放开**必须**按 `仅观测 → 只对高置信 Agent 误导 → 放开阈值 → 全量` 逐级推进；**每一级必须**在护栏指标达标后才允许进入下一级。 | 晋升记录（每级指标快照） |
| **INT-13** | 任一阶段护栏指标越界时**必须**自动回退到上一级或影子模式。 | 故障注入 + 指标断言 |
| **INT-14** | 接入**必须**分阶段推进：`旁路镜像（观察）→ 反向代理 / Sidecar（接管）`；**禁止**首次接入即全量接管。 | 接入计划评审 |
| **INT-15** | 解除接入**必须**能通过移除一段配置完成，且**禁止**要求重启被接入业务。 | 回滚演练 |

## 4. 接入物料（强制交付）

| ID | 交付物 | 要求 | 验证方式 |
| --- | --- | --- | --- |
| **INT-16** | 配置生成器 | **必须**能针对四种形态输出可直接粘贴的配置片段 | 生成物可直接应用并通过接入演练 |
| **INT-17** | `shen doctor` 自检 | **必须**能验证五项：① body 是否可读 ② TLS 是终结还是透传 ③ 会话粘性是否生效 ④ 真实业务与蜜罐是否可区分 ⑤ 引擎是否真的在请求路径上 | 五项各有对应用例且能给出通过 / 失败结论 |
| **INT-18** | 观测报表 | **必须**能按站点展示 Agent 识别量与处置分布，供影子模式期间使用 | 报表字段评审 |

## 5. 会话身份

会话身份来源的优先级（三条来源**全部禁止**在客户端留下新痕迹）：

| 优先级 | 来源 | 可见性 |
| --- | --- | --- |
| ① 最优 | 业务自身的 session cookie | 零痕迹（Agent 本来就会带） |
| ② | TLS session ticket / resumption | 零痕迹 |
| ③ 兜底 | 源 IP + User-Agent + 请求头指纹（**仅首跳可用**） | 零痕迹 |

| ID | 规则 | 验证方式 |
| --- | --- | --- |
| **INT-19** | 会话身份**必须**按上表优先级选取。 | 代码评审 + 差异哨兵（无新增 cookie） |
| **INT-20** | 会话身份值**禁止**上行到业务后端、**禁止**回传给客户端。 | 集成测试（抓取上行请求与下行响应核对） |
| **INT-21** | 同一会话的后端选择**必须**幂等于该会话（跨进程重启仍成立）。 | 单元测试（同 session → 同后端） |

> 同会话的后端选择由 `director` 保证（`route_mirage` 才需要粘性；`route_origin` / `block` 不涉及后端选择）。

## 6. 接入时必须解决的五个问题

| 问题 | 解决方案 |
| --- | --- |
| **HTTPS 解密** | 引擎持有证书，或 LB 卸载 TLS 后透传明文。**若走透传则读不到 body，欺骗式响应做不了** |
| **单点故障** | 引擎集群化 + VIP/健康检查自动摘除；核心故障 fail-open（见 [`architecture.md`](architecture.md) 的 AR-8） |
| **性能损耗** | 引擎无状态化 + 本地判定缓存 + 异步上报；P99 预算见 [`architecture.md`](architecture.md) §6 |
| **真实 IP 丢失** | 透传 `X-Forwarded-For` / `X-Real-IP`，或使用 PROXY protocol |
| **误伤正常用户** | 灰度 + 白名单 + 只对高置信可疑引流；阈值集中管理 |

| ID | 规则 | 验证方式 |
| --- | --- | --- |
| **INT-22** | TLS **必须**能读出请求体，否则**禁止**启用误导处置（只允许观察）。 | `shen doctor` 检查项 ① ② |
| **INT-23** | **必须**透传真实来源 IP；**禁止**因接入导致业务侧丢失客户端 IP。 | 接入演练 + 业务侧日志核对 |
| **INT-24** | 判定阈值、隔离有效期、去重窗口**必须**集中定义并可由配置覆盖。 | 代码评审（无散落硬编码） |
| **INT-25** | **必须**有白名单机制（内部 IP、健康检查、监控探针）并**必须**在引流判定前生效。 | 单元测试 |

## 7. 流水（判定分支简化视图）

```text
请求进入引擎
    │
    ▼
┌─────────────────┐
│ 1. 白名单检查    │──是──► 直接透传（内部 IP、健康检查）
└────────┬────────┘
         │ 否
         ▼
┌─────────────────┐
│ 2. 查本地缓存    │──命中──► 按缓存结果处置（不调用核心）
└────────┬────────┘
         │ 未命中
         ▼
┌─────────────────┐
│ 3. 调用核心判定  │  deadline ≤ 3ms；超时 → fail-open 放行
└────────┬────────┘
         │
         ▼
   按返回动作处置 → 记录遥测 → 高风险触发告警
```
