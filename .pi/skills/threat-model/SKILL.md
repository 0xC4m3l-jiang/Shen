# 威胁建模

威胁模型的作用是**把"我们假设对手不能做什么"写出来**——因为所有安全设计的漏洞都藏在那句没写出来的假设里。

## 顺序（不可颠倒）

1. **资产**：我们真正要保护的东西。不是"系统"，而是具体的东西（数据、可用性、第三方不被牵连、团队不担责）。
2. **对手**：分成 2–4 个具体档位，不要写"攻击者"这种笼统词。
3. **信任边界**：数据从哪里进来，在哪里从"不可信"变成"可信"，由谁执行这个转换。
4. **失效路径**：对手如何达成目标。
5. **缓解 → 残余风险 → 检测方式**。

## 对手档位表

对每一档写清「能力 / 资源 / 动机 / 已知技术 / 会被什么劝退」：

| 档位 | 能力 | 资源 | 动机 | 已知技术 | 劝退因素 |
| --- | --- | --- | --- | --- | --- |
| 脚本小子 | | | | | |
| 自动化扫描器 | | | | | |
| 自主渗透 Agent | | | 推理 + 工具集 + 记忆 | | |
| 有备而来的人类红队 | | | | | |

**关键**：把「对手会推理、会记忆、会跨会话复用结论」显式写成能力，而不是默认没有。

## 欺骗类系统的专用一节：识破路径

欺骗系统的威胁模型必须额外回答「对手怎么发现这是假的」。逐条给出**可观测的识破信号**与**我们能否检测到对手已识破**：

| 识破路径 | 对手需要的观察 | 我们是否可检测 | 缓解 | 缓解的代价 |
| --- | --- | --- | --- | --- |
| 内容不一致（两次访问不同） | | | | |
| 时序异常（延迟分布不同） | | | | |
| 元数据泄漏（头/证书/错误页） | | | | |
| 环境矛盾（不该存在的服务） | | | | |
| 行为反馈（写入不生效） | | | | |
| 跨会话记忆（把特征带出去复用） | | | | |
| 主动探测（故意注入标记再看回显） | | | | |

最后一列是重点：**如果缓解代价高于收益，就明确接受这个风险，而不是假装它不存在。**

## 必答问题清单

- 对手**已经知道**我们存在、并知道我们在欺骗，会怎样？（安全性不能依赖隐蔽）
- 对手换一个身份标识（UA / 会话 / 出口 IP）要花多少成本？
- 误处置一个正常用户的后果是什么？谁承担？
- 我们的日志本身是不是新的攻击面（记录了什么敏感信息、谁能看）？
- 我们会不会牵连第三方（伪造他人品牌、指向他人地址、发载荷给无关主机）？
- 失败模式是「失效开放」还是「失效关闭」？是否与业务期望一致？
- 我们如何知道防御**正在起作用**（而不是只看到它在运行）？

## 输出格式

```markdown
## 资产
## 对手（分档）
## 信任边界图（文字版即可：谁 → 谁，经哪里，在哪一步校验）
## 威胁表
| # | 威胁 | 前提 | 影响 | 现有缓解 | 残余风险 | 检测方式 |
## 识破路径（欺骗类专用）
## 明确接受的残余风险（附理由与复查条件）
## 未覆盖的部分
```

## 纪律

1. **区分「我们声称」与「我们证明」。** 没有实验支撑的缓解措施要标注为「设计意图，未验证」。
2. **残余风险必须显式接受。** 写「已缓解」但实际上只降低概率的，要写明降低后的量级。
3. **威胁表要有编号。** 编号才能被设计文档、测试用例、事故复盘引用。
4. **不写无对手的威胁。** 每条威胁都要指向具体档位；没有对手能实施的威胁是噪音。

## 反模式

- ❌ 只列攻击类型（SQLi/XSS…）而不列对手与信任边界——那是漏洞清单，不是威胁模型。
- ❌ 把「隐蔽」当作防御（安全性依赖对手不知道）。
- ❌ 假设对手不会读文档、不会换 UA、不会记住上次的结论。
- ❌ 忘记自己的日志/后台本身是资产与攻击面。
