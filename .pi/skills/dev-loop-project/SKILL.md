# 本项目的开发规范（实例化）与开工纪律

**通用部分不在本文件**：S/M/L 分级、五步流程、产物形状、评审、返工路径、输出形状
全在全局技能 `dev-loop`（绝对路径 `~/.pi/agent/skills/dev-loop/SKILL.md`，可用 `/skill:dev-loop` 加载）。
本文件回答：**在这条仓库里，那些规范落到什么路径、什么命令、什么边界上，以及动手前必须确认什么。**

## 0. 开工顺序（不许跳）

1. 读 [`AGENTS.md`](../../../AGENTS.md)（项目强制规范，**最优先**）
2. 读 [`.pi/devloop.md`](../../devloop.md)（**适配面**：文档路径 / 验证命令 / 依据在哪）
3. 读全局技能 `dev-loop`（流程与产物形状）；L 档收尾再读 `audit`（审视）
4. 判改动分级 **S / M / L** → 按该档的必做项走
5. 过一遍下面的**开工门禁**，再动第一行代码

## 1. 开工门禁（4 项，逐条确认）

- [ ] **要解决的问题**能用一句话说清，且用户认可这个表述。
- [ ] 这个改动会固化的技术选择，是否已有决策记录（`docs/background/decisions/`）或用户的明确指示？
      **没有 → 停下来先做 `evidence-and-decisions`（写 ADR），不要边写边定。**
- [ ] 我知道**「做完」的判定标准**（可验证的形式，不是「功能可用」）。
- [ ] 我知道哪些东西**不在**本次范围内。

任何一条不成立，就先问，不要先写。**问一句的成本远低于重做。**

## 2. 范围纪律

### 2.1 改动范围声明（第一次改动前给出）

```text
要改：<文件/模块> —— <为什么必须改>
不改：<看起来相关但不动的> —— <为什么不动>
不动但已注意到：<发现的问题> —— <建议另开一条>
```

「不动但已注意到」这一栏很重要：它让你报告发现而不擅自修，双方都不丢信息。

### 2.2 最小实现（6 条）

1. **一次只做一件事** —— 顺手重构、顺手加抽象、顺手升级依赖，全部拆出去。
2. **不加未要求的层** —— 没有第二个实现就不要抽接口；没有第二个调用方就不要提公共方法。
3. **不预置依赖** —— 引入任何库/工具/服务先问：它是长期成本。
4. **不预置配置项** —— 没人会改的开关不要加。
5. **不生成样板** —— 除非用户要，不要铺几十个文件/目录/测试占位。
6. **不替用户决定** —— 语言、框架、存储、部署形态、协议是用户的决定。

### 2.3 明确禁止（踩过的坑）

| 禁止 | 说明 |
| --- | --- |
| 替用户做技术选型 | 选型属于「决策」，先讨论 |
| 大范围预实现 | 用户要「能跑的最小骨架」，不要给完整系统 |
| 未授权安装 | 不装包、不改全局配置，除非用户要求 |
| 改用户既有文件 | 移动/重命名/改写前先问，并留可恢复路径（本仓库无 git：**先备份到仓库外**） |
| 悄悄扩大范围 | 「顺便把 X 也做了」是失控的开始 |
| 伪造完成度 | 未实现的部分必须显式标注，不要在文档里写得像已完成 |

### 2.4 变动纪律

- 一次改动一个逻辑单元；说明写**为什么**，不写「update」。
- 破坏性操作（删除、移动、覆盖）前：备份到仓库外可恢复位置，并**告知备份路径**（例：本轮直接删掉的第三方技能备份在 `~/.pi/backups/removed-skills/`）。
- 删除/替换既有实现必须写明：删了什么、为什么它失去了对象、怎么恢复（技能 `audit` 的门槛 ④）。

## 3. 本项目必须遵守的四条

| # | 规则 | 为什么 |
| --- | --- | --- |
| 1 | **开工前加载全局 `dev-loop` 技能**；未加载即视为流程未执行 | 全局 `AGENTS.md` 的强制条款 |

| 4 | **未识别状态必须回落放行到真实业务**（`NI-1` 优先级最高） | 不影响原始业务是首要约束 |

## 4. 追溯检查（本项目的实现）

`make trace` 是技能 `dev-loop` §5 那个「追溯接口」的本项目实现（源码 `scripts/tracecheck/`）。

| 核什么 | 依据 |
| --- | --- |
| 模块目录 ↔ 模块文档（九章）↔ 单测文件 | `MD-2` / `MD-17` / `MD-22` |
| 规则 ID 引用必须真实存在（定义或已在 `design/README.md` §4 登记） | `D-3` / `D-8` |
| 变更包模板与变更日志最新条目的形状 + 引用的路径必须存在 | 技能 `DEV-1` / `DEV-2` |
| `AGENTS.md` 点名的技能文件存在且有 `name` / `description` | 技能 `DEV-3` |
| 过期状态标记（「待建」却已存在） | 技能 `audit` `TC-2` |
| 悬空链接（相对路径 / `~/`） | 技能 `audit` `TC-3` |

**缺口的处理**（不许静默放过）：

- 已知缺口 → 写进 `scripts/tracecheck/allow.txt`**并写理由**；豁免**过期会被报出来**，必须删；
- 「尚未升格为规则的约定」→ 输出为**提示**，不拦门禁；
- 解析结果不合预期（清单骤降、文档格式变了）→ **直接失败**，不静默放行。

## 5. 验证入口（本项目特有）

| 命令 | 用途 |
| --- | --- |
| `make check` | 快速内循环：构建 + 格式化 + vet + 架构 + 追溯 |
| `make gate` | **一轮的验收命令**：静态检查 + 架构 + 追溯 + 许可 + 单测（`-race`） |
| `make dev` | 效果验证：配置干跑（合法 + 非法）→ 起核心 → 在线冒烟 → 规则回放 |
| `make replay` | 规则回放：样本 → 分数 → 命中信号（判定响应不回显分值，只能在这里看） |
| `make smoke` | 在线冒烟：判定面形状、三值闭集、`decision_id` 幂等 |

> 判定响应禁止回显分值、规则名与证据（`ST-7`）—— 「规则命中」只能从 `make replay` 与启动日志看。

## 6. 规则 ID 体系

规则 ID（`AR` / `INT` / `ST` / `MD` / `NI` / `TB` / `TM` / `SB` / `OH` / `BA` / `D`）的定义与废弃登记
在 [`docs/design/README.md`](../../../docs/design/README.md)。

- 引用前先确认存在（`make trace` 会核）；
- **废弃的 ID 不得删除、不得复用**（`D-6`）；引用废弃 ID 必须同时给出取代者；
- 追溯矩阵写规则 ID，不写「见 `design/`」。

## 7. 完成定义（本项目的补充项）

除全局技能 §10 的 DoD 之外：

- [ ] `make trace` 零错误（提示与登记豁免单独列出，允许存在但必须知情）
- [ ] `make dev` 输出 PASS，关键行贴进变更包 §6
- [ ] 变更日志在 [`docs/log.md`](../../../docs/log.md) 追加一条
- [ ] **L 档做过审视**（全局技能 `audit`：`~/.pi/agent/skills/audit/SKILL.md`），审视表写进变更包 §7.1
- [ ] 若动了 `docs/design/` → 有用户确认的记录；若动了数据模型 → 同步 `structure.md` §3 与 `spec/`

### 7.1 审视在本项目的落地

| 机器能核（已在 `make trace`） | 只能人读（按 `audit` §2 / §3 走） |
| --- | --- |
| 悬空规则 ID · 孤儿模块文档 · 过期状态标记 · 悬空链接 · 过期豁免 | 语义是否一致 · 叙述是否误导 · 内容是否真无用 · 代码已做而文档未写 |

> 历史记录类文件（`docs/background/` · `docs/plans/` · `docs/log.md` · `docs/kb/`）**不在审视范围内**：
> 它们是当时的快照，写下过时内容是正确的。

## 8. 反模式

- ❌ 「先把架子搭起来，回头再对齐决策」—— 架子会变成既成事实。
- ❌ 用大量代码回答一个还没定的设计问题。
- ❌ 把「我实现了」当成「问题解决了」；把「测过一遍」当成「有证据」。
- ❌ 在文档里把计划写成现状。
- ❌ 为了「看起来干净」删历史记录（见 `audit` 门槛 ③）。
